### ① RRF 算法实现

```python
def reciprocal_rank_fusion(rankings, k=60):
    """RRF — 多路排名融合，消除量纲差异。

    BM25 得分 0~几十，向量余弦相似度 0~1，直接加权 BM25 会碾压。
    RRF 用排名替代分数：score(chunk) = Σ 1/(k + rank(chunk))
    """
    scores = {}        # chunk_id → rrf_score
    chunk_map = {}     # chunk_id → (Chunk, original_source)

    for ranking in rankings:
        for rank, result in enumerate(ranking, start=1):
            cid = result.chunk.chunk_id
            scores[cid] = scores.get(cid, 0) + 1.0 / (k + rank)
            if cid not in chunk_map:
                chunk_map[cid] = (result.chunk, result.source)

    # 按 RRF 得分降序
    sorted_items = sorted(scores.items(), key=lambda x: x[1], reverse=True)

    results = []
    for cid, rrf_score in sorted_items:
        chunk, source = chunk_map[cid]
        chunk.metadata["rrf_score"] = round(rrf_score, 6)
        chunk.metadata["original_source"] = source
        results.append(RetrievalResult(chunk=chunk, score=rrf_score, source="rrf"))
    return results
```

**面试时边写边说**：
- k=60 是平滑常数，k 越小排名靠前的文档权重越大，消融实验验证 30/60/120 结果一致
- 时间复杂度 O(NlogN)，瓶颈在 sort，多路排名通常很短（Top-20），实际 <1ms
- 不依赖原始分数，天然消除 BM25（词频整数）和向量（余弦相似度 0~1）的量纲差异

### ② BM25 检索流程

```python
class BM25Retriever:
    def __init__(self, chunks):
        self.chunks = chunks
        self._tokenized_corpus = []
        self._bm25_map = []

        for idx, chunk in enumerate(chunks):
            tokens = list(jieba.cut(chunk.content))
            tokens = [t.strip() for t in tokens if t.strip()]
            if tokens:
                self._tokenized_corpus.append(tokens)
                self._bm25_map.append(idx)

        self._bm25_index = BM25Okapi(self._tokenized_corpus)

    def search(self, query, top_k=20):
        query_tokens = [t.strip() for t in jieba.cut(query) if t.strip()]
        scores = self._bm25_index.get_scores(query_tokens)
        top_indices = np.argsort(-scores)[:min(top_k, len(scores))]

        results = []
        for local_idx in top_indices:
            bm25_score = float(scores[local_idx])
            if bm25_score <= 0:
                continue
            chunk_idx = self._bm25_map[local_idx]
            results.append(RetrievalResult(
                chunk=self.chunks[chunk_idx], score=bm25_score, source="bm25"
            ))
        return results
```

**面试时边写边说**：
- jieba 分词 → 中文按词切分而非字符 n-gram，专有名词不会被拆碎
- `rank_bm25` 库底层是 BM25Okapi 算法，TF 饱和 + IDF 逆文档频率 + 文档长度归一化三因子
- 空 token 过滤：纯标点/空白 Chunk 跳过，避免空字符串污染索引
- 零分结果过滤：score ≤ 0 的不返回，BM25Okapi 对完全不相关的 query 会打出负分

### ③ Cross-Encoder 精排流程

```python
class CrossEncoderReranker:
    def __init__(self, model_name="cross-encoder/ms-marco-MiniLM-L-6-v2"):
        self.model = CrossEncoder(model_name)

    def rerank(self, query, candidates, top_k=5):
        # 1. 构造 query-doc pairs
        pairs = [(query, r.chunk.content) for r in candidates]

        # 2. 联合编码 → 一次性做完整注意力计算
        scores = self.model.predict(pairs, show_progress_bar=False)

        # 3. 按 CE 得分降序，取 Top-K
        scored = list(zip(candidates, scores))
        scored.sort(key=lambda x: x[1], reverse=True)

        results = []
        for rank, (candidate, ce_score) in enumerate(scored[:top_k]):
            meta = dict(candidate.chunk.metadata)
            meta["ce_score"] = round(float(ce_score), 4)
            meta["ce_rank"] = rank + 1
            results.append(RetrievalResult(
                chunk=Chunk(content=candidate.chunk.content, metadata=meta,
                            chunk_id=candidate.chunk.chunk_id),
                score=float(ce_score), source="cross_encoder",
            ))
        return results
```

**面试时边写边说**：
- Cross-Encoder 把 `(query, doc)` 拼接后送入模型做一次完整前向传播，query 和 doc 的每个 token 之间都有注意力交互
- 对比 Bi-Encoder——query 和 doc 分别独立编码，快但 query-doc 之间没有交互
- 两阶段策略：Bi-Encoder 粗筛 Top-20（快），Cross-Encoder 对 20 个候选精排 Top-5（准）

## 第二部分：三个必问题逐字稿

### 必问题 1：BM25 和向量检索有什么区别？为什么都用？

**面试官**："你用了 BM25 和向量检索双路召回，它们到底有什么区别？"

**回答**："两个字面维度：

**原理层**：BM25 是稀疏的关键词匹配，基于 TF-IDF 变体——TF 饱和曲线控制词频权重、IDF 抑制高频词、文档长度归一化防止长文档霸榜。向量检索是把句子编码成 384 维的稠密向量，在高维空间里算余弦距离。前者看字面，后者看语义。

**优劣势**：BM25 对专有名词、报错编号、数字精确匹配极强——你搜 'Cross-Encoder'，它绝对不会把 'Bi-Encoder' 捞出来。但它对同义词盲视——搜 '怎么评价检索系统'，语料里写的是 '评测好坏'，字面一个都不重合，BM25 MRR=0。向量检索反过来——它能理解 '评价' ≈ '评测'，语义召回极强，但对专有名词区分度弱。

**为什么都用**：我的消融实验给了硬数据——exact_match 类查询 BM25 和 Vector 持平，semantic 类 Vector 碾压 BM25。两者各有所长，混合才完整。这正是两阶段架构的起点。

**延迟代价**：BM25 <1ms，向量检索包括 encode + ChromaDB 查询约 100ms，差距两个数量级。所以我把 BM25 放在最前面当快速筛子。"

---

### 必问题 2：RRF 和加权求和有什么区别？为什么选 RRF？

**面试官**："为什么用 RRF 融合而不是直接加权求和？"

**回答**："核心问题是**量纲差异**。

BM25 的原始得分是词频统计值——可能 0 到几十。向量检索的余弦相似度是 0 到 1。如果直接加权，BM25 的分数会像坦克一样碾压向量检索的结果——你哪怕给向量 0.01 的权重也没用，因为它不知道 BM25 得分 20 是算高还是算低。

**RRF 的解法**：完全不看原始分数，只看排名。`score = Σ 1/(k + rank)`。排名第 1 永远得 1/(60+1)=0.0164，不管你是 BM25 的 22.5 分还是向量的 0.89 分。这天然消除了量纲差异。

**代价**：RRF 丢弃了分数梯度信息。比如 BM25 的 Top-1 和 Top-2 可能实际得分差了一个量级，但在 RRF 眼里它们就是 rank 1 和 rank 2 的区别。但实际工程中这个代价可接受——融合后还有 Cross-Encoder 做精细重排，RRF 只需要负责把两路的 '好苗子' 都拉进来就行。

**为什么不用学习型融合**（如 LambdaMART）：需要训练数据和在线特征工程，我的场景是零样本冷启动，RRF 不需要训练，开箱即用。"

### 必问题 3：Bi-Encoder 和 Cross-Encoder 有什么区别？为什么两阶段？

**面试官**："你的 VectorRetriever 不就是向量检索吗，后面再加 Cross-Encoder 不是重复了？"

**回答**："不重复，它们是**完全不同**的工作机制。

**Bi-Encoder 是怎么做的**：query 和所有 doc 分别独立过 encoder，各得到一个 384 维向量，然后算余弦相似度。这意味着 query 和 doc 之间**没有任何 token 级别的交互**——query 的 '如何评价' 和 doc 的 '评测好坏' 能不能对上，全靠训练时学到的句子级语义表示。好处是 doc 向量可以提前离线算好存到 ChromaDB，检索时只算 query 向量，一次查询只需 1 次模型推理 + 1 次向量相似度查找。适合**全库粗筛**。

**Cross-Encoder 是怎么做的**：把 `query [SEP] doc` 拼接成一对，送进 Transformer 做一次完整的前向传播。每个 token 都能看到对面所有 token。这意味它能捕捉 query-doc 之间的精细交互——比如 query 里的 '评价' 和 doc 里的 '评测' 究竟是不是在同一个语境下。代价是每一对 query-doc 都要做一次独立推理。做不到离线缓存，只能在线跑。

**两阶段的必要性**：Bi-Encoder 粗筛全库（快，100ms），Cross-Encoder 精排 Top-20（慢，~200ms）。如果直接用 Cross-Encoder 扫全库几百个 Chunk，延迟会爆炸。如果只用 Bi-Encoder，粗筛质量不够。消融实验证明了这一点——只用 RRF 的 MRR 是 0.93，加了 CE 提升到 1.0，代价是延迟翻倍。这是典型的**精度-延迟的工程权衡**。"

### 追问 1：CE 延迟优化（92% → 砍半）

**问题**：Cross-Encoder 精排把语义盲区的 MRR 从 0 救回 1.0，但它占了总延迟的 92%。在不牺牲太多召回精度的前提下，把延迟至少砍掉一半，你会从哪些方向优化？

**答题框架：先亮公式，再三条线展开**

```
CE 总延迟 = 单次推理延迟 × 候选数量
```

所有优化方案，要么砍左边，要么砍右边，要么并行重叠。

**方向一：减少候选数量（砍右边）— P0 优先**

| 方案 | 思路 | 效果 |
|------|------|------|
| 固定 top-K 截断 | RRF 后直接取前 20 | 候选从 40→20，延迟直接减半，零风险 |
| 自适应截断 | 根据 RRF 分数分布形状动态决定 K | 好查询截到 5 个，模糊查询保留全部 |
| 置信度门控 | RRF top-1 分数远超后续 → 直接跳过 CE | 高置信场景零 CE 成本 |

自适应截断的核心思路：固定截断用**位置**做决策，自适应截断用**信号的形状**做决策——检测 RRF 分数序列的衰减模式，如果第 5 位后出现断崖式下跌（相邻分数衰减率 > 阈值），在断崖处熔断；如果分数一路平缓下降，不截断，让 CE 全力精排。最小保留 5 个，最大保留原始候选数。

**方向二：降低单次推理延迟（砍左边）— P1**

| 方案 | 思路 | 延迟削减 | 代价 |
|------|------|----------|------|
| INT8 量化 + ONNX Runtime | 模型压缩 | ~20-35% | 需校准数据集，可能微掉点 |
| 换轻量 CE（MiniLM 6 层） | 更小的模型 | ~50% | 精度需验证 |
| 知识蒸馏 | 大 CE 教小 CE | ~50% | 训练成本高 |

**方向三：并行 / 流水线 — P2**

| 方案 | 思路 |
|------|------|
| CE 与 LLM 生成并行 | RRF 出结果后，一边跑 CE 精排，一边用未精排的 top-N 构建 prompt 预填充 KV cache |
| Batch CE | 多个 query 的候选合并成 batch 一次推理，利用 GPU 并行度 |

**回答收尾**：P0（砍候选）+ P1（量化）组合已经稳超 50%。自适应截断的阈值需要用生产数据持续校准，如果分布漂移导致截断率异常，回退到固定 top-K，保证 SLA 兜底。

### 追问 2：Bi-Encoder 二次过滤为什么是错的

**问题**：在 RRF 之后、CE 之前，能不能用 Bi-Encoder 的余弦相似度阈值再做一次过滤，减少 CE 候选量？

**答案：不行，这会破坏双路召回互补的前提假设。**

BM25 存在的价值恰恰是补充向量检索（Bi-Encoder）的语义盲区——专有名词、型号、代码片段等字面匹配强的内容，在 Bi-Encoder 眼里相似度天然偏低。用 Bi-Encoder 做阈值过滤，等于**用向量检索的偏见去否决 BM25 的贡献**——那些 BM25 辛辛苦苦捞上来、向量检索天然打低分的专有名词相关候选，会被 Bi-Encoder 阈值直接过滤掉。

结果：双路召回 → 又变回单路召回的瓶颈，而且多了一次模型推理，延迟不降反升，架构复杂度白增加。

**核心教训**：优化方案不能破坏上游模块存在的前提假设。正确的替代方案是直接基于 RRF 分数本身做截断，而不是引入一个新的评分模型。

### 追问 3：RRF 的 k 值怎么定

**问题**：经典默认 k=60，你是怎么定义这个值的？

**第一步：k 控制的是排名曲线的"陡峭度"**

| k 值 | rank=1 权重 | rank=N 权重 | 效果 |
|------|-----------|------------|------|
| k→0 | 极大 | 极小 | 只有 top-1 说了算 |
| k→∞ | 均等 | 均等 | 排名信号完全抹平 |
| k=60 | 适中 | 适中 | 头部有优势但不独裁 |

**第二步：60 没有理论推导。** 它是 Cormack 等人在 2009 年 TREC 数据集上网格搜索扫出来的经验值。换个数据集、换个候选规模，60 未必最优。

**第三步：正确的设置方式——k 与候选规模绑定。** 先确定期望的权重比（rank=1 与 rank=N 的权重比 r），再反推 k：

$$k = \frac{N - r}{r - 1}$$

以本项目为例：RRF 输入候选池 N=40（BM25 top-20 + Vector top-20），期望 rank=1 权重是 rank=40 的约 3 倍，代入得 k = (40-3)/(3-1) = 18.5。在验证集上以 MRR 为目标扫 k ∈ [10, 50]，实验最优 k=30。

**结论**：k 不是 magic number，是"你允许多少权重比"的数学表达。本项目实际数据：参数消融实验中 RRF_K ∈ {30, 60, 120} 在小语料下全部 MRR=1.0，系统对 k 不敏感。

### 追问 4：BM25 vs 向量，各自在什么情况下更强

**分场景数据（来自 15 组 GoldenTestSet）**

| 类别 | BM25 MRR | Vector MRR | Full Pipeline MRR |
|------|----------|------------|-------------------|
| exact_match（E01-E05） | 1.0 | 1.0 | 1.0 |
| mixed（M01-M05） | 0.9 | 0.9 | 1.0 |
| semantic（S01-S05） | **0.8** | **1.0** | **1.0** |

**BM25 的优势**：专有名词和精确术语匹配。query 中的关键词在文档中原文出现时，BM25 精准命中。

**向量检索的优势**：自然语言语义查询。典型案例 S03——"怎么评价一个检索系统好不好？"——query 里没有一个词直接命中文档中关于 Ragas 评测框架的部分：BM25 MRR = 0.0（完全失效），Vector MRR = 1.0（通过语义理解准确命中）。

**BM25 最致命的短板**：不是精确匹配不强，而是**它会引入强噪声**。S03 中 BM25 给不相关 chunk 打了 1.2 分排第一，直接把 RRF 融合后 MRR 从 1.0 拖到 0.5。好在 CE 精排兜底，最终修正回 1.0。

**怎么调两路权重**：答案是没有调，刻意不调。BM25 原始分数范围 0~几十，向量余弦相似度 0~1，直接加权融合 BM25 会靠量纲优势主导排序。采用的方案是 RRF 而非加权融合——只用排名位置，不用原始分数，天然消除量纲差异。核心结论：BM25 和向量检索的权不是"调"出来的，而是通过架构选择（RRF + CE）让它们各自在自己的优势区发挥作用。

### 追问 5：GoldenTestSet 构建 + 改写评测

**问题**：你的 GoldenTestSet 是如何构建的？怎么判断改写后的查询是"变好了"还是"变差了"？

**第一问：GoldenTestSet 如何构建**

15 组 query，手动构建，按检索难度分三类各 5 组：

| 类别 | 设计意图 | 示例 |
|------|----------|------|
| exact_match（E01-E05） | 专有名词精确匹配，测 BM25 优势 | "RRF 融合算法"、"Cross-Encoder 重排序" |
| semantic（S01-S05） | 口语化语义查询，字面不匹配，测向量 | "怎么评价一个检索系统好不好？" |
| mixed（M01-M05） | 综合多段信息，测全链路 | "混合检索加重排序比单纯用向量检索好在哪里？" |

每条用例含四个字段：`query`、`golden_chunk_sources`（文档级来源）、`golden_answer`（参考答案）、`notes`（测试意图说明）。

**为什么手动而非自动生成？** 在小规模语料下，人知道每一组 query 在测哪个模块的哪个能力（E01 测 BM25 对缩写术语的敏感度，S03 测向量对"评价"≈"评测"的语义理解）。自动生成做不到这种分层覆盖的意图设计。

**第二问：怎么判断改写后变好还是变差**

核心思路是 A/B 对比——对每组 test case 分别用原始 query 和改写 query 走全链路检索，计算 Δ = 改写后 MRR - 改写前 MRR。Δ > 0 → 改写有效，Δ < 0 → 改写退化。

同时做语义保真度检查：改写可能提升 MRR 但跑偏意图。用 LLM-as-Judge 判断"改写后的查询是否保留了原始的信息需求"，输出 fidelity_score 0~1。

再加 CE 阈值校准：原阈值 3.0 是拍脑袋的。扫 1.0~6.0，用"改写是否实际提升了 MRR"作为 ground truth，找 F1 最高的阈值。

### 追问 6：好的面试答案的共同结构

回顾所有追问，好的回答都有统一框架：

1. **先定义问题空间**（公式或前提假设）——CE 延迟 = 单次 × 候选数；RRF k 值 = 权重比的数学表达
2. **再按方向展开方案**——每个方向讲清做了什么、为什么、代价是什么
3. **最后点明风险和兜底策略**——分布漂移、回退机制
