# 第 3 章：BM25 + ChromaDB 双路召回

## 知识点

### 1. 为什么要请"两位性格相反"的查书军师

没有任何单一检索算法是完美的。所以同时聘请两位逻辑截然相反的军师并行查书：

| | BM25（字面匹配狂） | ChromaDB（AI 语义大师） |
|---|---|---|
| **性格** | 死脑筋会计，只看字面拼写 | 精通阅读理解的文科生 |
| **擅长** | 专有名词、报错代码、API 编号 | 同义词、意图泛化、口语转术语 |
| **致命短板** | 不懂同义词，搜"Q3营收"匹配不上"第三季度财务" | 面对冷门编号过度联想，把精准纸条稀释掉 |

**互补证据**：

| 场景 | BM25 | 向量 |
|------|------|------|
| 精确字面匹配 "ERR-429" | ✅ 瞬间命中 | ❌ 语义扩散，不精确 |
| 同义词转化 "医疗" → "卫生" | ❌ 完全无匹配 | ✅ 高度敏感 |
| 专有名词 "Transformer" | ✅ IDF 极高，一击命中 | ⚠️ 相关但不精确 |
| 语义查询 "怎么评价检索系统" | ❌ 字面没出现"评测" | ✅ 语义匹配命中 |

### 2. BM25 关键词检索 —— 三因子共同打分

BM25 不理解语义，只通过三个数学零件给每张纸条打分：

**① IDF（逆文档频率）—— 寻找罕见核心词**

```
IDF = log((N - df + 0.5) / (df + 0.5))
```

物理作用：衡量一个词有多罕见。"的"、"是"在整库泛滥，IDF 趋近于 0，分配极少权重；"Transformer"、"ERR-429" 在全库中凤毛麟角，一旦命中 IDF 爆炸式飙高。**IDF 让算法自动忽略废话，锁定核心线索。**

**② TF 饱和曲线 —— 遏制"复读机"刷分作弊**

```
TF_score = TF / (k1 * (1 - b + b * doc_len / avg_len) + TF)
```

物理作用：**限速器/刹车片**。随着关键词在当前纸条中出现次数（TF）增加，分数不会线性无限增长，而是呈现弯曲的饱和效应（`k1` 默认 1.5 控制饱和速度）。提及 1 次给 0.6 分，2 次给 0.8 分，3 次以上分数钝化封顶。**彻底剥夺靠疯狂复制粘贴关键词注水刷分的作弊可能。**

**③ 长度归一化 —— 维护短句的尊严**

通过 `doc_len / avg_len`（参数 `b` 默认 0.75 控制强度）调节分母。长文因为字数多，天然更容易撞上关键词。该因子发现当前纸条极短时，会缩小分母从而**狠狠给短句拉高总分**——因为短句是在精准、高密度地讨论这个话题，而长文命中大概率只是"水字数"。

**BM25 vs TF-IDF**：TF-IDF 的 TF 是原始词频，长文档或复读机刷频会产生碾压级高分作弊。BM25 引入了 TF 饱和曲线 + 长度归一化，对文档长度更鲁棒。

### 3. ChromaDB 向量检索 —— 384 维语义空间

**Embedding 模型：all-MiniLM-L6-v2**
- 吐出 384 维稠密向量，参数量 ~22M
- 本地 CPU 毫秒级推理
- 最大输入 256 token

**文本变向量的三步流水线**：

1. **Tokenize（查字典编号）**：模型拿过文本，去自带字典里查出数字代号
2. **Model Forward（走矩阵乘法迷宫）**：代号送入 12 层 Transformer，在几千万参数里走矩阵乘法，字面被完全剥离，留下的是抽象语义特征
3. **Pooling（提炼语义特征）**：输出层吐出 384 个高精度浮点数——这句话在 384 个抽象语义维度上的几何坐标

**为什么手动 embedding 而不是 ChromaDB 内置**：

| 维度 | 内置 embedding_function | 手动 embedding |
|------|------------------------|---------------|
| 可解释性 | 黑盒，不知道向量怎么来的 | 能背诵上面三步流水线 |
| 进度监控 | 无 | 可以套 `tqdm` 进度条 + 控制 `batch_size` |
| 换模型 | 需要改 ChromaDB 注册机制 | 改 `SentenceTransformer(model_name)` 一行 |
| 面试价值 | "我调了 API" | "我理解向量生成的每一步" |

**ChromaDB 的角色**：它自己不会算向量。它在应用层接过算好的 384 维数组，使用 **HNSW（层次导航小世界）** 图算法在磁盘上把坐标连成一个空间立体几何网。检索时，ChromaDB 在几何网里计算 query 向量与库内每条向量的余弦距离（Distance），值越小越相似。

**距离 → 相似度的数学反转**：`similarity = 1.0 - distance`。几何学上距离越近（趋近 0）越相似，反转后变成符合人类直觉的 1→0 相似度得分。

### 4. 为什么两路都保留原始分数

- BM25 得分量级：0~几十（IDF + TF 累加）
- 向量余弦相似度：0~1（被 cosine 严格限定）
- 如果在此阶段强行归一化，会产生权重失真
- **工业级做法**：各自保持原始分数，量纲差异交给第 4 章的 RRF 处理。RRF 根本不看绝对分数，只看排名。

### 面试速记

- **BM25 原理一句**：TF 饱和 + IDF 逆文档频率 + 长度归一化，三因子防刷分、锁核心词、护短句
- **BM25 vs TF-IDF**：BM25 多了饱和曲线和长度归一化，对文档长度鲁棒
- **两路互补本质**：BM25 是"死脑筋会计"，向量是"语义理解文科生"，性格相反的军师查同一本书
- **手动 embedding 的理由**：Tokenize → Forward → Pooling 三步全透明，面试能背诵
- **HNSW 是什么**：在 384 维空间里画几何网，近似找最近邻居，省去全库逐一比对
- **面试完整话术**：被问"检索层怎么设计的"时，先讲两路互补的架构决策，再抛出两个工程坑：① `_bm25_map` 账本解决空分词导致的索引错位；② 手动 embedding 实现应用层与向量数据库完全解耦，换模型只需一行代码

## 关键实现

### ① BM25 索引映射 —— `_bm25_map` 账本防错位

```python
for idx, chunk in enumerate(chunks):
    tokens = list(jieba.cut(chunk.content))
    tokens = [t.strip() for t in tokens if t.strip()]
    if tokens:                              # 只有分词后不为空的纸条才入库
        self._tokenized_corpus.append(tokens)
        self._bm25_map.append(idx)          # 账本：BM25内部序号 → 原始Chunk真实序号
```

**追问应对**：「为什么不用 `enumerate` 的 index 直接当 BM25 索引？」— 有些 Chunk 分词过滤后全为标点符号（如 Markdown 的 `|---|` 表格分隔线），它们被 BM25 索引库拒收。如果直接用 enumerate index，BM25 算法吐出的内部序号会跟原始 `chunks` 列表发生整体位移错乱，捞出来的全是错误数据。`_bm25_map` 账本充当路由转换角色，确保内部序号能 100% 精准射回真实的原始纸条。

### ② 手动 Embedding 入库 —— 拒绝黑盒

```python
# 显式控制本地模型，将文本列表编码为 (N, 384) 稠密矩阵
embeddings = self.model.encode(texts, batch_size=32, show_progress_bar=True)

self.collection.add(
    ids=ids,
    documents=texts,
    embeddings=embeddings.tolist(),   # 自己算好的向量，不让 ChromaDB 算
    metadatas=metadatas,
)
```

**追问应对**：「不用 ChromaDB 内置 embedding_function 有什么好处？」— ① 数据全程透明可见；② 自主控制 `batch_size` 并套进度条；③ 换模型（BGE-M3、text2vec-large-chinese）只改一行代码，不依赖 ChromaDB 的注册机制；④ 面试能讲清向量生成的每一步。

### ③ 显式 query_embeddings + 几何距离反转

```python
query_embedding = self.model.encode(query)                    # 亲自把提问变成 384 维向量

results = self.collection.query(
    query_embeddings=[query_embedding.tolist()],              # 拒绝 query_texts 黑盒
    n_results=top_k,
    include=["documents", "metadatas", "distances"],
)

similarity = 1.0 - distance   # 几何距离越小越相似 → 反转为 1→0 相似度得分
```

**追问应对**：「为什么用 `query_embeddings` 不用 `query_texts`？」— `query_texts` 会让 ChromaDB 内部调用 embedding 函数生成向量，又回到黑盒。用 `query_embeddings` 意味着 query 的向量也是自己 encode 的，embedding 过程全透明。ChromaDB 只做一件事：HNSW 近似最近邻搜索。
