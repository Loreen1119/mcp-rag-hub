# 第 1 章：项目骨架与数据模型

## 一、核心蓝图：高内聚低耦合的"快递链路"

RAG 系统整体架构就像一家**高性能知识快递公司**。每一层只干一件事，只依赖上一层送过来的固定盒子，层与层之间完美解耦。

```
【离线阶段：建图书馆】
原始文档 (PDF/TXT) ──> data_pipeline.py (切成 Chunk 纸条) ──> ChromaDB (摆上书架)

【在线阶段：提问快递】
用户提问 ──> retrievers.py (初选盒子) ──> fusion.py (RRF 融合 + 重排) ──> 送给 LLM 答题
```

每层只依赖上一层输出的数据结构，层间解耦。后续任何模块内部替换（换模型、换数据库），不动其他层。

## 二、核心文件拆解与代码对照

### 1. 账本中心 —— `config.py`

整个系统的"中控面板"。所有能调节的数字（超参数）全部集中在这里，调参时只改这一个文件，不需要去业务代码里大海捞针。

```python
# 离线切片规矩
CHUNK_SIZE = 512      # 每张 Chunk 纸条的最大 Token 数
CHUNK_OVERLAP = 128   # 相邻纸条之间为了保住上下文必须重叠的字数

# 在线检索拿书的规矩
BM25_TOP_K = 20       # 传统关键词搜索引擎先挑出最像的 20 段
VECTOR_TOP_K = 20     # AI 向量搜索引擎也挑出最像的 20 段
RRF_K = 60            # RRF（倒数排名融合）算法的常数因子
CE_TOP_K = 5          # Cross-Encoder（重排序大 Boss）精选后最终送给大模型的 5 个完美答案
```

**面试话术**：「为什么不写成 YAML 或 .env？」— YAML 需要额外 parser；.env 只能是字符串。Python 文件天然支持类型（int/float/Path），`from config import RRF_K` 一行拿到值，消融实验时跑脚本直接覆盖。

### 2. 标准集装箱 —— `src/models.py`

为防止用 dict 时手抖打错字导致系统崩溃，用 Python 的 `dataclass` 定制了两个标准模具。

```python
from dataclasses import dataclass, field
import uuid

@dataclass
class Chunk:
    """模具一：纯净的小纸条（离线阶段使用）"""
    content: str                            # 纸条上裁剪下来的文字内容
    metadata: dict = field(default_factory=dict)  # 背包：装来源、页码、Markdown 标题面包屑等
    chunk_id: str = field(                  # 自动生成 8 位全局唯一身份证
        default_factory=lambda: str(uuid.uuid4())[:8]
    )

@dataclass
class RetrievalResult:
    """模具二：带分数的快递盒（在线检索阶段使用）"""
    chunk: Chunk        # 快递盒里包裹着上面的 Chunk 纸条
    score: float        # 搜索引擎给这张纸条打出的相关性分数
    source: str         # 标记来源: "bm25" | "vector" | "rrf" | "cross_encoder"
```

## 三、硬核亮点与面试话术

### 1. 为什么不用 `dict` 传数据？

**大白话**：dict 像塑料袋，装了什么运行时才知道，打错一个字母就报 `KeyError`。

**面试话术**：「我使用 dataclass 统一数据结构。它提供严格的类型提示和 IDE 自动补全，多路召回和重排的复杂管线中，拼写错误在静态检查阶段就能暴露。且相比 Pydantic，dataclass 在大规模数据流转时没有运行时校验开销，性能更优。」

### 2. 滑窗重叠（Overlap）是怎么保证句子不被砍断的？

**大白话**：普通切片是死板地数 128 个字硬剪。我的算法是"基于句子边界的贪心倒退法"——一句话一句话往回数，直到凑满 128 token。

**面试话术**：「普通的字符切片会导致语义在中途截断。我引入了基于句子边界的贪心滑窗算法。切下一个 Chunk 时，算法持有一个探测指针，从上一个 Chunk 的尾部句子开始逐句倒退，直到累计 token 数满足 overlap。这样既确保重叠度足够，又保证每个 Chunk 的开头都是一句完整的话，避免了大模型的语义误解。」

### 3. 为什么 `chunk_id` 用 UUID 截取 8 位，不用 `1, 2, 3` 自增？

**大白话**：自增 ID 在多本书一起切的时候会撞车覆盖。

**面试话术**：「在分布式或多文件并行解析的 Pipeline 中，自增 ID 会发生严重碰撞。我用 UUID 并截取前 8 位。16 进制的 8 位数拥有将近 40 亿（16^8）的空间，对于企业级知识库完全够用，兼顾了全局唯一性与日志可读性。」

## 四、版本演进的"高级叙事线"

面试时主动提起你和这个项目的"相识微时"：

- **v0.1 MetaFetch-RAG（原型版）**：纯手写 HashEmbedder（MD5 n-gram 哈希，384 维）+ InMemoryVectorStore（numpy）+ RRF，零 C 扩展依赖。证明你**精通底层原理**。
- **v0.2 mcp-rag-hub（生产版）**：用成熟的 sentence-transformers + ChromaDB 做工业级重构，加上 Cross-Encoder 重排、评测体系和 FastMCP 协议。证明你**具备生产落地能力**。

面试话术：「我先手写了一个零依赖原型彻底理解了向量检索底层原理，然后用成熟库做了生产化重构。两个版本的 RRF 融合逻辑是一样的，但工程化程度完全不同。」

## 五、Windows 环境踩坑

- **PyTorch DLL 问题**：pip 装的 PyTorch 在 Windows 上缺 VC++ 运行时。用 conda 安装：`conda install pytorch cpuonly -c pytorch`
- **OpenMP 重复加载**：Anaconda 的 MKL 和 PyTorch 各带了一份 `libiomp5md.dll`，启动报错。修复：`src/__init__.py` 首行设置 `KMP_DUPLICATE_LIB_OK=TRUE`
- **版本组合**：PyTorch 2.5.1 + transformers 4.44 + sentence-transformers 2.7 可稳定工作

## 七、关键实现（追问级）

### ① Chunk — 为什么 metadata 是 dict 且 chunk_id 自动生成

```python
@dataclass
class Chunk:
    content: str
    metadata: dict = field(default_factory=dict)  # 不写死字段，不同文档类型弹性扩展
    chunk_id: str = field(default_factory=lambda: str(uuid.uuid4())[:8])  # 自动生成
```

**追问应对**：「为什么 chunk_id 用 UUID 而不是自增数字？」— 自增数字在并发写入和多文件合并时会冲突；UUID 全局唯一，ChromaDB 用它做主键也不会碰撞。截取前 8 位是因为 16^8 ≈ 40 亿，项目规模够用且日志可读性好。

### ② RetrievalResult — source 字段追踪检索来源

```python
@dataclass
class RetrievalResult:
    chunk: Chunk
    score: float
    source: str  # "bm25" | "vector" | "rrf" | "cross_encoder"
```

**追问应对**：「为什么需要 source 字段？」— 消融实验靠它区分：source="bm25" 的数据单独评估 vs source="cross_encoder" 的数据，能算出每个模块的贡献。Streamlit 展示时也能对比同一 query 在不同阶段的变化。

### ③ config.py — 参数集中管理

```python
# 切片参数
CHUNK_SIZE = 512
CHUNK_OVERLAP = 128

# 检索参数
BM25_TOP_K = 20
VECTOR_TOP_K = 20
RRF_K = 60
CE_TOP_K = 5
```

**追问应对**：「为什么不写成 YAML 或 .env？」— YAML 需要额外 parser；.env 只能是字符串。Python 文件天然支持类型（int/float/Path），`from config import RRF_K` 一行拿到值，消融实验时跑脚本直接 `config.RRF_K = 30` 覆盖。
