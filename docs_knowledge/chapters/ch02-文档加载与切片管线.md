# 第 2 章：文档加载与切片管线

## 知识点

### 1. 为什么不能把整本书直接塞给 AI

两个硬约束：

- **Embedding 模型是"小胃王"**：all-MiniLM-L6-v2 的有效微调窗口是 256 token，超过则被 Tokenizer 静默截断——向量只代表前半段，后半段语义永久丢失。就算更大模型，长文本 embedding 后语义也被稀释——AI 看前忘后。
- **检索精度要求**：用户搜"Transformer 自注意力"，应该返回那一段，而不是包含这个词的整篇 50 页 PDF。

**核心思路**：把长文档切成最大 256 token 的"标准小纸条（Chunk）"，每张纸条自带章节坐标。后面检索时按纸条匹配，精准到段。

### 2. 度量衡统一：Token 级计数 vs 字符级计数

| 方式 | 英文 "Hello world" | 中文 "你好世界" | 问题 |
|------|-------------------|----------------|------|
| `len()` 字符 | 11 字符 | 4 字符 | 英文字符多但信息少，中文反之 —— 度量不公平 |
| `tiktoken` token | ~3 tokens | ~4 tokens | **统一翻译成模型认的数字**，中英文体积对等 |

用 `tiktoken` (cl100k_base) 做 token 计数，不管中英文，**凑满 256 token 的信息量一致**。这个编码和下游 GPT 系列 embedding 模型用的是同一套，计数精度最高。

### 3. 三个关键参数

| 参数 | 值 | 作用 |
|------|-----|------|
| chunk_size | 256 tokens | 对齐 all-MiniLM-L6-v2 的有效编码窗口 |
| overlap | 38 tokens | ≈15%，行业推荐 10%~20% 区间 |
| length_function | tiktoken (cl100k_base) | 与大模型共用一套度量衡 |

**参数选型的决策链**

```
业务文档类型 ──→ Embedding 模型 ──→ Chunk Size ──→ Overlap
              (选型)           (物理天花板)      (语义连贯性)
```

**第一步：根据文档类型选模型。** 短文本、FAQ → 轻量模型（all-MiniLM，256 窗口）。长篇论文、合同 → 长窗口模型（bge-large-zh 1024、bge-m3 8192）。

**第二步：模型窗口是 Chunk 的硬天花板。** Chunk 不能超过 `max_seq_len`。all-MiniLM 微调窗口就是 256，设 512 的话 Tokenizer 自动尾部截断——向量只代表前半段，后半段不参与编码，搜到了也匹配不上。BERT 的 512 是 2018 年算力妥协，不是正确答案。

**第三步：根据文本连贯性定 Overlap 比例（10%~20%）。** 对话、长叙事取 15%~20%；独立条款取 10%。38/256≈15%，通用文档基线。

### 4. 为什么要 overlap

假设原文："自注意力机制是 Transformer 的核心创新"

如果 Chunk 边界恰好落在 "Transformer" 和 "的核心创新" 之间：
- Chunk A 结尾："自注意力机制是 Transformer"
- Chunk B 开头："的核心创新"

→ 用户搜 "Transformer 的核心创新"，两个 Chunk 各自只有一半，谁都匹配不上。38 token 的 overlap 确保每个句子都可能出现在前后两个 Chunk 中。

**怎么实现**：不是简单地按字符倒退，而是**逐句倒推、按 token 累加**，直到凑满 38 token 为止。这样可以保证下一个 Chunk 始终以完整句子开头。

### 5. Markdown 标题面包屑

- 正则匹配 `#` ~ `######` 六级标题
- **用栈维护层级关系**：遇到更深或同级标题时弹栈再入栈 —— 天然建模"退出旧章节、进入新章节"
- 每个 Chunk 的 `metadata` 里记录完整章节路径，如 `RAG 综述 > 核心优化方向 > 2. 混合检索策略`
- 非 Markdown 文件不启用标题追踪
- 检索命中后可以溯源到原文具体章节 —— 一种零成本的"结构增强检索"

### 6. 编码自动检测 —— 降级链防崩锁

公司文档编码五花八门：新系统用 UTF-8，老系统可能用 GBK/GB2312。直接 `read_text()` 遇错即崩。

**策略**：建立降级尝试队列，按优先级依次试钥匙：

```
UTF-8 → GBK → GB2312 → GB18030 → Latin-1
```

- 任何一把钥匙打开就立刻返回，不浪费性能
- 全部失败用 UTF-8 做最终 fallback（保底撞运气）
- GB18030 放在 GBK 之后，因为它是 GBK 的超集（覆盖藏文、蒙文等），先试 GBK 可以减少一次异常开销

- **token 级 vs 字符级**：和下游 embedding 模型保持相同度量衡，中英文体积对等

## 切片追问：一句话太长，Chunk 装不下怎么处理？

> 注意：这道题问的是"装不下时的处理策略"。如果面试官问的是"256/38 这两个数字怎么定的"，那是在问参数选型逻辑——答案在第 3 节"参数选型的决策链"。两道题分开答，别搞混。

面试时按"三道防线"框架回答——从常态机制到极端兜底，逐层递进。

### 第一道防线：常规切片 — 按句贪心合并 + Overlap 重叠

**场景**：正常文本，有完整的句号、感叹号等标点。

**做法**：按句号切成小句 → 贪心拼到 256 token → 装满后，下一个 Chunk 倒退 38 token 再开始。

**效果**：截断点附近的文字在下一个 Chunk 里重复出现一次，靠重叠修复轻微的跨句上下文断裂。正常文本在这一层就处理完了。

### 第二道防线：父子文档检索 — 小 Chunk 精准检索 + 大 Parent 完整喂 LLM

**场景**：段落特别长、逻辑极复杂、代词特别多（"上述规则第二条""前款所述情形"）。Overlap 覆盖不了这么长的跨度。

**做法**：切片时依然切成 256 token 的小 Chunk（给向量库做检索雷达），但把小 Chunk 归属的完整大段落（Parent）存在数据库里。检索时小 Chunk 命中了不返回，返回的是它映射的完整父文档。

**效果**：大模型拿到的是上下文绝对完整的大段落，指代断裂从根源上消除。

### 第三道防线：强制硬截断 — 无标点的极端文本兜底

**场景**：500 字没有标点的长文、一整串无换行的 JSON/代码。因为没有句号可切，前两道防线失效。

**做法**：按 chunk_size 长度强行"咔嚓"截断，用 `i = max(next_i, i + 1)` 强制推进指针。

**效果**：上下文虽然被物理切断，但系统不会死锁崩溃。

### 第三道防线 + 第二道防线联动：化腐朽为神奇

第三道防线的硬截断单独使用会破坏语义。但和第二道防线联动后，断点被完美修复：

**第一步 — 切片阶段建立映射**：完整文本先作为 Parent Block 存入数据库（`parent_id = "P1"`）。然后触发硬截断，切成子 Chunk 1、子 Chunk 2……每个碎片 Chunk 的 metadata 里记录 `parent_id: "P1"`。

**第二步 — 检索阶段修复**：用户提问，向量检索命中了碎片 Chunk 2（半句话，但包含关键词，相似度极高）。系统不看碎片的文本内容，而是读它的 `parent_id → "P1"` → 去数据库把完整 Parent Block 取出来 → 塞给 LLM。

**最终效果**：碎片 Chunk 只当"雷达"用——在向量库中标定位置。LLM 拿到的始终是那个完整的前因后果。

## 追问：触发硬截断后，父子文档能修复吗？

**"完全可以，而且这正是父子文档架构最强悍的地方——它为底层的硬截断实现了'语义无痕缝合'。**

在索引端（切片时）：面对极端超长文本，哪怕触发字符级硬截断，每个切出的碎片 Chunk 在生成向量的同时，依然会绑定原始完整段落的 `parent_id`。

在消费端（召回时）：硬截断的碎片 Chunk 仅仅作为'定位雷达'去向量库撞线匹配；一旦命中，系统就通过 `parent_id` 提取出截断前的完整父段落。

**最终结果**：大模型接收到的依然是未经破坏的完备上下文。第三道防线保障了代码不死锁、系统不崩溃，第二道防线抹平了截断带来的语义损伤——底层兜底与高层架构之间形成了真正的工程闭环。"

## 面试高频话术

### 话术 1：「你们的切片参数是多少？怎么定的？」

"我们在切片管线的设计上，核心原则是**'以 Embedding 模型的编码窗口为硬天花板，以句子语义完整性为边界'**。

参数上，我们最终选定的是 Chunk Size 为 256 tokens，Overlap 为 38 tokens（约 15%）。

这个选型背后有很清晰的决策链：

1.首先看模型硬约束：我们检索端使用的是 all-MiniLM-L6-v2，它的有效微调窗口就是 256 tokens。超出的部分会被 Tokenizer 静默截断，导致后半段语义丢失。所以 256 是我们绝不能跨过的物理天花板。

2.其次选重叠度：为了防止重要实体或跨句指代被切断，我们取了通用基线 15% 左右的重叠，也就是 38 tokens。

3.最后是度量衡：为了保证中英文切片的信息量对等，我们没有用字符数，而是统一用大模型同款的 tiktoken (cl100k_base) 进行 Token 级的准确计数。

这样切出来的纸条，既契合向量模型的胃口，又能保证检索的精确定位。"

### 话术 2：「Overlap 是怎么实现的？直接截取前后字符吗？」

"不是简单的字符倒退，因为直接按字符倒退很容易产生句中硬截断，导致下一个 Chunk 以半个词或半句话开头。

我们的实现机制是**'先基于标点断句，再贪心合并，最后逐句倒退累加'**：

1.切片时：我们先用正则按中英文标点把文本切成独立句子，然后按 Token 累加装进当前 Chunk，确保每个 Chunk 的边界都在完整的句号或感叹号处。

2.做 Overlap 时：当前 Chunk 装满后，指针不直接从新句子开始，而是从当前 Chunk 的最后一句开始向前倒退，按句子 Token 数逐句累加，直到凑满 38 个 Token 为止。

3.安全兜底：为了防止某句过长导致死循环，我们在代码里加了 `max(next_i, i + 1)` 的指针保底移动机制，确保指针永远向前推进。

这样在源码层面，就卡死了'下一个 Chunk 永远以完整句子开头'的铁律，同时兼顾了语义连贯和代码安全性。"

### 话术 3：「复杂长文档，256/38 效果不好怎么办？」

"针对超长段落的处理，我们在工程上有分层应对机制：

**1. 常规长段落（有标点）**：先按标点断句，贪心合并至 256 token。为了防止切断上下文，我们使用了 38 token 的逐句倒退重叠（Overlap），让前后 Chunk 有 15% 的交集，靠重叠来保护句子间的连贯性。

**2. 复杂长上下文（上下文要求极高）**：如果仅仅依靠重叠依然会导致跨段落指代丢失，我们会采用父子文档（Parent-Document）架构：切片时用 256 的小 Chunk 建立向量索引保证检索精度，召回时则提取对应的完整父段落（如 1500 token）喂给 LLM，从架构层面彻底消除上下文损失。

**3. 极端无标点超长单句（代码保底）**：如果遇到极罕见的几百字不打标点的硬核文本，常规断句会失效。此时代码会触发字符级硬截断保底，并依靠指针强制推进（`i = max(next_i, i + 1)`）防止死循环。虽然这种极端截断会损失部分语义，但它保障了系统整体的鲁棒性与可用性。

如果追问'硬截断破坏了上下文，父子文档能修复吗？'——完全可以。在索引端，每个被硬截断的碎片 Chunk 生成向量时，依然绑定原始完整段落的 parent_id。检索命中后，碎片只当'定位雷达'用，系统通过 parent_id 提取出截断前的完整父段落。第三道防线保障代码不死锁，第二道防线抹平语义损伤——底层兜底与高层架构形成真正的工程闭环。"

### 话术 4：「Markdown 或异构文档做了哪些结构化增强？」

"主要做了两件事：标题面包屑提取和编码降级防护。

标题面包屑：解析 Markdown 时，我们利用**栈（Stack）**天然的后进先出特性来维护章节层级。遍历标题时，遇到更深层级就 push，遇到同级或更浅层级就 pop。这样栈里永远保持着当前位置的完整作用域链。我们将这个路径（比如 RAG综述 > 混合检索 > 2.1 算法）注入到每个 Chunk 的 metadata 中，实现了零成本的结构增强检索。

编码防崩：面对 GBK、GB2312 等老旧格式文档，我们设计了一条尝试队列：UTF-8 → GBK → GB2312 → GB18030 → Latin-1。按优先级试解，解开即返回，全部失败再用 UTF-8 fallback 兜底，避免了任何因编码异常导致的 Pipeline 崩溃。"

## 关键实现

### ① 编码降级链

```python
def _detect_encoding(file_path, fallback="utf-8"):
    for enc in ["utf-8", "gbk", "gb2312", "gb18030", "latin-1"]:
        try:
            file_path.read_text(encoding=enc)  # 试钥匙
            return enc                          # 成功即返回
        except (UnicodeDecodeError, UnicodeError):
            continue                            # 钥匙断了，不崩，换下一把
    return fallback  # 全军覆没 → utf-8 撞运气
```

**追问应对**：「GB18030 和 GBK 有什么区别？」— GB18030 是国家强制标准，是 GBK 的超集，额外覆盖了藏文、蒙古文等少数民族文字和罕见汉字。放在 GBK 之后尝试可以减少一次异常开销（因为绝大多数中文文档 GBK 就够用了）。

### ② 标题面包屑 —— 栈维护层级

```python
def _heading_breadcrumb(pos, headings):
    stack = []                              # 空栈：垂直的细桶，后进先出
    for h_pos, level, title in headings:
        if h_pos > pos:
            break                           # 还没读到的标题，不管
        while stack and stack[-1][0] >= level:
            stack.pop()                     # 同级或上级 → 弹出，给新标题腾位置
        stack.append((level, title))        # 完美父子关系 → 压入
    return [title for _, title in stack]    # 栈里就是完整的面包屑路径
```

**追问应对**：「为什么用栈？」— Markdown 标题天生是嵌套结构。遍历到 `### 2.1` 时，前面的 `## 2` 还在作用域内，但 `### 1.1` 已经出了。栈天然建模了这种"进入更深 push，遇到同级或更浅 pop"的关系。`while stack and stack[-1][0] >= level` 这一行在底层完美建模了"退出旧章节、进入新章节"的逻辑——这里 `>=` 而不是 `>` 保证了同级标题之间不会出现交叉引用。

### ③ Token 级滑窗切片 —— 贪心合并 + 倒退重叠

这是 Pipeline 最核心的算法，分两个阶段：

**阶段 1 — 贪心装句子**（先断句，再按 token 数贪心合并）：

```python
# 先按中英文标点断句，保证所有 Chunk 边界都在完整句号处
sentences = _split_sentences(text)  # ["句子A。", "句子B！", "句子C。"]

while j < len(sent_map) and token_count + sent_map[j]["tokens"] <= chunk_size:
    parts.append(sent_map[j]["text"])      # 塞进箱子
    token_count += sent_map[j]["tokens"]   # 累加计数
    j += 1                                 # 下一句
```

**阶段 2 — 倒退重叠**（不是硬切，而是逐句倒推凑满 38 token）：

```python
# 从当前箱子的最后一句开始，逐句向前倒退累加
overlap_acc = 0
next_i = j                          # 从刚装满的位置开始往回看

while next_i > i:                   # i 是上一轮的起点，不能退过头
    overlap_acc += sent_map[next_i]["tokens"]
    if overlap_acc >= overlap:      # 凑够 38 token，停！
        break
    next_i -= 1                     # 没凑够，再往后退一句

# 倒退成功 → next_i 是下一轮起点
# 如果一句话就超了 38 token → 保底: next_i = i + 1，避免原地踏步
i = max(next_i, i + 1)
```

**追问应对**：「为什么先断句再合并，而不是直接按字符数切？」— 直接按字符切会从句子中间截断，产生"自注意力机制是 Trans"和"former 的核心创新"这种无意义片段。先断句保证每个 Chunk 的边界都在句号/问号/感叹号处，语义完整。

**追问应对**：「单句就超过 256 token 怎么办？」— 按比例硬截断：`cut_chars = int((chunk_size / 该句 token 数) * 该句字符数)`。这种情况极少见（需要单句超过 ~190 个中文字），但必须兜底，否则 while 循环会死锁。

**追问应对**：「overlap 倒退会不会导致死循环？」— 不会，因为有 `i = max(next_i, i + 1)` 兜底。即使 `_split_sentences` 断句异常、一整段被识别为一句话，`i + 1` 也保证起点至少前进一格，不会原地踏步。

**追问应对**：「那截断的后半句重要怎么办」— overlap 要解决的正是这个。下一个 Chunk 倒退 38 token 开始，截断点附近的内容会在下一个 Chunk 里完整出现。
