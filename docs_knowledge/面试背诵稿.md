# MCP-RAG-Hub 面试背诵稿

> 用法：先背每节的“面试版”，再用“关键词”检查自己是否遗漏。遇到追问时，以“展开回答”为准。所有指标仅代表当前知识库、当前切块策略和 18 条 test 集结果，不应表述为普适结论。

## 一、项目总述

### 30 秒面试版

我做的是一个将私有文档检索能力封装为 MCP Server 的 RAG 系统。文档侧支持多格式解析、Token 级切块、Markdown 标题溯源和 Python AST 语义分块；检索侧采用 BM25 与向量双路召回、RRF 融合和 Cross-Encoder 精排。系统用 36 条分层 Golden Test Set 做阶段级评测，RRF 的 Hit@5 为 1.00、Recall@5 为 0.9722，CE 将 Precision@5 从约 0.49 提升到 0.56。工程上我将 MCP、Agent、前端和评测统一到共享管线，并实现懒加载、初始化锁和版本化索引复用。

**关键词：** RAG、双路召回、RRF、精排、评测、MCP。

### 3 分钟展开版

这个项目的目标是将私有文档转化为可被 AI 客户端调用的可评测检索能力。文档进入系统后，会根据类型采用不同切块策略：Markdown 保留标题面包屑，Python 文件按 AST 的类和函数边界切块，其余文档采用 Token 级滑窗切块。每个 Chunk 都保存来源、顺序、Token 数等元数据，供后续检索和溯源使用。

查询阶段，我没有只使用向量检索。BM25 对专有名词、编号和精确关键词更敏感，向量检索更擅长处理同义改写和语义相近表达。两路各召回 Top-20 后，使用 RRF 按排名融合，避免直接比较不同量纲的原始分数。之后使用 Cross-Encoder 对融合候选做联合编码精排，以提高最终结果的相关性。

我还构建了 36 条分层 Golden Test Set，分为 exact_match、semantic、mixed 和 graph 四类，并分离 train/test，避免调参时测试集过拟合。实验中，RRF 的 Hit@5 达到 1.00，说明召回侧基本能覆盖正确文档；Cross-Encoder 将 Precision@5 从 0.4889 提升到 0.5556，但 MRR@5 和 Hit@5 有下降，说明当前精排配置存在“提高结果纯度但可能漏掉部分正确结果”的权衡。

工程上，我使用 LangGraph 将初检、质量判断、查询改写和重检组织为可控状态图；再通过 FastMCP 以 stdio 模式暴露 `search_knowledge` 等工具，使支持 MCP 的客户端可以复用检索能力。当前已实现进程内共享管线、懒加载和初始化锁；本地 stdio 调用已验证，生产化仍需补充鉴权、限流、远程部署、观测和跨进程治理。

## 二、文档处理与切块

### 为什么使用 Token 级切块，而不是固定字符数？

**面试版：**

我采用 Token 级切块而不是固定字符切块，因为 Token 更接近 Embedding 模型和 LLM 的实际输入单位。相同字符数的中英文、代码和标点，实际占用的 Token 数可能差异很大；按字符切块无法稳定控制模型输入长度。项目使用 `tiktoken` 统计 Token，并将 Chunk 上限设置为 256 Token，与 Embedding 模型的有效编码窗口对齐，避免尾部截断造成信息丢失。

**关键词：** 输入单位、语言差异、模型窗口、256 Token、避免截断。

### overlap 有什么作用和代价？

**面试版：**

overlap 用于避免关键信息恰好位于两个 Chunk 边界，导致语义上下文被割裂。当前项目的 overlap 为 38 Token，约为 chunk_size 的 15%。它不是越大越好：过小仍可能丢失上下文，过大则会增加索引规模、重复候选、计算成本和检索噪声。

**关键词：** 边界上下文、15%、索引膨胀、重复噪声。

### 为什么 Markdown 要保留标题面包屑？

**面试版：**

Markdown 的标题本身包含主题语义。普通滑窗切块会让正文脱离原有章节，因此项目解析标题层级，并将例如“RAG 系统 > 检索 > BM25”写入 Chunk 的 breadcrumb 元数据。这样能保留 Chunk 所属主题，提升结果可解释性，也为后续回答展示来源上下文提供基础。

### 为什么 Python 文件使用 AST 切块？

**面试版：**

如果按固定长度从函数中间切开，代码会失去完整语义和局部上下文。项目使用 Python AST，尽量按顶层函数、类和方法边界切块，并记录 `class`、`def` 等结构信息。这样既保证代码片段完整，也更利于按函数或类定位检索结果。AST 解析失败时回退到普通滑窗，确保管线不会因为单个文件失败而中断。

### Chunk 元数据有什么用？

**面试版：**

`source` 用于回答结果溯源，说明内容来自哪个文件；`chunk_index` 用于定位切片在原文中的顺序；两者还用于生成确定性的 `chunk_id`，使同一文件重复处理时 ID 保持稳定，方便缓存复用。`heading_breadcrumb` 用于保留 Markdown 的层级语义。当前项目没有实现父子文档检索，不能把这些元数据描述为父子文档能力。

## 三、双路召回与 RRF

### 为什么不用单一路径检索？

**面试版：**

BM25 和向量检索的优势互补。BM25 基于词项匹配，对函数名、版本号、错误码和专有名词这类精确查询更稳定；向量检索将 query 和文档映射到语义空间，对同义改写和概念性表达更敏感。例如用户问“如何减少大模型幻觉”，而文档写的是“提升生成可信度”，BM25 可能因词面不重合而召回不足，向量检索更可能识别语义关联。真实用户查询类型不可预先保证，因此采用双路召回提高鲁棒性。

### 为什么 BM25 和向量分数不能直接相加？

**面试版：**

两路原始分数不在同一量纲。BM25 分数由语料统计、词频和文档长度等因素决定，没有固定范围；向量路使用余弦相似度，反映语义向量空间中的接近程度。直接加权会让数值尺度较大的一路主导结果，而且归一化方式会随语料和查询变化。RRF 放弃直接比较原始分数，只使用各路排名，因此更稳健。

**易错：** 向量相似度不是“概率”；BM25 分数不是固定 0 到 50。

### RRF 是什么？

**面试版：**

RRF 的公式是 `RRF(d) = Σ 1 / (k + rank_i(d))`。它将每一路的排名转换为倒数权重后相加。一个 Chunk 如果同时在 BM25 和向量检索中排名靠前，会获得两路贡献，因此通常会被优先提升；只在一路出现的结果仍会保留，从而兼顾可靠性和召回覆盖。

### k=60 的作用是什么？

**面试版：**

`k` 是 RRF 的平滑常数，用于控制排名权重的衰减速度。`k` 较小时，前几名的分差更明显，系统更偏向各路头部结果；`k` 较大时，排名衰减更平缓，靠后的候选也能贡献更多。项目先采用常见经验值 60 作为基线，最终应在调参集上通过 MRR、Hit@K、Precision@K 和 Recall@K 等指标验证，而不能说 60 是理论最优。

**易错：** `k` 不是每路召回数量。每路召回多少由 `top_k` 决定；`k` 只控制 RRF 的排名衰减。

## 四、Bi-Encoder 与 Cross-Encoder

### 两者有什么区别？为什么配合使用？

**面试版：**

Bi-Encoder 分别编码 query 和 document，再计算向量相似度。文档向量可以离线批量计算并存入 ChromaDB，查询时只需要编码 query 并做向量近邻搜索，因此速度快，适合全库粗召回；但 query 和文档之间没有 Token 级交互，精确判断能力有限。

Cross-Encoder 将 query 和 document 拼接后联合输入 Transformer，每个 Token 可以与另一侧 Token 做注意力交互，因此能判断更细粒度的相关性；但每个 query-document pair 都需要联合推理，无法像文档向量一样离线缓存，成本随候选数增加。项目采用 Bi-Encoder 负责全库召回，Cross-Encoder 负责融合候选精排，在速度和准确性之间平衡。

**易错：** Cross-Encoder 通常可以 batch 推理多个 pair，但每个 pair 仍需独立联合编码。

### 为什么先 RRF，再用 Cross-Encoder？

**面试版：**

Cross-Encoder 准但慢，如果直接对全库文档逐一计算，延迟不可接受。BM25 和向量检索先各自召回 Top-20，RRF 将两路结果合并为统一候选集，Cross-Encoder 再只对候选做精排。RRF 不只是粗筛，还保证精排阶段能同时看到关键词路和语义路召回的结果。

### 为什么 CE 提升 Precision，但 Hit/MRR 下降？

**面试版：**

这说明 Cross-Encoder 的收益不是所有指标同步提升。项目中 CE 将 Precision@5 从 0.4889 提升到 0.5556，说明 Top-5 的相关结果密度更高；但 Hit@5 从 1.00 降到 0.9444，MRR@5 从 0.8565 降到 0.7546，说明部分相关结果被重排到 Top-5 之外，或者第一个相关结果位置后移。它不是“全面优化”，而是精度和不漏答案之间的权衡。

如果业务最看重不能漏答案，我会优先采用 RRF 结果，因为 RRF 的 Hit@5 为 1.00；如果更强调前几条结果的相关性，则 CE 仍有价值。下一步应该分析失败样本、调整候选数或 Top-K、尝试更适合中文或领域数据的模型，最后才考虑领域微调。

## 五、检索评测

### 四个指标分别是什么？

**面试版：**

Hit@5 衡量前 5 个结果中是否至少包含一个相关文档，关注“能否找到”；Recall@5 衡量所有相关文档中有多少被前 5 个结果召回，关注覆盖率；Precision@5 衡量前 5 个结果中相关文档所占比例，关注结果纯度；MRR@5 计算第一个相关结果排名倒数的平均值，关注第一个正确结果是否靠前。

**速记：** Hit 看有没有，Recall 看找全没，Precision 看干净不，MRR 看排前没。

### 为什么要 train/test 分离？

**面试版：**

36 条 Golden Test Set 被划分为 train 和 test。Chunk 大小、overlap、RRF 参数和 Top-K 等策略只在 train 集上选择，方案冻结后再在 test 集评估。否则反复根据同一批测试问题调参，会让系统迎合这些样本，导致指标虚高、泛化能力下降。这里的 train 集主要是检索策略调参集，不是用于训练 Embedding 或 Cross-Encoder 模型的训练集。

### 为什么分 exact_match、semantic、mixed、graph 四类？

**面试版：**

分层设计让评测能够对齐系统的多路检索能力。exact_match 主要测试关键词、名称和编号；semantic 测试同义表达和概念理解；mixed 同时包含字面与语义线索；graph 测试实体关系和关联检索。随机收集问题无法保证各类查询均衡，简单样本可能把总指标抬高，也难以定位具体短板和指导后续优化。

### 为什么要分别评估 BM25、向量、RRF 和 CE，而不是只看最终结果？

**面试版：**

对同一批 query，评测脚本分别计算 BM25、向量、RRF 和 Cross-Encoder 的四项指标，才能观察每个阶段在当前流水线中的增量表现。只看最终 CE 结果，无法判断 RRF 是否扩展了召回，还是 CE 单独带来了变化。评测能支持当前数据、模型和参数下的阶段归因，但不能证明某个模块在任何数据集上都必然有效。

### RRF 提升 Recall，CE 提升 Precision 但降低 MRR，如何解释？

**面试版：**

RRF 的 Recall@5 上升，说明关键词路与语义路的互补结果进入了 Top-5，召回覆盖扩大。CE 后 Precision@5 上升，说明精排使最终前 5 的相关结果密度更高；但 MRR@5 下降，说明第一个按 gold 标注判定的相关结果被排得更靠后，甚至被挤出 Top-5。不能笼统说 CE “一定过滤噪声”，它也可能误降某些相关候选；应结合失败 query、候选数和分数分布继续分析，并按业务在纯度和不漏答案之间取舍。

### 正式评测与消融实验为什么分别复用和隔离索引？

**面试版：**

正式评测应复用线上 `get_pipeline()`，确保评测环境与当前服务的文档、切片、模型和索引一致，结果才具有代表性，同时避免重复 embedding。消融实验需要改变模块或参数，并可能强制重建或删除 collection，所以使用 `experiments/chroma_db` 隔离，避免污染正式索引和不同实验条件相互干扰。原则上，如果变量只在检索后发生，例如仅改变 RRF 权重或 reranker，底层索引可以复用；如果变量影响切片、embedding 模型或向量空间，必须独立重建。当前实验脚本为保证可重复性采取统一隔离策略，即使部分后处理实验理论上可以复用索引。

### 参数扫描为什么不能只按 MRR 选最优？

**面试版：**

切片参数会改变物理索引，必须重切块和重建向量；RRF_K 与 CE_TOP_K 只影响检索后排序，可复用底层索引。选择参数不能只看 MRR：MRR 体现首个相关结果的位置，Recall/Hit 体现是否漏掉证据，Precision 体现结果噪声，延迟体现实际可用性。当前脚本虽然输出多项指标，但自动 best config 只按 MRR 选取，后续可改为带约束的多目标选择，例如先满足最低 Recall/Hit，再在候选配置中比较 MRR、Precision 和延迟。

对于医疗等高风险、宁可多给候选也不能漏掉关键证据的场景，应优先确保 Recall@K 和 Hit@K，并同时关注 MRR；再通过更谨慎的精排、引用和人工审核控制噪声。不能假设 LLM 能可靠自行过滤无关医疗证据。当前 `CE_THRESHOLD` 是 Agent 是否触发查询改写的阈值，不是 Cross-Encoder 的候选截断阈值。

### Cross-Encoder 是延迟瓶颈，如何优化？

**面试版：**

CE 对每个 query-candidate pair 做联合 Transformer 推理，候选数增加时成本近似线性增加。优先方向是提升前级召回质量并限制送入 CE 的候选数量，例如调小粗召回 Top-K，或在验证集上研究基于 RRF 排名/分数差距的自适应候选截断；这必须同时监控 Recall，避免过早截断漏掉相关证据。其次可采用轻量模型、ONNX Runtime 或量化降低单次推理延迟；有 GPU 和稳定并发时可 batch 多个请求的 pair，但排队会增加单请求时延。当前项目已实现的是两阶段召回加 CE 精排，量化、ONNX、动态截断和批处理均是后续优化。

**易错：** 不能简单让 CE 与最终 LLM 答案生成并行，因为当前生成必须使用 CE 精排后的 Top-3 证据。可以研究推测执行和取消重算，但它会引入实现复杂度和可能浪费计算，不是当前项目已实现能力。

### 为什么既要汇总指标，又要逐 query 深度追踪？

**面试版：**

汇总指标是宏观监控，回答系统整体是否改善、是否回归；深度追踪是微观诊断，保存单条 query 在 BM25、向量、RRF、CE 四阶段的 Top-5、分数、来源、预览和相关性标记，回答具体失败发生在召回、融合还是精排。两者不能互相替代：只有汇总看不到失败原因，只有个例又无法代表整体趋势。当前相关性标记仍是文档级 gold source，而不是 chunk 级证据标注。

若向量阶段命中正确文档、RRF 后却掉出 Top-5，应优先检查融合阶段的候选排名、RRF 参数和两路结果分布。默认两路 RRF 权重相等且均为正值，BM25 不会“负向扣分”；更可能是 BM25 的高排名噪声候选在 RRF 中与向量命中候选竞争，从而改变最终排序。应查看该 query 的两路 Top-K 和 RRF 贡献，而不是仅凭汇总指标断言。

## 六、LangGraph Agent

### 为什么需要 LangGraph？

**面试版：**

简单问题可以直接“查询、检索、返回”，但当 query 有歧义、检索置信度低或需要多次工具调用时，线性流程无法表达查询改写、重新检索、结果评估和失败兜底。LangGraph 把流程拆成节点和条件边，并通过显式 State 传递 query、检索结果和评估信息，从而支持条件路由、可控循环和过程调试。它不会自动让 Agent 更聪明，真正效果仍取决于改写策略、质量判断和停止条件。

### 什么情况触发查询改写？

**面试版：**

查询改写适合处理歧义、指代缺失、检索失败和术语不匹配。应先进行初次检索，只有结果质量较差时才触发，例如最高 CE 分数低于阈值、Top-K 相关性不足，或者 query 缺少上下文。无条件改写会带来语义漂移、额外延迟、成本上升和错误累积；对函数名、错误码、版本号等精确查询，还要尽量保留原始关键词。

### 如何避免无限循环？

**面试版：**

我会设置三层 guardrail：第一，最大改写次数和总延迟预算；第二，比较改写前后的检索质量，连续没有改善就提前停止；第三，改写无效时触发兜底，例如返回原始结果并标注低置信度、要求用户补充信息或扩大召回范围。还可以检测新 query 是否与历史 query 高度相似，避免重复改写。LangGraph 可以通过 State 字段和条件边将这些规则显式化。

**边界：** 若当前代码没有全部实现这些规则，应说“生产化方案”，不要说已经落地。

### 当前 Agent 是多 Agent 吗？

**面试版：**

不是。当前是一个 LangGraph 单 Agent 工作流，`analyze_query`、`retrieve`、`check_results`、`rewrite_query` 和 `generate_answer` 是同一个 Agent 的不同节点，不是多个独立 Agent 协作。RAG 管线负责找证据，Agent 负责决定是否改写再检索，以及如何基于证据生成答案。

### `last_retrieved_chunks` 和 `retrieval_history` 为什么要分开？

**面试版：**

`last_retrieved_chunks` 保存最近一轮的完整检索结果，每次重检索都会覆盖，供 `generate_answer` 使用；`retrieval_history` 使用 `operator.add` 追加每轮的轻量观测，包括 query、Top-K 数、最高 CE 分数和来源文档，用于分析改写前后是否改善。完整正文若每轮都存入历史会使 Agent State 和日志持续膨胀。

`rewritten_queries` 只追加改写后的 query 文本，`search_log` 则保存各节点的可读事件日志。前者用于分析改写策略，后者用于排查流程和条件路由。

### 当前如何判断要不要改写？

**面试版：**

当前实现以最后一轮 Top-1 的 Cross-Encoder 分数作为轻量质量信号。`best_score < CE_THRESHOLD` 且检索次数少于 2 次时，路由到 `rewrite_query`；否则直接生成答案。当前阈值为 3.0，是该模型和当前语料下的经验值，不是通用标准。换模型、领域或业务目标后，应在验证集上重新校准。

**边界：** 当前生成阶段使用最后一轮结果，不会自动保留历史最高分的一轮。可以增加 `best_retrieved_chunks`，在多轮中保留最高分对应的完整结果，作为后续改进。

### 检索阶段与生成阶段分别做什么？

**面试版：**

检索阶段执行 BM25、向量和可选 KG 粗召回，经 RRF 融合、Cross-Encoder 精排后得到候选 Chunk；生成阶段把精排靠前的 3 条 Chunk、来源信息和用户问题一起交给本地 Ollama，由 LLM 基于证据组织自然语言答案。检索保留 Top-5，便于质量判断、调试和 MCP 返回；生成只用 Top-3，以控制上下文长度、推理成本和低排名噪声。Top-3/Top-5 是当前经验性权衡，后续应在验证集比较不同 K 对回答质量、延迟和成本的影响。

### RAG 能彻底消除幻觉吗？Ollama 不可用怎么办？

**面试版：**

不能。提示词要求模型只基于检索到的文档回答、证据不足时如实说明，这能降低脱离知识库编造的概率；但上下文可能不相关或不完整，模型也可能错误归纳多个 Chunk，当前还没有逐句事实校验，因此不能承诺零幻觉。没有检索结果时系统明确返回“未找到相关文档”；Ollama 不可用时降级返回 Top-3 原始证据片段并标明“本地 LLM 未连接”，使检索能力仍可用。

## 七、MCP 与 FastMCP

### 为什么封装为 MCP 工具，而不是直接调用 Python 函数？

**面试版：**

单体原型中直接调用 Python 函数更简单，但调用方会依赖同一语言、运行环境和具体函数签名。FastMCP 将检索能力封装为标准工具，客户端通过工具名称、描述和输入输出 Schema 调用，不需要了解底层是 BM25、向量检索还是 RRF。这样支持 MCP 的客户端可以复用同一套知识库能力，检索实现也可以独立升级。当前项目验证的是本地 stdio 模式；远程部署、鉴权、限流、超时和监控仍需补充。

### MCP 和 FastAPI 有什么区别？

**面试版：**

FastAPI 是 Web 服务框架，解决 HTTP 路由、请求响应、并发和中间件等问题；MCP 是面向 AI 客户端的工具与上下文协议，定义能力发现、工具描述、输入 Schema 和调用结果。MCP 也需要传输层，可以使用 stdio 或基于 HTTP 的传输。两者不是互斥关系：普通业务系统可以通过 FastAPI 调用服务，AI 客户端则可通过 MCP 发现和调用工具。

### 为什么工具名称、描述和 Schema 很重要？

**面试版：**

工具名称、描述和参数 Schema 是 Agent 理解工具能力的核心接口信息。名称表达意图，描述说明使用场景和返回内容，Schema 约束参数类型、必填项和含义。描述模糊或多个工具职责重叠时，模型可能选错工具；Schema 不清晰时，模型可能传错参数，导致调用失败或结果偏离预期。

项目实际提供四个工具：`search_knowledge` 执行完整检索，`list_documents` 列出文档及切片数，`get_chunk` 按 ID 获取完整切片，`get_chunk_count` 返回切片总数。

**易错：** KG 默认关闭，工具描述不应无条件声称每次都是“三路融合”。

### `search_knowledge` 的调用链和参数保护是什么？

**面试版：**

工具先拒绝空 query、超过 500 字符的 query，以及不在 1 到 50 范围内的 `top_k`。随后并行执行 BM25、向量和可选 KG 粗召回，经 RRF 融合后由 Cross-Encoder 精排；最终只返回 JSON 风格的结构化字段，包括排名、正文前 500 字、来源、标题、RRF 分数、CE 分数和 `chunk_id`。`graph_results` 是可选 KG 检索结果，不是 Cross-Encoder；CE 发生在 `FusionPipeline.run(..., ce_top_k=top_k)` 内部。

### 为什么只返回正文前 500 字，还要返回 `chunk_id`？

**面试版：**

首次响应截断正文可以控制 MCP 返回体和下游 LLM 上下文成本；`chunk_id` 是稳定定位符。客户端确认某条结果重要后，可调用 `get_chunk(chunk_id)` 按需取得该切片完整正文和 metadata。这是先定位摘要、再按需展开的工具设计。

### 为什么 `get_chunk` 查内存 `chunks`，而不是查 Chroma？

**面试版：**

Chroma 同时保存向量、Chunk 文本、metadata 和 ID，理论上也能按 ID 返回数据；但 `get_chunk` 不需要语义检索，只需根据已知 ID 精确定位。当前项目让 BM25、`list_documents` 和 `get_chunk` 共享 `PipelineContext.chunks` 这份内存权威源，保证检索到的 ID 与后续展开的是同一批切片，也避免额外数据库查询。`list_documents` 返回每份文档的 Chunk 数，便于确认索引覆盖范围、发现加载或切片异常。

## 八、MCP Server 懒加载与并发初始化

### 为什么使用懒加载？

**面试版：**

MCP Server 是长驻进程，SentenceTransformer、ChromaDB 和 Cross-Encoder 的初始化成本较高。如果在模块 import 阶段加载，会拖慢 Server 启动，stdio 客户端作为子进程拉起 Server 时可能因握手等待过久而超时。因此我采用懒加载：服务启动时只创建 Server，第一次 Tool 调用时再初始化 RAG 管线；后续请求复用已加载的模型、索引和检索器。代价是首个检索请求延迟较高，生产环境可通过预热缓解。

### 后续请求如何复用管线？

**面试版：**

首次调用时，MCP 通过 `_ensure_pipeline()` 获取 `src.pipeline.get_pipeline()` 返回的 `PipelineContext`，其中包含 BM25、向量模型、ChromaDB、可选 Graph 和 Fusion 组件。该上下文保存在进程内并由多个入口复用；后续请求直接使用已有对象，不再重复加载模型或建立索引，因此响应更快。

### 为什么要初始化锁？

**面试版：**

多个请求可能同时发现系统尚未初始化。如果没有保护，它们可能同时加载模型和建索引，浪费内存和计算资源，还可能产生状态竞争。当前 `src.pipeline.get_pipeline()` 已使用互斥锁和双重检查：第一个成功获取锁的请求负责初始化，其他请求等待；初始化完成后，等待者再次检查并直接复用管线。

```python
with init_lock:
    if not initialized:
        initialize_pipeline()
        initialized = True
```

**边界：** 这是进程内锁。多进程部署时每个进程仍有自己的 Python 模型对象；Chroma 持久化 collection 可以按 hash 复用，但不能共享进程内 BM25/模型实例。

### 为什么 MCP 层和 pipeline 层都有 `_ctx`？

**面试版：**

MCP 层的 `_ctx` 只是 Tool 适配层的本地缓存；`src.pipeline` 的 `_ctx` 才是所有入口共享的进程内权威单例。锁放在 `get_pipeline()` 而不是 MCP 层，是因为 Agent、Streamlit 和评测也直接调用它。实现采用双重检查：外层避免正常请求频繁获取锁，内层防止多个并发首请求在等待后重复构建。

## 九、索引生命周期与文档更新

### `corpus_hash` 和 `schema_version` 分别解决什么问题？

**面试版：**

`corpus_hash` 是整套语料的内容指纹，覆盖文档路径、内容、`chunk_size` 和 `chunk_overlap`，用于判断“文档或切片配置变没变”。`INDEX_SCHEMA_VERSION` 标记索引的数据格式和解释规则，用于判断“即使内容不变，ID 规则、metadata 含义或索引配置是否发生不兼容变化”。向量 collection 名包含 embedding 模型、schema version 和 corpus hash，因此内容、模型或格式变化时，新旧索引天然隔离。

### 索引什么时候复用，什么时候重建？

**面试版：**

默认情况下，当前 collection 的 metadata 与 corpus hash、schema version、chunk 数、chunk ID 数和 cosine 配置都匹配时，直接复用 Chroma 索引，不重复计算 embedding。内容或切片配置变化时，系统创建新的版本化 collection；新集合构建成功后才清理旧集合，避免失败导致没有可用索引。`force_rebuild=True` 会先删除当前 collection 再重建，适合实验或明确维护操作，但构建失败时当前索引会不可用。

### 哈希能解决 RAG 知识过时问题吗？

**面试版：**

它解决的是静态文件知识库的变更检测和缓存失效判断，不是实时同步。当前长驻进程的上下文签名只包含文档目录和切片参数，运行中直接修改文件不会自动刷新已存在的上下文；需要显式重置管线，或进一步加入 corpus hash 到签名、文件监听、定时刷新和后台增量索引。面对数据库、网页等高频动态数据源，还需要独立的数据同步与多进程更新协调机制。

## 十、KG 缓存一致性与原子更新

### 为什么 KG 缓存不能只看 `chunk_id`？

**面试版：**

当前 `chunk_id` 由文件名和切片序号生成，用于稳定定位切片，但不能证明内容没有变化。同一文件同一序号的文本被修改后，ID 仍可能相同。因此 KG 三元组缓存还使用 `corpus_hash`，它覆盖文档内容、文档集合和切片参数；内容或切片配置变化时，hash 不匹配，缓存就会全量重建。

### sidecar 文件检查什么？

**面试版：**

`knowledge_triples.jsonl` 保存三元组主数据，`knowledge_triples.jsonl.meta` 是配套 sidecar，保存构建信息。复用时先确认 JSONL 与 sidecar 存在且 sidecar 可解析，再校验 `meta_version`、`chunk_id_rule_version` 和 `corpus_hash`。`chunk_size`、`chunk_overlap` 也记录在 sidecar 中便于诊断，但它们已经进入 corpus hash 计算，因此配置变化会间接导致 hash 不匹配。

### 为什么先写临时文件，再替换 JSONL，最后写 sidecar？

**面试版：**

三元组抽取可能中途失败，若直接写正式 JSONL，会破坏原有完整缓存并留下半成品。项目先写临时文件，成功后使用 `os.replace()` 原子替换正式 JSONL，因此替换前旧文件可用、替换后新文件整体可见。sidecar 最后写入，表示正式 JSONL 已按当前语料和规则完整构建；这样不会出现 sidecar 已声明缓存有效、主文件却尚未完成或替换失败的状态不一致。

## 十二、真实能力边界

### 已实现

- 多格式文档解析、Token 切块、Markdown breadcrumb、Python AST 分块。
- BM25 + 向量双路召回、RRF 融合、Cross-Encoder 精排。
- 36 条分层 Golden Test Set 与检索指标评测。
- LangGraph 查询改写与条件路由框架。
- FastMCP 工具封装与本地 stdio 调用。
- 进程内共享管线、懒加载、初始化锁，以及版本化 Chroma collection 复用。

### 不应夸大为已实现

- 远程 MCP 服务部署、鉴权、限流、观测与高并发治理。
- 初始化锁：`src.pipeline.get_pipeline()` 已实现进程内初始化锁；跨进程治理仍未实现。
- `ai-lowcode-assistant` 与本项目的真实 MCP 联调：未实际打通则只能说“可接入”。
- 知识图谱默认关闭：实验模块，不是当前主链路收益来源。
- 文件实时监听、增量索引、动态数据源同步和跨进程索引更新协调。
- Agent 当前以最后一轮 `last_retrieved_chunks` 生成答案，尚未保留多轮检索中的历史最佳完整结果。
- 检索评测目前按来源文档做相关性标注，尚未标注 gold chunk ID 或答案证据文本范围，因此无法严格评估 chunk 级证据命中质量。
- 参数扫描虽然输出多项指标，但自动 best config 目前只按 MRR 选择，尚未实现 Recall/Hit、Precision 与延迟约束下的多目标选择。
- 医疗等高风险场景所需的引用校验、人工审核、领域规则与严格拒答策略未实现，不能把当前项目直接表述为可用于高风险决策。
