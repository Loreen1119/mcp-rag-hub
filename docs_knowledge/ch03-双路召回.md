# 第 3 章：BM25 + ChromaDB 双路召回

## 知识点

### 1. BM25 关键词检索

**原理**：基于词频统计的稀疏检索算法，核心公式包含三个因子：

- **TF 饱和曲线**：`TF / (k1 * (1 - b + b * doc_len / avg_len) + TF)`
  - TF 不会无限增长，对单一词汇重复出现有"饱和"效应
  - `k1` 控制 TF 饱和度（默认 1.5），`b` 控制文档长度归一化强度
- **IDF 逆文档频率**：`log((N - df + 0.5) / (df + 0.5))`
  - 稀有词 IDF 高，常见词（"的"、"是"）IDF 低
- **文档长度归一化**：长文档不会因为词多就霸占高分

**BM25 vs TF-IDF**：
- TF-IDF 的 TF 是原始词频，长文档中高频词会碾压
- BM25 的 TF 有饱和曲线 + 长度归一化，对文档长度更鲁棒

**为什么对专有名词强**：
- "Q3营收"、"Transformer"、"API-Key-42" 这类词在语料中出现次数少（IDF 极高）
- 一旦命中，得分非常高
- 向量检索同义词时会"分散"注意力，BM25 不会

### 2. ChromaDB 向量检索

**Embedding 模型：all-MiniLM-L6-v2**
- 384 维向量
- 基于 MiniLM 架构，参数量小（~22M）
- 本地 CPU 毫秒级推理
- 最大输入 256 token（由 max_seq_length 控制）

**为什么手动 embedding 而不是 ChromaDB 内置**：
- 面试能讲清：文本 → tokenize → model forward → pooling → 384 维向量
- 可以用 `query_embeddings` 查询，确保全程可见 embedding 过程
- 后续换模型（BGE-M3、text2vec-large-chinese）只需改 model_name

**ChromaDB 持久化**：
- `PersistentClient` 将向量索引持久化到磁盘
- HNSW（Hierarchical Navigable Small World）图索引，近似最近邻搜索
- 余弦距离：`distance = 1 - cosine_similarity`，越小越相似

### 3. 两路互补的本质

| 场景 | BM25 | 向量 |
|------|------|------|
| "Q3营收" | 精确命中，高分 | 语义扩散，相关但不精确 |
| "第三季度财务表现" | 无法匹配（字面不同） | 语义匹配，能检索到"Q3营收"文档 |
| 代码/编号 "ERR-429" | 精确匹配 | 困难（训练数据无此 pattern） |
| 同义词 "医疗" vs "卫生" | 无匹配 | 语义相似度高 |

### 4. 为什么两路都返回原始分数而不做归一化

- BM25 得分量级：0~几十（依赖 IDF 和 TF）
- 向量余弦相似度：0~1
- 量纲差异留给 RRF 融合处理，RRF 只看排名不看绝对分数
- 各检索器保持独立，方便单独替换或做消融实验

### 面试速记

- **BM25 原理**：TF 饱和 + IDF + 长度归一化，三因子共同决定分数
- **BM25 vs TF-IDF**：BM25 有 TF 饱和曲线和长度归一化，更鲁棒
- **为什么两路融合**：BM25 偏字面匹配，向量偏语义相似，天然互补
- **384 维是什么概念**：MiniLM 模型输出，在精度和速度之间取平衡点
- **手动 embedding 的好处**：可控、可解释、面试能讲清流程

## 关键实现

### ① BM25 索引映射 — _bm25_map 处理空分词

```python
for idx, chunk in enumerate(chunks):
    tokens = list(jieba.cut(chunk.content))
    tokens = [t.strip() for t in tokens if t.strip()]
    if tokens:                              # 分词为空则跳过
        self._tokenized_corpus.append(tokens)
        self._bm25_map.append(idx)          # local_idx → chunk_idx 映射
```

**追问应对**：「为什么不用 `enumerate` 的 index 直接当 BM25 索引？」— 有些 Chunk 分词后可能全为标点符号（空 tokens），它们不进入 BM25 索引。如果直接用 enumerate index，`_bm25_index.get_scores()` 返回的 local index 会对应到错误的 Chunk。`_bm25_map` 确保检索结果能准确映射回原始的 chunks 列表。

### ② 手动 Embedding — 不用 ChromaDB 内置函数

```python
# 手动 encode → 显式传入 embeddings 参数
embeddings = self.model.encode(texts, batch_size=32)
self.collection.add(
    ids=ids,
    documents=texts,
    embeddings=embeddings.tolist(),  # 自己算好的向量，不是让 ChromaDB 算
    metadatas=metadatas,
)
```

**追问应对**：「不用 ChromaDB 内置的 embedding_function 有什么好处？」— ① 自己控制 batch_size 和进度条，大文档集加索引时能监控进度；② 后续换模型只需改 `SentenceTransformer(model_name)` 一行，不依赖 ChromaDB 的 embedding 注册机制；③ 面试时能讲清楚向量是怎样从文本一步步行成的，而不是黑盒。

### ③ 余弦距离转相似度 + query_embeddings 查询

```python
query_embedding = self.model.encode(query)
results = self.collection.query(
    query_embeddings=[query_embedding.tolist()],  # 不用 query_texts
    n_results=top_k,
    include=["documents", "metadatas", "distances"],
)
similarity = 1.0 - distance  # ChromaDB cosine distance → similarity
```

**追问应对**：「为什么用 `query_embeddings` 不用 `query_texts`？」— `query_texts` 会让 ChromaDB 内部调用 embedding 函数生成向量，我们又回到了黑盒。用 `query_embeddings` 意味着 query 的向量也是我们自己 encode 的，embedding 过程全透明。ChromaDB 只做 HNSW 近似最近邻搜索这一件事。
