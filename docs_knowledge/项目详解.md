# MCP-RAG-Hub —— 从零搭建一个可演示的智能知识检索系统

## 这是什么？

一个**从底层原理出发、完整实现的知识检索增强生成（RAG）系统**。

简单来说，你给它一堆文档（PDF、Markdown、TXT），它把这些文档「消化」成一个知识库。之后你向它提任何问题，它不会凭空编造答案，而是先去知识库里找到最相关的段落，然后基于这些真实段落来回答你。整个过程是透明的——你能看到它在知识库里找到了什么、是怎么找到的、以及为什么认为这些内容最相关。

这篇文章面向完全不了解算法的读者，用循序渐进的方式讲清楚：这个项目做了什么、怎么做、以及为什么这样做。

---

## 一、它解决了什么问题？

大语言模型（比如 ChatGPT、通义千问这类 AI）有一个众所周知的毛病：**它们会"编造"答案**。当你问一个它没学过的问题，它不会老实说"我不知道"，而是会一本正经地胡说八道。这在技术领域被称为「幻觉」。

更麻烦的是，这些模型的「知识」停留在它们的训练日期。比如一个 2024 年训练的模型，你问它 2025 年发生的事情，它要么不知道，要么靠猜。

**RAG 的解决思路很直观**：不给模型凭空回答的机会。每次用户提问时，先去一个外部知识库里搜出最相关的几段文字，把这些文字连同问题一起塞给模型，然后说：「请只根据我给你的这些资料回答，不要自己编。」

这个项目就是一个**完整的 RAG 系统实现**。它不是调一个现成的黑盒 API，而是把人从文档处理、内容切割、关键词搜索、语义搜索、结果融合、精排、到最终呈现的每一个环节都拆开、讲清楚、并且能跑。

## 二、用户看到的是什么？

项目提供了三种交互方式，面向不同的使用场景：

### 方式一：网页交互界面

打开浏览器，你会看到一个由四个标签页组成的分析面板：

**标签页 1：BM25 关键词检索结果**

BM25 是一种经典的搜索引擎算法，它的工作方式很像 Google 搜索——根据你输入的关键词，去文档里找包含这些词的段落，并按相关度排序。这个标签页展示的就是纯关键词匹配的结果，你会看到每条结果旁边标注了得分和来源文档。

**标签页 2：向量语义检索结果**

这是更「聪明」的一种搜索方式。它不是机械地匹配关键词，而是理解你问题的大致意思，然后去找意思相近的段落。比如你搜「如何提升系统性能」，它也能找到「怎样优化运行速度」的段落——因为这两句话在语义上是接近的，尽管用词完全不同。这个标签页展示的就是语义理解后的检索结果。

**标签页 3：混合融合结果**

这个标签页把前面两种方法的结果「融合」在一起，展示一个综合排名。融合的逻辑是：不直接比较两种方法不一致的分数（就像你不能拿语文成绩和数学成绩直接比大小），而是比较排名位置——两种方法都排得高的段落，在融合结果里自然也排得高。

**标签页 4：精准重排序结果**

这是最精细的一步。混合融合的结果经过一个更强大的模型做「精读」——把问题和每个候选段落一起读，逐字逐句地判断是否真的相关。结果是质量最高、最精准的 Top 5 排序。同时，页面右侧会展示每个段落所属的原始文档段落，以及你当前问题的完整上下文。

### 方式二：MCP 智能工具

项目封装了一个标准的 MCP 服务，可以像插件一样接到其他 AI 助手上。它对外暴露四个工具接口：

- **搜索知识**：传入问题，返回最相关的文档段落
- **列出文档**：查看知识库里有哪些文档
- **获取指定段落**：按编号取出某一段的具体内容
- **统计总段落数**：查看知识库的规模

这意味着这个项目本身也可以作为其他系统的「知识底座」。

### 方式三：智能代理自主问答

项目内置了一个能「自我反思」的智能代理。它的思考流程是这样的：

1. 拿到用户问题，先分析这个问题的类型和重点
2. 去知识库里检索相关内容
3. 检查检索结果的质量——如果最匹配的段落得分很低，说明可能没找到好东西
4. 如果质量不达标，就主动**改写问题**（换个角度、换种说法），再搜一次
5. 反复尝试最多 2 次，直到找到满意的结果
6. 最终基于找到的资料生成答案

整个过程是透明的——你能看到代理每一步在想什么、为什么改写问题、改成了什么样。

## 三、文档是怎么"消化"成知识库的？

这是系统离线完成的工作，不需要用户参与。整个「消化」过程分为几个步骤：

### 第 1 步：文档加载

系统自动识别文档类型并提取文字：

- **PDF 文件**：使用专门的 PDF 解析工具提取文字内容，能处理中文文档
- **Markdown 文件**：解析 Markdown 格式，同时记录各级标题（一级标题、二级标题等）
- **纯文本文件**：自动检测中文编码——无论是 UTF-8 还是 GBK、GB2312，都能正确读取

### 第 2 步：智能切块

把一整篇长文档直接丢进检索系统是不可行的——用户问的问题通常只和其中几段话相关。所以需要把文档切成一个个小「块」。

这个项目的切块方式有几个讲究：

- **按 token 切，不按字数切**。AI 模型不是按汉字数量计数的，而是按 token（一种模型内部的计量单位）。用 token 计数能保证每个块大小精确受控，不会因为中英文混排导致大小不一。
- **滑动窗口重叠**。相邻两个块之间保留 128 个 token 的重叠内容。这是为了防止某个关键句子刚好被切成两半——重叠区保证了每个句子至少完整地出现在至少一个块里。
- **句子边界感知**。切分点不会粗暴地落在句子中间，而是尽量落在句号、换行等自然断点处。

### 第 3 步：标题面包屑

对于 Markdown 文档，系统会记录每个块在原文中处于哪个章节。比如一个块会被标记为「RAG 概述 → 核心优化 → 混合检索」，就像网页导航栏的面包屑一样。这在展示检索结果时很有用——用户可以知道这段内容出自文档的哪个部分。

### 第 4 步：建立双重索引

切好的所有文本块，系统同时建立两套索引：

- **关键词索引**：类似传统搜索引擎的倒排索引，记录每个词在哪些块里出现。使用结巴分词处理中文，能正确切分出「人工智能」「机器学习」这样的中文词组。
- **语义向量索引**：把每个文本块转换成一个 384 维的数学向量（可以理解为一段文字的「语义坐标」）。意思相近的段落，它们的向量在空间中就靠得近。这个转换使用了一个预训练的句子嵌入模型。

两套索引互补：关键词索引擅长精确匹配（搜「销售额」就找出现「销售额」的段落），语义索引擅长模糊理解（搜「赚钱能力」也能找到关于「营收」的段落）。

## 四、用户提问之后，发生了什么？

这是理解整个项目的关键。我们追踪一次完整的检索请求链路。

### 第 1 步：关键词检索

系统把你的问题用结巴分词切成词组，然后用 BM25 算法去关键词索引里查找。BM25 的核心思想是：

- 一个词在少数文档中频繁出现 → 这个词很能代表这些文档（给高分）
- 一个词在几乎所有文档中都出现 → 这个词没什么区分度（给低分）
- 文档越长，相同词频的重要性越低（防止长文档天然占优）

### 第 2 步：语义向量检索

系统把你的问题也转换成那个 384 维的数学向量，然后去向量索引里找和它夹角最小的几个向量。夹角越小，说明语义越相近。这个过程很快——因为向量索引底层使用了高效的近似搜索算法，不需要和每一个存储的向量逐一比较。

### 第 3 步：混合融合

现在手里有两份排名——关键词检索的前 20 名，和语义检索的前 20 名。但问题是两个排名用的评分标准完全不同（关键词的分数是 0 到 50 左右，语义的分数是 0 到 1 之间），不能直接比。

解决方案叫做 **RRF（倒数排名融合）**：不看原始分数，只看排名位置。公式很简单——对于每个文档，计算它在各个排名中的倒数位置之和。排第 1 就 +1，排第 5 就 +0.2，没进前 20 就 +0。这样两个排名就能公平地合在一起了。

这个公式里只有一个可调参数 K（默认是 60），它的作用是平滑——防止第 1 名和第 2 名之间的差距过大。

### 第 4 步：精准重排序

混合融合给出前 20 名后，一个更强大的模型登场了。它不是像步骤 2 那样分别理解问题和文档再比较——而是把问题和候选文档**放在一起读**，像一个严谨的阅卷老师，逐字逐句地判断「这篇文章到底有没有在回答这个问题？」

这个过程比语义检索慢（大约需要 200 毫秒），但判断准确得多。最终只保留最相关的 Top 5 呈现给用户。

### 第 5 步：按需生成答案

在智能代理模式下，最后一步是由大模型根据检索到的资料生成自然语言回答——带上引用来源，说明每句话出自哪个文档。如果检索结果质量不行，代理会主动改写问题重新搜索。

## 五、系统是怎么评测和验证自己的？

一个检索系统好不好的标准是什么？这个项目建立了一套完整的评测体系：

### 检索质量评测

预先设计 15 道「黄金测试题」，每道题都人工标注了正确答案来自哪个文档的哪个段落。测试覆盖三种类型：

- **精确匹配型**：问题中的关键词和文档中的词基本一致（比如「什么是 RAG？」）
- **语义理解型**：问题和答案用词不同但意思相近（比如问「怎样让搜索更快？」答案在「性能优化」章节）
- **混合型**：既有精确词又有模糊语义

然后让系统按不同配置去跑这 15 道题，看它有没有把正确答案排在第一位。评测指标包括命中率、精确率、召回率等。

### 各环节消融实验

「消融」的意思是关掉某个环节，看效果下降多少，从而验证这个环节到底有没有用。比如：

- 只开关键词检索 → 准确率 90%
- 只开语义检索 → 准确率 97%
- 两种都用 + 融合 → 准确率 100%

这就用数据证明了：每种方法都有各自擅长的情况，组合在一起才能做到完美。

### 参数敏感度分析

系统里有很多可调参数（块大小、重叠量、融合公式的 K 值、精排保留数等），每个参数取不同值时，评测系统会自动跑一遍全部测试题，生成一份对比报告，帮助确定最优配置。

### AI 裁判评测

除了用标准答案验证检索是否准确，项目还引入了 AI 评分机制，从三个维度评价最终生成的回答质量：

- **忠实度**：回答是否严格基于检索到的资料？（有没有信口开河？）
- **相关性**：回答是否切题？（有没有答非所问？）
- **上下文召回**：回答中用到的信息，是否都有对应的检索来源？

## 六、有哪些特别的设计？

### 1. 全手工实现，不用黑盒

市面上有很多现成的 RAG 框架（比如 LangChain 的高级检索器、LlamaIndex 等），调几个函数就能搭一个能跑的检索系统。但这个项目选择把每个环节都亲手写：

- 向量的计算和存储是自己调用模型完成的，没有用封装好的快捷函数
- 混合融合的算法是自己用几行公式实现的，没有调现成的融合器
- 评测指标是自己定义的，没有用框架内置的评判函数

这样做不是为了重复造轮子，而是为了**把每个环节的内部机制完全暴露出来**——就像学车时开手动挡，虽然操作复杂了，但对车的运行原理理解得更透彻。

### 2. 两道检索互补，而非冗余

关键词检索和语义检索不是简单的「多搜了一遍」，而是**互补关系**：

- 当你搜一个非常具体的专有名词时，关键词检索最准——这个词可能在整篇文档里只出现了一次，BM25 能精准命中
- 当你搜一个概念性、概括性的问题时，语义检索更好——它不管具体用了什么词，只关心意思对不对

最终的融合结果比任意单一方法都好——这验证了「1+1>2」。

### 3. 分阶段检索的经济性

检索是分两步的，不是一开始就用最耗时的模型：

- 第一步用轻量级模型（Bi-Encoder）快速扫一遍所有文档，筛出前 20 个候选
- 第二步用重量级模型（Cross-Encoder）只对这 20 个精读排序

速度差异是数量级的：轻量模型扫几千个文档只要十几毫秒，重量模型精排 20 个文档要两百毫秒。如果一开始就上重量模型扫全部文档，用户要等好几秒才能看到结果。

### 4. 代理的自我纠错

智能代理最重要的设计是：**它知道自己什么时候没搜好**。

很多 RAG 系统直接拿第一次检索的结果就去生成答案了，即使搜出来的东西和问题毫无关系。这个项目的代理在检索之后多了一个「自检」环节——如果排名第一的结果相关性得分太低，它不硬着头皮编答案，而是改写问题重新搜。

这有点像人类查资料的方式：搜一次不理想，换个关键词再搜，直到找到真正有用的东西。

### 5. 可复现的实验体系

所有的评测数据、消融结果、参数对比都保存为结构化的 JSON 文件，并且自动生成可读的实验报告。任何人都可以复现结果——跑一遍评测脚本，对照报告，验证每个结论。

## 七、总结

这个项目的核心价值一句话概括：

> **从最底层的文档切分、到中间的混合检索与精排、到最上层的代理问答和 MCP 工具封装，完整实现了一个生产级 RAG 系统的全部环节。每个环节都是手写而不是黑盒调用，每个设计决策都有评测数据支撑，每个结果都是可复现的。**

它不是为了「做一个能用的搜索工具」——市面上有很多更简单的方式做到这一点。真正的价值在于：

- 把 RAG 这条技术链路的每个节点都拆开来看了
- 理解了为什么关键词搜索和语义搜索要一起用
- 用数据证明了融合和重排序各自带来了多少提升
- 设计了一个能自我纠错的智能代理
- 封装了标准的工具接口供外部调用
- 建立了一套完整的评测体系来验证每个改动

这是一套**既能够演示、又能够教学、还能够作为其他项目知识底座**的完整系统。
