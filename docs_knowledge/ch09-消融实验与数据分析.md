# 第 9 章：消融实验与数据分析

## 知识点

### 1. 消融实验的两层含义

**狭义消融**（Ablation）：依次移除一个模块，看性能下降多少 → 证明每个模块都有贡献。

**广义实验**：包含模块隔离对比、参数敏感性扫描、分类别分析、延迟剖析、单 Query 链路追踪共五个维度。

实验套件的核心价值：**把架构决策从"我觉得"变成"数据证明"**。

### 2. 五个实验维度

| 实验 | 回答的问题 | 面试价值 |
|------|-----------|----------|
| 模块隔离消融 | 每个模块独立贡献多大？ | 证明混合检索 + CE 有价值 |
| 分类别分析 | 哪个模块对哪类 query 最有帮助？ | 证明 BM25/Vector 互补 |
| 参数敏感性 | 参数调不调有区别吗？ | 证明系统鲁棒性好 |
| 延迟剖析 | 时间花在哪？瓶颈是什么？ | 证明需要 tradeoff 思维 |
| Query 深度追踪 | 单个 query 在链路中怎么被处理？ | 讲清一次检索的全过程 |

### 3. 核心发现

#### 发现 1：BM25 与 Vector 各有所长，互补证据确凿

| 类别 | BM25 MRR | Vector MRR | 结论 |
|------|----------|------------|------|
| exact_match | 1.0000 | 1.0000 | BM25 对专有名词精准 |
| semantic | 0.8000 | 1.0000 | Vector 语义理解碾压 |
| mixed | 0.9000 | 0.9000 | 复杂查询两者都不足，需要 CE |

**面试表述**：「我跑了分类别消融实验，数据清楚地显示——BM25 对语义查询的 MRR 只有 0.8，Vector 能做到 1.0；反过来 Vector 在精确匹配上的 Precision@5 略低于 BM25。这是混合召回最有说服力的证据：不是感觉上需要两者，而是数据上两者确实互补。」

#### 发现 2：Cross-Encoder 是最有价值的模块（也是最贵的）

```
bm25_only    MRR=0.9000  [基线]
vector_only  MRR=0.9667  [+0.0667]
rrf_fusion   MRR=0.9333  [-0.0334 ← RRF 反而退化！]
full_pipeline MRR=1.0000  [+0.0667 ← CE 扳回并超出]
```

**关键观察**：RRF 在小语料下比单独 Vector 还差（MRR 0.9667 → 0.9333），因为 RRF 只看排名不看原始分数质量。BM25 的差结果如果排在 Vector 的好结果前面，RRF 会降低整体质量。**Cross-Encoder 是 RRf 的"纠错器"**——它不看排名，用自己的全注意力打分重新排序。

**访谈一手证据**：S03 查询"怎么评价一个检索系统好不好"：
- BM25: MRR=0.0000（完全找不到，因为文章用的是"评测"不是"评价"）
- Vector: MRR=1.0000（语义理解找到了）
- RRF: MRR=0.5000（BM25 的噪音拖累了排名）
- CE: MRR=1.0000（修复了 RRF 的退化）

#### 发现 3：Cross-Encoder 占总耗时的 92%

```
BM25 Search      0.33 ms   ( 0.1%)
Vector Search   17.56 ms   ( 7.6%)
RRF Fusion       0.05 ms   ( 0.0%)
CE Rerank      214.01 ms   (92.3%)
------------------------
Total          231.95 ms
```

**面试表述**：「管道总延迟约 232ms，其中 CE 占了 92%。这解释了为什么系统设计是两阶段的——Bi-Encoder 粗筛 20 个候选，CE 只精排这 20 个，而不是对所有文档跑 CE。如果全量跑 CE，延迟会从 232ms 膨胀到数秒。这是一个典型的 **recall-vs-latency tradeoff**：Bi-Encoder 保证召回，CE 保证精度，管道串联平衡两者。」

#### 发现 4：小语料下的参数不敏感（这是好事）

RRF_K 在 30/60/120 之间、CE_TOP_K 在 3/5/10 之间，MRR 全部为 1.0000。

**面试表述**：「参数扫描全部满分，不是因为系统无敌，而是因为测试语料只有 3 个 Chunk——天花板效应。但这个结果告诉我们一个重要信息：在这些参数的合理范围内，系统行为是稳定的。你不需要精确调参才能让系统工作，这对生产环境很重要——降低运维成本。」

### 4. 小语料的局限性 & 诚实表述

当前测试语料 = 2 个文档、3 个 Chunk，实际生产可能是十万级。

**实验中应该诚实说明的有**：

- Parameter sweep 全部满分是因为天花板效应，不是系统完美
- RRF 在小语料下可能负优化——这个是真实发现，大语料下 RRF 的价值会更明显
- 延迟数据中的向量搜索（17.56ms）在 10 万级语料下会显著增加

**面试表述模板**：「这些数字是 2 文档 3 Chunk 下的基线，绝对值不具有生产参考意义。我跑这套实验的目的不是证明数字好看，而是**验证模块间的相对关系**——BM25 比 Vector 更适合专有名词、CE 能修正 RRF 的退化、延迟瓶颈在 CE 而非向量检索——这些**相对结论**在小语料和大语料下是一样的。」

### 面试速记

- **五维度实验**：模块消融 / 分类别 / 参数扫描 / 延迟 / 深度追踪
- **S03 是最强证据**：BM25=0 → Vector=1.0 → RRF=0.5(退化!) → CE=1.0(修复)
- **CE 占 92% 延迟**：证明两阶段设计（粗筛+精排）的正确性
- **BM25 vs Vector 互补数据**：semantic 类别 BM25=0.8 vs Vector=1.0
- **诚实面对天花板**：小语料数据验证相对关系，不夸大绝对值
- **RRF 可能退化**：在噪音多于信号时，排名融合不如单独用最好的那路

## 关键实现

### ① 模块隔离 vs 累积增量

```python
configs = {
    "bm25_only": lambda q: bm25.search(q),         # 单独 BM25
    "vector_only": lambda q: vector.search(q),      # 单独 Vector
    "concat_naive": lambda q: dedup_concat(...),    # 拼接（无 RRF）
    "rrf_fusion": lambda q: rrf(...),               # RRF 融合
    "full_pipeline": lambda q: ce_pipeline.run(...)  # RRF+CE
}
```

**追问应对**：「为什么测 concat_naive（直接拼接去重）？」— 因为要证明 RRF 本身的价值。如果 RRF 和直接拼接效果一样，那 RRF 就是多余的复杂度。实测中 RRF=0.933 和 Concat=0.933 持平——**这恰恰说明在小语料下 RRF 没有提供额外增益，但也没造成伤害**。大语料下 RRF 的排名归一化优势会更明显。

### ② Naive Concat 的分数归一化

```python
def _normalize(rl):
    scores = [r.score for r in rl]
    smin, smax = min(scores), max(scores)
    for r in rl:
        r.score = (r.score - smin) / (smax - smin)  # min-max to [0,1]
    return rl
```

**追问应对**：「BM25 和向量分数怎么比？」— BM25 原始分数可能 >100，向量 cosine similarity 在 0~1 之间。不归一化的话 BM25 会碾压向量的排名。这里用 min-max 归一化到 [0,1] 区间，然后合并排序。但这只是基准线对比，生产环境用 RRF 就绕过了归一化问题。

### ③ 延迟剖析的度量方法

```python
t0 = time.perf_counter()
results = retriever.search(query)
elapsed_ms = (time.perf_counter() - t0) * 1000
```

用 `perf_counter()` 而非 `time.time()`——前者是墙上时钟的高精度版本，不受系统时间调整影响，适合做微基准。
