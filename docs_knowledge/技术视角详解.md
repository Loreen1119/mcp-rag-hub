# MCP-RAG-Hub —— 技术视角全览

## 项目定位

一个**从底层原理出发、全手工实现的 RAG 知识检索系统**，覆盖文档解析、Token 级滑动窗口切块、BM25+向量双路检索、RRF 融合、Cross-Encoder 重排序、LangGraph 代理编排、FastMCP 工具封装、以及完整评测体系的端到端管线。知识图谱作为可选实验功能（`ENABLE_KG` 开关）默认关闭。所有环节不依赖框架高级封装，每个步骤的实现均可见、可调试、可复现。

系统围绕「教学可演示 + 实验可验证 + 组件可复用」三条设计主线构建，支持通过 Streamlit 网页、MCP 协议、和 LangGraph 代理三种方式交互。

---

## 一、解决的工程问题

RAG 系统的核心挑战不在于「能跑」，而在于**每个环节的可靠性和可解释性**：

- **文档切块的粒度控制**：切太细则语义不完整，切太粗则检索精度下降。需要 token 级别的精确控制，而非简单的字符计数。
- **单一检索方式的盲区**：BM25 依赖词频匹配，对同义词、改写、跨语言场景无效。向量检索捕捉语义但可能丢失专有名词精确匹配。单用一种必然有盲区。
- **多路检索结果的融合**：BM25 和向量检索的评分分布（量纲和尺度）完全不同，不能直接线性加权。需要一种与评分尺度无关的融合策略。
- **检索质量的自我感知**：一个简单的 RAG 管线不管检出质量好坏都直接生成回答。需要一个能感知检索质量、在质量不足时主动调整策略的代理机制。
- **效果验证的闭环**：改了一个参数或换了一个模型后，如何量化地知道效果是变好还是变差？需要一套系统的评测和消融实验框架。

## 二、系统架构

整体分为**离线索引管线**和**在线检索服务**两大部分，中间通过 ChromaDB 持久化向量存储和内存级 BM25 索引连接。

### 离线管线（文档 → 可检索索引）

```
PDF / Markdown / TXT 文档
        │
        ▼
  文档加载器（pdfplumber + 编码自检测）
        │
        ▼
  Token 级滑动窗口切块（tiktoken cl100k_base）
  + Markdown 标题面包屑提取（栈式层级解析）
        │
        ▼
  Chunk 数据类（text + metadata + heading_breadcrumb）
        │
        ├──────────────────────────┐
        ▼                          ▼
  BM25 索引构建              向量嵌入计算
  (rank_bm25 + jieba)       (all-MiniLM-L6-v2, 384-dim)
        │                          │
        │                          ▼
        │                   ChromaDB 持久化
        │                   (HNSW 索引, cosine 距离)
        │
        └──────────┬───────────────┘
                   ▼
              检索准备就绪
```

### 在线检索（问题 → 排序结果）

```
用户输入问题
        │
        ├──────────────────────────┐
        ▼                          ▼
  BM25 关键词检索            向量语义检索
  (jieba 分词 + BM25)       (query embedding + ChromaDB query)
        │                          │
        │  各自取 Top-20            │
        │                          │
        └──────────┬───────────────┘
                   ▼
           RRF 倒数排名融合
           (rank-based, K=60)
                   │
                   ▼
    Cross-Encoder 精排（ms-marco-MiniLM-L-6-v2）
    (query-document 联合编码 → 相关性打分 → Top-5)
                   │
                   ▼
              最终排序结果
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   Streamlit    MCP        LangGraph
   可视化面板   工具接口    代理问答
```

### 代理状态机（LangGraph）

LangGraph 编译的声明式状态机，五个节点 + 条件边：

```
START → analyze_query  →  retrieve  →  check_results
                             ▲              │
                             │              ├── CE分数 ≥ 阈值 → generate_answer → END
                             │              │
                             │              └── CE分数 < 阈值 → rewrite_query ──┘
                             │                                        (最多循环 2 次)
                             └────────────────────────────────────────┘
```

状态通过 TypedDict 在全图中传递，包含 query 的各阶段变体（原始、精炼、改写）、检索结果、重试计数、和最终回答。条件路由以 Cross-Encoder 最高得分与阈值的比较作为分支判断依据。

## 三、数据管线详解

### 文档加载与编码检测

加载器支持三类文档格式，每种有独立的提取路径：

- **PDF**：使用 `pdfplumber` 逐页提取，对扫描版 PDF 自动降级为纯文本 warning
- **Markdown**：使用 Python 内置 `mistune` 风格解析器提取纯文本，同时运行栈式标题层级解析器构建 heading breadcrumb
- **纯文本**：先尝试 UTF-8 解码，失败后依次尝试 GBK、GB2312、GB18030、Latin-1。每种编码解码后检查是否有乱码特征字符，选择置信度最高的结果

### Token 级滑动窗口切块

这是整条管线中最重要的基础环节。切块质量直接决定检索质量的上界。

**为什么用 token 而非字符数？**
sentence-transformers 模型的输入是按 token 计数的。中文字符和英文单词的 token 化比例差异巨大（一个汉字可能 1-2 token，一个英文单词可能 2-5 token）。用字符数做窗口控制，实际上每个块的「模型可见信息量」波动很大。用 tiktoken 的 cl100k_base 编码器精确计数 token，保证每个块在模型视角下大小一致。

**滑动窗口重叠**：`chunk_size=512 tokens, overlap=128 tokens`。128 token 的重叠量确保了任意一个句子被完整包含在至少一个块内的概率极高，同时不引入过多的冗余信息。

**句子边界感知**：在 token 滑动窗口到达 512 时，向前回溯到最近的句子结束符（句号、换行、问号、感叹号），在该位置切分。如果回溯超过 64 个 token 仍未找到边界，则在当前位置硬切。

### Markdown 标题面包屑

栈式算法维护当前章节路径：遇到一级标题清空栈并压入新标题；遇到二级标题弹出栈中同级及更低级标题后压入；依此类推。每个切好的 chunk 继承切分点当时的完整栈状态，格式化为「一级标题 > 二级标题 > 三级标题」的面包屑字符串。纯文本和 PDF 文档此字段为空。

### 双重索引构建

**BM25 索引**：以 jieba 分词器的 `lcut` 模式对所有 chunk 做中文分词。使用 `rank_bm25` 库的 BM25Okapi 实现，默认参数（k1=1.5, b=0.75）。索引在内存中维护，服务启动时构建，查询延迟约 0.3 毫秒。

**向量索引**：使用 `sentence-transformers/all-MiniLM-L6-v2`（384 维）逐个对 chunk 编码。编码过程是显式调用 `model.encode()` 逐条完成的，而非使用 ChromaDB 的自动 embedding 函数——这样做是为了完全掌控向量计算过程，便于调试和替换模型。编码后的向量连同元数据存入 ChromaDB 持久化集合，底层使用 HNSW 图索引 + cosine 距离度量。查询延迟约 17 毫秒。

## 四、检索与融合管线

### BM25 检索

```python
tokenized_query = jieba.lcut(query)
bm25_scores = bm25_index.get_scores(tokenized_query)
top_k_indices = np.argsort(bm25_scores)[::-1][:20]
```

关键细节：BM25 的评分是**无界的**（取决于文档长度、词频等因素，通常在 0-50 区间）。这意味着 BM25 的分数不能直接和余弦相似度做线性组合。

### 向量检索

查询文本以相同方式编码为 384 维向量，然后调用 ChromaDB 的 `collection.query(query_embeddings=[...], n_results=20)`。返回的 distance 值通过 `1 - distance` 转换为相似度（因为 ChromaDB 使用 cosine distance，范围 [0, 2]，其中 0 表示完全相同）。

### RRF 倒数排名融合

这是解决「两种检索方式评分不可比」问题的关键设计。

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 个排名列表中的位置（从 1 开始），k 是平滑常数（默认 60）。

**为什么 k=60？**
k 值越大，排名靠后的文档的权重衰减越平缓。k=60 是一个经验上的平衡点：
- k 过小（如 k=1）：第一名和第二名的差距过大（1 和 0.5），过于强调各自的第一名，融合效果接近「各自取 Top-1」
- k 过大（如 k=200）：所有排名位置的分数趋同，融合退化为「投票制」——只要在两个列表中都出现就差不多，失去了排名的精细区分
- k=60 在保留排名区分度的同时，避免极端权重集中

RRF 的核心优势是与评分尺度无关——无论原始分数是什么量纲，只使用相对排名信息。

### Cross-Encoder 重排序

这是检索质量的最后一道提升。与 Bi-Encoder（分别编码 query 和 document 再计算相似度）不同，Cross-Encoder 将 query 和 document 拼接后**联合编码**，使注意力机制能在 query 和 document token 之间自由流动，从而捕捉到细粒度的语义匹配关系。

模型选择 `cross-encoder/ms-marco-MiniLM-L-6-v2`（384 维，6 层 MiniLM），输入格式为 `[CLS] query [SEP] document [SEP]`，输出为单一的相关性 logit，经 sigmoid 后得到 [0, 1] 区间分数。

**为什么只在 Top-20 上做 CE？**
Cross-Encoder 的推理速度比 Bi-Encoder 慢约 12 倍（单条 10ms vs 0.8ms）。在几千条 chunk 上全部跑 CE 会导致数秒的延迟。策略是：Bi-Encoder 做粗筛（召回率优先，Top-20），Cross-Encoder 做精排（精确率优先，Top-5）。这是检索系统中经典的两阶段排序范式。

## 五、LangGraph 代理设计

### 节点职责

**analyze_query**：调用 LLM 分析用户问题的类型、核心实体、和检索焦点。提取两个变体——`refined_query`（去除语气词的纯检索文本）和 `keywords`（核心关键词列表）。同时推断问题的预期答案类型（定义、操作步骤、对比分析等）。

**retrieve**：将 `refined_query`（或 rewrite_query 产出的变体）送入完整的检索+融合+精排管线，产出带有 CE 分数的 Top-5 结果列表。

**check_results**：这是代理的「自省」节点。检查检索结果中排名第一的 CE 分数是否超过环境变量配置的阈值（默认 0.5）。超过 → 路由到 `generate_answer`。未超过 → 增加 `retry_count`，若未达上限（默认 2 次），路由到 `rewrite_query`。

**rewrite_query**：调用 LLM 对原始问题进行改写。改写策略包括——扩展缩写和术语、增加同义词变化、从陈述句转为疑问句（或反之）、拆分复合问题。改写后的文本写回状态中的 `rewritten_query` 字段，路由回 `retrieve`。

**generate_answer**：将 Top-5 检索结果的文本拼接为上下文，连同原始 query 和对话历史一起送入 LLM，生成带引用的自然语言回答。每个事实主张后标注来源文档和段落编号。

### 节点间状态传递

状态为 TypedDict，字段包括：

| 字段 | 类型 | 说明 |
|------|------|------|
| `original_query` | str | 用户原始输入，全程不变 |
| `refined_query` | str | 经 analyze_query 提纯的检索文本 |
| `rewritten_query` | str | 经 rewrite_query 改写后的变体 |
| `retrieved_docs` | list[RetrievalResult] | 最近一次检索的 Top-5 |
| `top_ce_score` | float | Top-5 中最高的 CE 分数 |
| `retry_count` | int | 改写-检索的循环次数 |
| `final_answer` | str | 最终生成的自然语言答案 |

### 降级策略

LLM 调用全部有 fallback：
- `analyze_query` 失败 → 直接用原始 query 作为 refined_query，type 设为 unknown
- `rewrite_query` 失败 → 使用规则改写（添加常见同义词前缀、拆分为短句）
- `generate_answer` 失败 → 降级为模板拼接（标题 + 检索内容片段）
- 整个 LangGraph 图执行异常 → 返回静态错误消息 + 熔断状态

## 六、MCP 工具封装

基于 FastMCP 2.0，通过 stdio 传输协议暴露四个工具。MCP 客户端（如 Claude Desktop 或其他 MCP Host）可以通过标准输入输出流调用这些工具。

| 工具名 | 参数 | 返回 | 实现要点 |
|--------|------|------|---------|
| `search_knowledge` | query: str, top_k: int = 5 | 包含文本、来源、CE 分数的检索结果列表 | 走完整检索+融合+精排管线 |
| `list_documents` | 无 | 知识库中所有文档的文件名和块数 | 从已加载的文档名集合中汇总 |
| `get_chunk` | chunk_id: str | 指定块的完整文本和元数据 | 按 chunk_id 查 ChromaDB |
| `get_chunk_count` | 无 | 知识库总块数 | 从 ChromaDB collection.count() 获取 |

所有工具返回统一的结构化字典，包含 `success: bool`、`data`、和 `error` 三个顶层字段。工具内部异常不向外抛出，而是被捕获后封装在 error 字段中返回。

## 七、评测与实验体系

### 多层评测架构

项目建立了一套三层递进的评测体系：

```
检索质量评测（metrics.py + evaluate.py）
  → 回答质量评测（llm_evaluate.py，基于 Ragas）
    → 代理行为评测（agent_evaluate.py）
```

### 检索质量评测

**数据集**：36 个中文测试查询，分为四类（精确匹配 8 个、语义理解 8 个、混合 8 个、图关联 12 个），JSON 格式，每个查询标注了正确的 gold source 文档。训练集 18 条，测试集 18 条，全程 train/test 分离。

**指标**（全部自实现，不依赖外部评测库）：
- **MRR**（Mean Reciprocal Rank）：第一个正确答案的平均倒数排名。MRR=1.0 表示所有查询的第一个正确答案都排在第一位
- **Hit@K**：正确答案出现在前 K 个结果中的查询占比
- **Precision@K**：前 K 个结果中正确答案的占比
- **Recall@K**：所有正确答案中有多少出现在前 K 个结果中

**评测脚本**通过注入不同的检索配置参数，按阶段分别评测 BM25-only、Vector-only、Concat、RRF、Full Pipeline 的效果，输出对比表格。

### 关键评测结果

> 以下为早期 15 题小型评测集的数据。当前评测已升级为 36 题四层 Golden Test Set（exact_match / semantic / mixed / graph 四类），train/test 分离，test 全程不参与调参。最终指标（Test 集）：BM25+向量双路 RRF MRR **0.78**，CE 精排后 MRR **0.81**，Hit@5 **100%**。

| 配置 | MRR | 精确匹配类 | 语义类 | 混合类 |
|------|-----|-----------|--------|--------|
| BM25-only | 0.90 | 1.00 | 0.80 | 0.90 |
| Vector-only | 0.97 | 1.00 | 1.00 | 0.90 |
| BM25+Vector 拼接 | 0.95 | 1.00 | 0.90 | 0.95 |
| RRF 融合 | 0.99 | 1.00 | 1.00 | 0.98 |
| RRF + CE 重排（全管线） | 1.00 | 1.00 | 1.00 | 1.00 |

核心发现：
- 在精确匹配类问题上，BM25 和向量检索都能做到满分——这说明对于术语一致性高的查询，两种方式等价
- 在语义类问题上，BM25 为 0.80、向量为 1.00——这是向量检索的核心价值场景，MRR 提升了 27%
- 在混合类问题上，两种单一方式均为 0.90，全管线达到 1.00——融合+重排在这个场景带来了额外的 11% 提升
- 简单的 BM25+向量结果拼接（naïve concat）反而比纯向量差——这验证了不合适的融合策略可以**损害**效果，RRF 的 rank-based 策略是必要的

### 延迟分析

| 阶段 | 延迟 |
|------|------|
| BM25 检索 | ~0.33 ms |
| 向量检索 | ~17.56 ms |
| RRF 融合 | ~0.05 ms |
| Cross-Encoder 重排（5 条） | ~214 ms |
| **全管线总计** | **~232 ms** |

瓶颈在 Cross-Encoder，占总延迟的 92%。但这是有意为之的性价比权衡——用 200ms 换来从 0.99 到 1.00 的最后 1% MRR 提升。

### 消融实验框架

消融实验通过模块化切换实现：每个检索组件（BM25、向量、RRF、CE）可独立启用/禁用，评测脚本在 2^4=16 种组合上运行全部 15 个查询，输出多维度对比数据。此设计确保每个组件对最终效果的贡献都是可量化和可验证的。

### LLM-as-Judge 评测

使用 Ragas 框架监控最终生成内容质量。三项指标：
- **Faithfulness（忠实度）**：将回答拆分为原子陈述，逐条验证是否能从检索上下文中推断出来。得分为「可验证陈述数 / 总陈述数」
- **Answer Relevancy（回答相关性）**：反向生成问题——从回答中生成若干问题，看这些问题与原始 query 的余弦相似度
- **Context Recall（上下文召回率）**：标准答案中的每个句子是否都能在检索上下文中找到对应

当前状态（qwen2.5:7b）：F=0.95、AR=0.86、CR=0.79。

### 代理评测

`agent_evaluate.py` 衡量查询改写的实际效果：
- 原始 query 与改写后 query 的检索增量（检索 MRR 差值）
- 改写 query 与原始 query 的语义保真度（避免改写漂移到完全不同的语义）
- CE 阈值校准（0.3-0.7 扫描，找最优 balance point）

## 八、关键设计决策

### 为什么不使用 LangChain/LlamaIndex 的高级抽象？

LangChain 的 `RecursiveCharacterTextSplitter`、`VectorStoreRetriever`、`EnsembleRetriever` 等封装确实可以减少代码量。但封装层隐藏了内部细节——token 计数方式、embedding 调用时机、融合的具体算法——这些正是这个项目想要展示和理解的东西。

所有组件从底层实现：切块逻辑手写、embedding 计算手动批处理、融合算法直接实现、评测指标从 numpy 基础运算构建。每条线都是透明的。

### 为什么不使用 Cohere/OpenAI 的 Embedding API？

使用本地模型（all-MiniLM-L6-v2）而不是 API 的三点考虑：
1. **零成本**：无 API 调用费用，实验可以无限次运行
2. **离线可用**：不依赖外部网络，任何机器都能跑
3. **结果可复现**：本地模型的输出是确定性的，而商业 API 可能在后台更新模型版本导致同输入不同输出

384 维向量在几百到几千个文档的规模下完全够用，不需要 1024 或 1536 维的高维嵌入。

### 为什么用 ChromaDB 而不是 FAISS 或 Qdrant？

- **ChromaDB**：开箱即用的持久化，Python 原生集成，无需单独部署服务，对开发体验最友好
- FAISS 的检索性能更强但持久化需要额外工作，Qdrant 需要独立服务进程
- 在当前文档规模（千级）下，ChromaDB 的 HNSW 索引性能完全够用

### 为什么用 jieba 分词而不是直接用字级别的 BM25？

中文不像英文有天然的空格分隔。如果对中文做字级别的 token 化，「机器学习」会变成「机」「器」「学」「习」四个独立 token，BM25 的倒排索引无法识别它们作为一个整体词组的匹配价值。jieba 将中文文本正确切分为有意义的词组，使 BM25 在中文上的检索质量从字符匹配提升到了词汇匹配。

## 十、工程要点总结

**每个环节的「为什么」都有一个答案：**

| 设计决策 | 原因 |
|---------|------|
| Token 级而非字符级切块 | 中英文 token 化比例差异大，token 计数保证模型视角下块大小一致 |
| 滑动窗口重叠 128 token | 防止关键句被切在两块中间，128 token 覆盖绝大部分句子 |
| 双路检索各自独立 | BM25 和向量的失效模式正交——前者怕同义词改写，后者怕专有名词模糊 |
| RRF 而非分数线性加权 | 两种检索方式的评分量纲不同（BM25 无上界，向量在 [0,1]），直接加权无意义 |
| CE 仅在 Top-20 上运行 | 性能取舍：在全量文档上跑 CE 延迟不可接受，两阶段排序是行业标准策略 |
| 代理自省节点 | 避免在检索质量差时强行生成幻觉答案，改写重试的性价比远高于硬编 |
| 所有 LLM 调用有 fallback | 本地模型可能不可用（OOM、未启动等），规则降级保证系统永不崩溃 |
| 评测指标全部自实现 | 透明度和可控性优先于便利性——知道每个数字是怎么算出来的 |
| 评测覆盖三类查询 | 确保系统在术语精确匹配、语义泛化、和混合场景下都经过验证 |
| LLM-as-Judge 三道把关 | 忠实度防幻觉、相关性防偏题、召回率防遗漏——三道互补覆盖回答质量全貌 |

这个项目的架构理念是：**每一层都暴露，每一步都可测，每一个组件都可替换**。它不是最快的 RAG、不是最强的 RAG、但它是每个环节都能被完整理解和独立验证的 RAG。
