# RAG (检索增强生成) 基础概念与架构

## 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将大规模语言模型（LLM）与外部知识检索系统相结合的架构范式。其核心思想是：在 LLM 生成回答之前，先从可信的知识库中检索与用户问题最相关的内容，作为上下文喂给模型，从而显著提升回答的准确性与可信度。

传统的大语言模型完全依赖训练时学到的参数知识来回答问题。这种方式存在两个根本性缺陷：一是模型的知识有截止日期，无法回答最新发生的事；二是模型容易产生"幻觉"（Hallucination），即一本正经地编造看似合理实则错误的内容。RAG 通过引入外部检索环节，从根本上缓解了这两个问题。

---

## RAG 的基本原理

一个标准的 RAG 流程包含以下四个环节：

**1. 索引（Indexing）**

将知识文档切分成若干片段（Chunk），经过嵌入模型（Embedding Model）转换为向量表示，存入向量数据库（Vector Database）。这个过程通常在离线阶段完成。

**2. 检索（Retrieval）**

用户输入查询（Query）后，使用相同的嵌入模型将查询转换为向量，然后在向量数据库中进行相似度搜索，返回与查询最相关的 Top-K 个文档片段。

**3. 增强（Augmentation）**

将检索得到的相关文档片段与原始用户查询组合，形成结构化的提示词（Prompt）。通常采用 "Context + Question + Answer instruction" 的模板。

**4. 生成（Generation）**

将增强后的提示词发送给大语言模型，由模型基于提供的上下文生成最终回答。

```
用户查询 → 检索模块 → 向量数据库匹配 → Top-K 文档
                    ↓
           构造增强提示词
                    ↓
           LLM 生成回答
```

---

## Vector Database 的角色

向量数据库是 RAG 系统中承上启下的核心组件。它的职责是将文本片段转化为高维向量，并通过高效索引实现毫秒级的相似度搜索。

常见的向量数据库包括：

| 数据库 | 特点 |
|--------|------|
| ChromaDB | 轻量级，专为 LLM 应用设计，易用性好 |
| Milvus | 开源分布式向量数据库，支持十亿级规模 |
| Qdrant | 支持混合搜索（向量 + 过滤条件） |
| Weaviate | 原生支持多模态数据 |

向量数据库的核心技术是近似最近邻搜索（ANN）。由于在高维空间中精确搜索的计算代价极高，通常采用 HNSW（Hierarchical Navigable Small World）、IVF（Inverted File Index）等算法，在召回率与性能之间取得平衡。

---

## Generator 与 Retriever 的配合

Retriever（检索器）和 Generator（生成器）是 RAG 的两大支柱，二者的协作质量直接决定系统效果。

**Retriever 负责"找对东西"**

检索器的目标是尽可能精准地找到与用户问题相关的文档片段。常用的检索策略包括：

- **稀疏检索（Sparse Retrieval）**：如 BM25，基于关键词词频和逆文档频率计算相关性，适合精确术语匹配。
- **稠密检索（Dense Retrieval）**：如基于 BERT 或 Sentence-Transformers 的向量检索，能捕捉语义层面的相关性。
- **混合检索（Hybrid Retrieval）**：同时使用稀疏和稠密方法，再通过 RRF（Reciprocal Rank Fusion）等融合策略合并结果。

**Generator 负责"理解并回答"**

生成器通常是一个大语言模型，负责理解检索到的上下文并生成自然语言回答。生成器的表现受以下因素影响：

- 上下文窗口大小：决定能喂入多少检索结果
- 对齐上下文信息的能力：能否充分利用检索内容而非依赖自身知识
- 指令遵循能力：能否基于给定事实回答，而非天马行空

**二者配合的挑战**

Retriever 和 Generator 并非总能完美配合。检索结果的相关性直接影响生成质量：如果检索返回了错误或无关的片段，模型很可能会被误导。因此，现代 RAG 系统往往会引入重排序（Re-ranking）环节，如使用 Cross-Encoder 对检索结果进行二次打分筛选。

---

## Naive RAG 的局限性

最基础的 RAG 实现（称为 Naive RAG 或 Classic RAG）遵循"检索 → 拼接 → 生成"的线性流程。这种架构简单直接，但存在以下明显不足：

**1. 检索质量不稳定**

当用户查询与知识库文档的表述方式差异较大时（如使用同义词或间接表述），基于向量相似度的检索容易漏掉相关内容。这被称为"语义鸿沟"问题。

**2. 上下文窗口利用不充分**

一次性将所有检索结果塞入上下文，可能导致关键信息被稀释。特别是当 Top-K 较大时，不相关的内容会挤占模型对核心信息的注意力。

**3. 无法处理多跳推理**

Naive RAG 的单次检索-生成流程难以回答需要综合多个文档片段进行推理的问题。例如"作者 A 和作者 B 对某个观点有什么不同看法"这类对比性问题，单次检索往往无能为力。

**4. 缺乏自我纠错机制**

生成结果如果包含错误，Naive RAG 没有反馈回路来检测和修正，只能依赖外部评估手段。

---

## 从 Naive RAG 到 Advanced RAG

为解决上述问题，社区发展出多种优化策略：

- **查询改写（Query Rewriting）**：将用户口语化查询转换为更适合检索的表述。
- **子问题拆分（Sub-question Decomposition）**：将复杂问题拆解为多个简单子问题分别检索。
- **重排序与过滤（Re-ranking）**：用更精准的模型（如 Cross-Encoder）对初检结果二次筛选。
- **图结构增强（Graph-Augmented RAG）**：引入知识图谱或实体共现图，在语义层面扩展检索范围。
- **迭代检索与生成（Iterative RAG）**：在生成过程中引入反思机制，根据需要触发多次检索。

这些进阶方法共同推动 RAG 从简单的"查-拼-答"走向更智能的知识问答系统。

---

## 总结

RAG 通过将外部知识库的精确性与大语言模型的生成能力相结合，提供了一种可行的大模型落地路径。理解 Retriever 与 Generator 的协作机制、认识 Naive RAG 的局限性，是设计高质量 RAG 系统的基础。随着检索算法、向量索引和生成模型的持续进步，RAG 将在企业知识管理、智能客服、代码助手等场景中发挥越来越重要的作用。
