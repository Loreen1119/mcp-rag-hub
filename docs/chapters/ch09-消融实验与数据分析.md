# 第 9 章：消融实验与数据分析

> 本章数据基线：**2026-09-12，语料 `corpora/fastapi-zh`（FastAPI 中文文档 122 篇 / 677KB / 1445 chunk）**，测试集 `data/test_queries.json` 18 条。
> 复现：`python -m src.evaluation.retrieval_eval --split test`
> ⚠️ 本章所有数字都绑定这份语料。换语料必须重跑，不可沿用。

## 知识点

### 1. 消融实验的两层含义

**狭义消融**（Ablation）：依次移除一个模块，看性能下降多少 → 证明每个模块都有贡献。

**广义实验**：包含模块隔离对比、参数敏感性扫描、分类别分析、延迟剖析、单 Query 链路追踪共五个维度。

实验套件的核心价值：**把架构决策从"我觉得"变成"数据证明"**。

### 2. 五个实验维度

| 实验 | 回答的问题 | 面试价值 |
|------|-----------|----------|
| 模块隔离消融 | 每个模块独立贡献多大？ | 证明混合检索 + CE 有价值 |
| 分类别分析 | 哪个模块对哪类 query 最有帮助？ | 证明 BM25/Vector 互补 |
| 参数敏感性 | 参数调不调有区别吗？ | 证明系统鲁棒性 |
| 延迟剖析 | 时间花在哪？瓶颈是什么？ | 证明需要 tradeoff 思维 |
| Query 深度追踪 | 单个 query 在链路中怎么被处理？ | 讲清一次检索的全过程 |
| 改写评测 | 改写是否提升了检索？阈值多高最优？ | 证明 Agent 决策逻辑有数据支撑 |

### 3. 本次实验的语料与数据

| 项 | 值 |
|---|---|
| 语料 | `corpora/fastapi-zh`（FastAPI 官方中文文档，MIT） |
| 规模 | 122 篇 Markdown / 677KB / **1445 chunk**（chunk_size=256, overlap=38） |
| 测试集 | 18 条，四类分层：exact_match 4 / semantic 4 / mixed 4 / graph 6 |
| 每条的 golden 依据 | `golden_chunk_sources` 指定具体文件，`golden_answer` 可从该文件正文回查（`scripts/validate_golden.py` 自动校验，0 问题） |
| 评测阶段 | BM25 → Vector → RRF → Cross-Encoder 四级，逐级累积 |

## 核心结果

### 各阶段总体指标（18 条）

| 阶段 | MRR | Hit@5 | Prec@5 | Recall@5 |
|------|-------|-------|--------|----------|
| BM25 | 0.5469 | 0.8889 | 0.4333 | 0.8889 |
| Vector | 0.7246 | 0.8333 | 0.3889 | 0.8333 |
| RRF 融合 | 0.7833 | 0.9444 | 0.5000 | 0.9444 |
| CE 精排（全管线） | **0.7889** | **1.0000** | **0.5444** | **1.0000** |

### 消融增量（相对上一级）

| 跃迁 | ΔMRR | ΔHit@5 | ΔPrec@5 |
|------|------|--------|---------|
| BM25 → Vector | **+0.1777** | −0.0556 | −0.0444 |
| Vector → RRF | **+0.0587** | **+0.1111** | **+0.1111** |
| RRF → CE | +0.0056 | **+0.0556** | +0.0444 |

## 核心发现

### 发现 1：两路召回互补，而且互补方式可以量化

单看总表，BM25（MRR 0.547）明显弱于 Vector（0.725），容易误判成"BM25 是多余的"。但看分类别看单条，结论完全不同：

| 单条 case | 查询 | BM25 MRR | Vector MRR | 说明 |
|---|---|---|---|---|
| S04 | 请求进入前后插入通用逻辑（→ 中间件） | **0.0000**（完全召回失败） | **1.0000** | 字面完全不含"中间件"，BM25 无能为力 |
| M08 | FastAPI 应用怎么做测试？ | **0.1111**（Hit@5=0） | 0.5000 | 同上 |
| S02 | 启动执行一次、关闭收尾的机制（→ lifespan） | 0.5000 | **0.0000**（Hit@5=0） | 反向：Vector 漏了 |
| S06 | 配置项放代码外、运行时读取并保证类型（→ settings） | 0.2000 | **0.0000**（Hit@5=0） | 同上 |

**关键**：向量路把 S04 从"完全找不到"提到满分，却在 S02/S06 上掉到 0——**两路的失败集合几乎不重叠**。这就是"混合召回"最硬的证据：不是感觉上需要两者，而是数据上两者的盲区互补。

### 发现 2：RRF 的价值在"补短板"，不在"提上限"

RRF 的 MRR 只比 Vector 高 0.059，但 **Hit@5 从 88.9%(BM25) / 83.3%(Vector) 升到 94.4%** —— 它是唯一一个把两路各自漏掉的单条同时补回来的环节：

- S04：BM25 Hit@5=0 → RRF 命中（Vector 的贡献）
- S02：Vector Hit@5=0 → RRF 命中（BM25 的贡献）

**面试表述**：「RRF 不是给最强的单路锦上添花，而是把两路失败集合的并集缩小。我的数据里 BM25 和 Vector 的单路 Hit@5 分别是 88.9% 和 83.3%，两者都不低但都不全；融合后 94.4%。如果只选一路，无论选哪一路都会有约 1/6 的问题完全召回不到。」

### 发现 3：Cross-Encoder 的职责是"排序"和"兜底"，不是"提升"

CE 阶段 Hit@5 = **100%**（18/18 全部进 Top-5），Prec@5 从 0.50 → 0.544，**但 MRR 只涨了 0.0056**。

拆开看每一级 MRR 的变化，会看到更诚实的一面——CE 是**有得有失**的：

| 方向 | case | RRF MRR → CE MRR |
|---|---|---|
| CE 修好了 | E02 路径操作装饰器 | 0.3333 → **1.0000** |
| CE 修好了 | S04 中间件 | 0.5000 → 1.0000 |
| CE 修好了 | M02 请求体/响应体 | 0.5000 → 1.0000 |
| CE 修好了 | S02 lifespan | 0.3333 → 0.5000 |
| **CE 弄坏了** | G08 直接返回 Response 的副作用 | 1.0000 → **0.2500** |
| **CE 弄坏了** | M04 指定 HTTP 状态码 | 1.0000 → **0.2500** |
| **CE 弄坏了** | S08 返回网页而非 JSON | 1.0000 → 0.5000 |

净收益 = (+2.101 − 2.000) / 18 ≈ **+0.006**。

**面试表述（这一段比"CE 全能"可信得多）**：「CE 的收益不是单调的。它在 RRF 已经排错的 case 上把它救回第 1 位（E02 从 MRR 0.33 到 1.0），但在 RRF 已经排对的 case 上也会把正确答案从第 1 位挪到第 3、4 位（G08、M04 从 1.0 掉到 0.25）。净 MRR 提升只有 0.006，看起来几乎无用。**但真正的价值在 Hit@5：它把召回从 94.4% 补到了 100%**。所以我的结论是——召回交给 RRF 保证，CE 只负责在 Top-20 候选内做排序，并且它的定位应该是'兜底'而不是'提分'。如果把 CE 当成提 MRR 的银弹，这个数据会直接打脸。」

### 发现 4：最弱单条 S06 揭示了 pipeline 的边界

S06（"怎么把配置项放在代码之外、运行时再读进程序，并保证类型正确？" → `advanced/settings.md`）：

```
bm25    MRR 0.2000  Hit@5=1
vector  MRR 0.0000  Hit@5=0
rrf     MRR 0.1000  Hit@5=0   ← 融合后反而丢了
ce      MRR 0.2000  Hit@5=1   ← 只有 CE 救回
```

这是全 18 条里唯一"RRF 阶段完全召回失败、只有 CE 救回"的案例，也是 CE 存在必要性的最直接证据。根因是查询用的是纯自然语言描述需求（"配置项放在代码之外"），与文档标题「设置和环境变量」字面零重叠——**这类查询需要的是跨语义的强匹配，正是 Cross-Encoder 全注意力打分的强项**。

## 语料升级前后：一次方法论层面的修正

这一节是本章最重要的部分——它是"承认早期实验在错误条件下得出结论、并说明何时结论才成立"的完整记录。

| 维度 | 升级前（旧语料） | 升级后（`corpora/fastapi-zh`） |
|---|---|---|
| 语料规模 | 3 chunk（后扩到 45 chunk / 7 文件 19KB） | **1445 chunk / 122 文件 677KB** |
| 与召回参数的关系 | `VECTOR_TOP_K=20` 一次召回 **44% 的库**，"检索"没有可挑的余地 | 召回 1.4% 的库，检索真正在做筛选 |
| 指标表现 | 参数扫描（RRF_K、CE_TOP_K）**全部满分** | 出现真实梯度，参数有意义 |
| RRF 结论 | **负优化**：优于 Vector 单路时为 −0.0334（RRF MRR 0.9333 < Vector 0.9667） | **正向**：+0.0587 MRR、+0.1111 Hit@5 |
| 天花板效应 | 存在，且作者当时已诚实标注 | **消失**，指标差异来自真实能力差异 |

**被修正的结论**：旧 ch09 曾记录「RRF 在小语料下比单独 Vector 还差，因为 RRF 只看排名不看原始分数质量」——这个观察在 3 chunk 语料下是真的，但**不能外推**。在 1445 chunk 上，RRF 是明确的正向环节。原因也很清楚：语料太小时，"排名"信息本身没有信息量（所有 chunk 都能被召回），RRF 自然退化成噪声放大器。

**面试表述**：「我早期在一个 3 chunk 的语料上做消融，得到过'RRF 负优化'的结论。后来换了 1445 chunk 的真实文档语料重跑，结论反过来了——RRF 是明确正向的。这件事让我记住一个方法论上的坑：**当语料规模小到召回参数一次能捞回半个库时，所有关于'召回策略'的实验都失去意义**，因为不存在'筛掉'这个动作。旧结论不是错的，是被错误的条件限制住了。我在文档里保留了这段修正过程，而不是删掉旧数据假装一直都对。」

## 一次被数据推翻的设计假设（重要）

比消融实验更值得记录的是：**一个曾经写进代码的核心设计，被自己跑的数据否掉了。**

**原设计**：用 Cross-Encoder 的 Top-1 绝对分数卡一个阈值，低于阈值就判定"知识库没有答案"直接拒答。阈值定为 7.81，注释写着"让 10 条不可回答里只放行 2 条，误接受率 20%"。

**实测（旧语料 Phase 0 分析：36 条可答 / 10 条不可答）**：

| 阈值 | 可答放行 | 误拒可答 | 误放无答案 | 误接受率 |
|---|---|---|---|---|
| 7.81 | 12/36 | **24 (67%)** | 2 | 20% |
| 7.0 | 27/36 | 9 (25%) | 7 | **70%** |

可答组均值 **7.4248**、不可答组均值 **7.0910**，两组分布**严重重叠**（不可答组的最大值 8.2350 比很多可答样本还高）。

**结论**：CE Top-1 绝对分数对"可答/不可答"**没有二分区分能力**。卡 7.81 会误拒 2/3 的正确问题，卡 7.0 会误放 70% 的无答案问题——**任何单一阈值都是赌**。

**处置**：`CE_ANSWER_THRESHOLD` 常量从 `config.py` **删除**；拒答判断完全交给 LLM 的语义判断 + validator；CE 分数只在排序和界面展示中使用。相关的 train/test 拆分（train 集本就是为调这个阈值而设）也随之失去用途。

**面试表述**：「我一开始把'拒答'设计成一个阈值问题，用一个查表选出来的 7.81 当门控。跑数据时发现可答组和不可答组的分数分布几乎完全重叠，均值只差 0.33——阈值往上调误拒 67%，往下调误放 70%。所以我把这个设计整个删掉了，改成让 LLM 在拿到证据后做语义判断。**这件事的价值不在于'我删了一个常量'，而在于我没有选择调参硬凑一个看起来合理的数字**——如果我只在 10 条不可答样本上调阈值，很容易找到一个'误接受率 0%'的漂亮数字，但它会在真实流量上把大部分能答的问题拒掉。」

## 诚实面对实验条件

面试时主动说明条件的边界，比被追问出来可信得多：

- 本套指标是**单一语料**（FastAPI 中文文档）上的结果，换语料需重跑，**不可外推**。
- 18 条测试集规模偏小，单条 case 的指标波动会显著影响总体数字（例如 CE 净 MRR 收益只有 0.006，其中 −2.0 的扣分只来自 3 条 case）。**相对趋势（哪一路擅长什么）比绝对数值更可靠。**
- 消融是**累积式**（BM25→+Vector→+RRF→+CE），不是完全正交的模块隔离；后一级的增益里含有前一级的贡献。
- 语料来自第三方开源文档（MIT），测试集的 golden 依据可逐条回查源文件（`scripts/validate_golden.py`），**不存在"为考试补答案"**。

## 面试速记

- **四级累积指标**：BM25 → 0.5469 → Vector 0.7246 → RRF 0.7833 → CE 0.7889（MRR）；Hit@5 最终 **100%**
- **两路失败集合几乎不重叠**：向量救 S04（0.000→1.000），BM25 救 S02/S06（Vector 掉到 0.000）
- **RRF 补短板**：单路 Hit@5 88.9% / 83.3% → 融合 94.4%
- **CE 有得有失**：救回 E02（0.33→1.0）、弄坏 G08/M04（1.0→0.25），净 MRR 仅 +0.006，价值在 Hit@5 补到 100%
- **S06 是 CE 唯一不可替代的证据**：RRF 阶段 Hit@5=0，只有 CE 救回
- **被自己数据打死的设计**：CE 阈值拒答门控（7.81 → 误拒 67%；7.0 → 误放 70%；分布重叠无区分度）→ 直接删除，拒答交给 LLM
- **旧结论会被条件限制**：「RRF 负优化」在 3 chunk 语料下成立，1445 chunk 下反向——小语料下"召回策略"实验没有意义
- **诚实标注**：单语料、18 条、累积式消融；延迟数据待重测

## 关键实现

### ① 模块隔离 vs 累积增量

评测脚本对同一批 query 依次跑四级，**每级都在上一级的候选基础上工作**，因此指标是累积式的：

```python
# src/evaluation/retrieval_eval.py —— 四级依次评测同一批 query
"bm25"          -> bm25.search(query)
"vector"        -> vector.search(query)
"rrf"           -> rrf_fuse(bm25_results, vector_results)
"cross_encoder" -> ce_rerank(rrf_results)
```

**追问应对**：「为什么不做完全正交的模块隔离？」— 正交隔离（如 full_pipeline 去掉 CE）在我这套实现里等价于"取 RRF 的结果"，因为 CE 是链路最后一级、只重排不改召回集合。所以 RRF → CE 这一跃迁实际就是"加不加 CE"的隔离对比，可以直接读。真正需要额外构造隔离对比的是 Vector 是否存在——那要靠只跑 BM25 的 `bm25` 行与 `rrf` 行对比。

### ② 指标口径

```python
# src/evaluation/metrics.py
MRR       = 1/rank_of_first_relevant     # 只奖励第一条相关结果的位置
Hit@K     = 1 if any relevant in top_K   # 只要进了 K 就算召回成功
Precision@K = relevant_in_top_K / K
Recall@K    = relevant_in_top_K / total_relevant
```

**为什么 MRR 和 Hit@5 要一起看**（本次实验最有用的一个组合）：MRR 对"排序位置"敏感、Hit@5 对"是否召回到"敏感。CE 阶段 MRR 只涨 0.006 会让人误以为它没用，但 Hit@5 从 94.4% 涨到 100% 才是它真正的贡献——**只看单一指标会得出完全错误的模块结论**。

### ③ 延迟剖析的度量方法

```python
t0 = time.perf_counter()
results = retriever.search(query)
elapsed_ms = (time.perf_counter() - t0) * 1000
```

用 `perf_counter()` 而非 `time.time()`——前者是墙上时钟的高精度版本，不受系统时间调整影响，适合做微基准。
