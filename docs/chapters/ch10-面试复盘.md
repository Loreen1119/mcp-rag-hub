### ① RRF 算法实现

```python
def reciprocal_rank_fusion(rankings, k=60):
    """RRF — 多路排名融合，消除量纲差异。

    BM25 得分 0~几十，向量余弦相似度 0~1，直接加权 BM25 会碾压。
    RRF 用排名替代分数：score(chunk) = Σ 1/(k + rank(chunk))
    """
    scores = {}        # chunk_id → rrf_score
    chunk_map = {}     # chunk_id → (Chunk, original_source)

    for ranking in rankings:
        for rank, result in enumerate(ranking, start=1):
            cid = result.chunk.chunk_id
            scores[cid] = scores.get(cid, 0) + 1.0 / (k + rank)
            if cid not in chunk_map:
                chunk_map[cid] = (result.chunk, result.source)

    # 按 RRF 得分降序
    sorted_items = sorted(scores.items(), key=lambda x: x[1], reverse=True)

    results = []
    for cid, rrf_score in sorted_items:
        chunk, source = chunk_map[cid]
        chunk.metadata["rrf_score"] = round(rrf_score, 6)
        chunk.metadata["original_source"] = source
        results.append(RetrievalResult(chunk=chunk, score=rrf_score, source="rrf"))
    return results
```

**面试时边写边说**：
- k=60 是平滑常数，k 越小排名靠前的文档权重越大，消融实验验证 30/60/120 结果一致
- 时间复杂度 O(NlogN)，瓶颈在 sort，多路排名通常很短（Top-20），实际 <1ms
- 不依赖原始分数，天然消除 BM25（词频整数）和向量（余弦相似度 0~1）的量纲差异

### ② BM25 检索流程

```python
class BM25Retriever:
    def __init__(self, chunks):
        self.chunks = chunks
        self._tokenized_corpus = []
        self._bm25_map = []

        for idx, chunk in enumerate(chunks):
            tokens = list(jieba.cut(chunk.content))
            tokens = [t.strip() for t in tokens if t.strip()]
            if tokens:
                self._tokenized_corpus.append(tokens)
                self._bm25_map.append(idx)

        self._bm25_index = BM25Okapi(self._tokenized_corpus)

    def search(self, query, top_k=20):
        query_tokens = [t.strip() for t in jieba.cut(query) if t.strip()]
        scores = self._bm25_index.get_scores(query_tokens)
        top_indices = np.argsort(-scores)[:min(top_k, len(scores))]

        results = []
        for local_idx in top_indices:
            bm25_score = float(scores[local_idx])
            if bm25_score <= 0:
                continue
            chunk_idx = self._bm25_map[local_idx]
            results.append(RetrievalResult(
                chunk=self.chunks[chunk_idx], score=bm25_score, source="bm25"
            ))
        return results
```

**面试时边写边说**：
- jieba 分词 → 中文按词切分而非字符 n-gram，专有名词不会被拆碎
- `rank_bm25` 库底层是 BM25Okapi 算法，TF 饱和 + IDF 逆文档频率 + 文档长度归一化三因子
- 空 token 过滤：纯标点/空白 Chunk 跳过，避免空字符串污染索引
- 零分结果过滤：score ≤ 0 的不返回，BM25Okapi 对完全不相关的 query 会打出负分

### ③ Cross-Encoder 精排流程

```python
class CrossEncoderReranker:
    def __init__(self, model_name="BAAI/bge-reranker-base"):
        self.model = CrossEncoder(model_name)

    def rerank(self, query, candidates, top_k=5):
        # 1. 构造 query-doc pairs
        pairs = [(query, r.chunk.content) for r in candidates]

        # 2. 联合编码 → 一次性做完整注意力计算
        scores = self.model.predict(pairs, show_progress_bar=False)

        # 3. 按 CE 得分降序，取 Top-K
        scored = list(zip(candidates, scores))
        scored.sort(key=lambda x: x[1], reverse=True)

        results = []
        for rank, (candidate, ce_score) in enumerate(scored[:top_k]):
            meta = dict(candidate.chunk.metadata)
            meta["ce_score"] = round(float(ce_score), 4)
            meta["ce_rank"] = rank + 1
            results.append(RetrievalResult(
                chunk=Chunk(content=candidate.chunk.content, metadata=meta,
                            chunk_id=candidate.chunk.chunk_id),
                score=float(ce_score), source="cross_encoder",
            ))
        return results
```

**面试时边写边说**：
- Cross-Encoder 把 `(query, doc)` 拼接后送入模型做一次完整前向传播，query 和 doc 的每个 token 之间都有注意力交互
- 对比 Bi-Encoder——query 和 doc 分别独立编码，快但 query-doc 之间没有交互
- 两阶段策略：Bi-Encoder 粗筛 Top-20（快，约 21ms），Cross-Encoder 对 20 个候选精排 Top-5（准，约 373ms）
- **模型选型**：中文语料必须用中文 reranker。早期用英文 `ms-marco-MiniLM`，判定不准；
  现在用 `bge-reranker-base`，sigmoid 输出 [0,1]。换模型后**所有分数阈值都要重标**
  （质量门控从 3.0 降到 0.3）—— 这是个很好的"踩过坑"的谈资。

## 第二部分：三个必问题逐字稿

### 必问题 1：BM25 和向量检索有什么区别？为什么都用？

**面试官**："你用了 BM25 和向量检索双路召回，它们到底有什么区别？"

**回答**："两个字面维度：

**原理层**：BM25 是稀疏的关键词匹配，基于 TF-IDF 变体——TF 饱和曲线控制词频权重、IDF 抑制高频词、文档长度归一化防止长文档霸榜。向量检索是把句子编码成 512 维的稠密向量（`bge-small-zh-v1.5`），在高维空间里算余弦距离。前者看字面，后者看语义。

**优劣势**：BM25 对专有名词、报错编号、数字精确匹配极强——你搜 '路径操作装饰器'，它精准命中。但它对同义词盲视。我语料里最典型的一条：S04 问"请求进入前后插入通用逻辑"（答案是"中间件"），query 里**一个字都没提到中间件**，BM25 的 MRR 直接是 **0.0000**，向量检索是 **1.0000**。

**为什么都用**：关键不只是"各有优势"，而是**两路的失败集合几乎不重叠**——我 18 条测试集里，向量路救回了 BM25 完全找不到的 S04（0.000→1.000），而 BM25 在向量路掉到 0.000 的 S02 / S06 上仍有召回。整体看：BM25 MRR 0.5469 / Hit@5 88.9%，Vector 0.7246 / 83.3%，**谁都不全**。这不是感觉上需要两路，是数据上两路的盲区互补。

**延迟代价**：BM25 约 0.4ms，向量检索（encode + ChromaDB 查询）约 21ms，差约 50 倍。（⚠️ 这批延迟数是旧英文 CE 模型下的记录，重测后会更新；数量级关系不变。）"

### 必问题 2：RRF 和加权求和有什么区别？为什么选 RRF？

**面试官**："为什么用 RRF 融合而不是直接加权求和？"

**回答**："核心问题是**量纲差异**。

BM25 的原始得分是词频统计值——可能 0 到几十。向量检索的余弦相似度是 0 到 1。如果直接加权，BM25 的分数会像坦克一样碾压向量检索的结果——你哪怕给向量 0.01 的权重也没用，因为它不知道 BM25 得分 20 是算高还是算低。

**RRF 的解法**：完全不看原始分数，只看排名。`score = Σ 1/(k + rank)`。排名第 1 永远得 1/(60+1)=0.0164，不管你是 BM25 的 22.5 分还是向量的 0.89 分。这天然消除了量纲差异。

**代价**：RRF 丢弃了分数梯度信息。比如 BM25 的 Top-1 和 Top-2 可能实际得分差了一个量级，但在 RRF 眼里它们就是 rank 1 和 rank 2 的区别。但实际工程中这个代价可接受——融合后还有 Cross-Encoder 做精细重排，RRF 只需要负责把两路的 '好苗子' 都拉进来就行。

**为什么不用学习型融合**（如 LambdaMART）：需要训练数据和在线特征工程，我的场景是零样本冷启动，RRF 不需要训练，开箱即用。"

### 必问题 3：Bi-Encoder 和 Cross-Encoder 有什么区别？为什么两阶段？

**面试官**："你的 VectorRetriever 不就是向量检索吗，后面再加 Cross-Encoder 不是重复了？"

**回答**："不重复，它们是**完全不同**的工作机制。

**Bi-Encoder 是怎么做的**：query 和所有 doc 分别独立过 encoder，各得到一个 512 维向量，然后算余弦相似度。这意味着 query 和 doc 之间**没有任何 token 级别的交互**——query 的 '如何评价' 和 doc 的 '评测好坏' 能不能对上，全靠训练时学到的句子级语义表示。好处是 doc 向量可以提前离线算好存到 ChromaDB，检索时只算 query 向量，一次查询只需 1 次模型推理 + 1 次向量相似度查找。适合**全库粗筛**。

**Cross-Encoder 是怎么做的**：把 `query [SEP] doc` 拼接成一对，送进 Transformer 做一次完整的前向传播。每个 token 都能看到对面所有 token。这意味它能捕捉 query-doc 之间的精细交互——比如 query 里的 '评价' 和 doc 里的 '评测' 究竟是不是在同一个语境下。代价是每一对 query-doc 都要做一次独立推理。做不到离线缓存，只能在线跑。

**两阶段的必要性**：Bi-Encoder 粗筛全库（快，约 21ms），Cross-Encoder 精排 Top-20（慢，约 373ms，占总延迟约 94%）。如果直接用 Cross-Encoder 扫全库 1445 个 Chunk，延迟会爆炸。如果只用 Bi-Encoder，粗筛质量不够。

这里我要说个**反直觉的数据**：加 CE 之后，MRR 只从 0.7833 涨到 0.7889——几乎没动。但 **Hit@5 从 94.4% 补到 100%**。而且拆开看它**有得有失**：救回了 E02（0.33→1.00），也把 G08 / M04 从 1.0 弄到 0.25。所以 CE 的准确定位是"**兜底 + 排序**"，不是"提分"——最硬的证据是 S06：RRF 阶段 Hit@5=0（融合后反而丢了），只有 CE 把它救回来。这是典型的**精度-延迟的工程权衡**，而且我更愿意把 CE 的真实贡献讲准，而不是只报一个好看的 MRR。"

### 追问 1：CE 延迟优化（94% → 砍半）

**问题**：Cross-Encoder 精排把 Hit@5 补到了 100%，但它占了总延迟的约 94%。在不牺牲太多召回精度的前提下，把延迟至少砍掉一半，你会从哪些方向优化？

> ⚠️ 94% 这个数是旧英文 CE 模型（`ms-marco-MiniLM`）下的记录，现已换成 `bge-reranker-base`（约 1.1GB），
> **重测前只当数量级参考**。面试时主动说明"这批延迟数待重测"，反而显得严谨。

**答题框架：先亮公式，再三条线展开**

```
CE 总延迟 = 单次推理延迟 × 候选数量
```

所有优化方案，要么砍左边，要么砍右边，要么并行重叠。

**方向一：减少候选数量（砍右边）— P0 优先**

| 方案 | 思路 | 效果 |
|------|------|------|
| 固定 top-K 截断 | RRF 后直接取前 20 | 候选从 40→20，延迟直接减半，零风险 |
| 自适应截断 | 根据 RRF 分数分布形状动态决定 K | 好查询截到 5 个，模糊查询保留全部 |
| 置信度门控 | RRF top-1 分数远超后续 → 直接跳过 CE | 高置信场景零 CE 成本 |

自适应截断的核心思路：固定截断用**位置**做决策，自适应截断用**信号的形状**做决策——检测 RRF 分数序列的衰减模式，如果第 5 位后出现断崖式下跌（相邻分数衰减率 > 阈值），在断崖处熔断；如果分数一路平缓下降，不截断，让 CE 全力精排。最小保留 5 个，最大保留原始候选数。

**方向二：降低单次推理延迟（砍左边）— P1**

| 方案 | 思路 | 延迟削减 | 代价 |
|------|------|----------|------|
| INT8 量化 + ONNX Runtime | 模型压缩 | ~20-35% | 需校准数据集，可能微掉点 |
| 换轻量 CE（MiniLM 6 层） | 更小的模型 | ~50% | 精度需验证 |
| 知识蒸馏 | 大 CE 教小 CE | ~50% | 训练成本高 |

**方向三：并行 / 流水线 — P2**

| 方案 | 思路 |
|------|------|
| CE 与 LLM 生成并行 | RRF 出结果后，一边跑 CE 精排，一边用未精排的 top-N 构建 prompt 预填充 KV cache |
| Batch CE | 多个 query 的候选合并成 batch 一次推理，利用 GPU 并行度 |

**回答收尾**：P0（砍候选）+ P1（量化）组合已经稳超 50%。自适应截断的阈值需要用生产数据持续校准，如果分布漂移导致截断率异常，回退到固定 top-K，保证 SLA 兜底。

### 追问 2：Bi-Encoder 二次过滤为什么是错的

**问题**：在 RRF 之后、CE 之前，能不能用 Bi-Encoder 的余弦相似度阈值再做一次过滤，减少 CE 候选量？

**答案：不行，这会破坏双路召回互补的前提假设。**

BM25 存在的价值恰恰是补充向量检索（Bi-Encoder）的语义盲区——专有名词、型号、代码片段等字面匹配强的内容，在 Bi-Encoder 眼里相似度天然偏低。用 Bi-Encoder 做阈值过滤，等于**用向量检索的偏见去否决 BM25 的贡献**——那些 BM25 辛辛苦苦捞上来、向量检索天然打低分的专有名词相关候选，会被 Bi-Encoder 阈值直接过滤掉。

结果：双路召回 → 又变回单路召回的瓶颈，而且多了一次模型推理，延迟不降反升，架构复杂度白增加。

**核心教训**：优化方案不能破坏上游模块存在的前提假设。正确的替代方案是直接基于 RRF 分数本身做截断，而不是引入一个新的评分模型。

### 追问 3：RRF 的 k 值怎么定

**问题**：经典默认 k=60，你是怎么定义这个值的？

**第一步：k 控制的是排名曲线的"陡峭度"**

| k 值 | rank=1 权重 | rank=N 权重 | 效果 |
|------|-----------|------------|------|
| k→0 | 极大 | 极小 | 只有 top-1 说了算 |
| k→∞ | 均等 | 均等 | 排名信号完全抹平 |
| k=60 | 适中 | 适中 | 头部有优势但不独裁 |

**第二步：60 没有理论推导。** 它是 Cormack 等人在 2009 年 TREC 数据集上网格搜索扫出来的经验值。换个数据集、换个候选规模，60 未必最优。

**第三步：正确的设置方式——k 与候选规模绑定。** 先确定期望的权重比（rank=1 与 rank=N 的权重比 r），再反推 k：

$$k = \frac{N - r}{r - 1}$$

以本项目为例：RRF 输入候选池 N=40（BM25 top-20 + Vector top-20），期望 rank=1 权重是 rank=40 的约 3 倍，代入得 k = (40-3)/(3-1) = 18.5。在验证集上以 MRR 为目标扫 k ∈ [10, 50]，实验最优 k=30。

**结论**：k 不是 magic number，是"你允许多少权重比"的数学表达。

⚠️ **关于"系统对 k 不敏感"这句话要谨慎**：那是早期极小语料（3 个 Chunk）下的结论——所有配置都满分，等于没测出区分度。在新语料（1445 Chunk、18 条）上我还没重跑参数扫描，**面试时应该这么说**："旧结论来自极小语料、可信度低；当前沿用 k=60 这个行业默认值，参数敏感性扫描在新语料上待复验。"——主动指出自己旧结论的局限，比被面试官挖出来强。

### 追问 4：BM25 vs 向量，各自在什么情况下更强

**整体数据（18 条 Golden Test Set，语料 1445 Chunk）**

| 阶段 | MRR | Hit@5 |
|------|-----|-------|
| BM25 | 0.5469 | 88.9% |
| Vector | 0.7246 | 83.3% |
| RRF 融合 | 0.7833 | 94.4% |
| 全管线（+CE） | **0.7889** | **100%** |

但**整体数字会骗人**——BM25 的 0.547 明显弱于 Vector 的 0.725，很容易判它"多余"。拆到单条才是真相：

| 单条 case | 查询（→答案） | BM25 MRR | Vector MRR | 说明 |
|---|---|---|---|---|
| **S04** | 请求前后插入通用逻辑（→中间件） | **0.0000** | **1.0000** | 字面完全不含"中间件"，BM25 无能为力 |
| **S02** | 启动执行一次、关闭收尾（→lifespan） | 0.5000 | **0.0000** | **反向**：这次是 Vector 漏了 |
| **S06** | 配置放代码外、运行时读取（→settings） | 0.2000 | **0.0000** | 同上 |
| M08 | FastAPI 怎么做测试？ | 0.1111 | 0.5000 | 语义改写类，Vector 强 |

**BM25 的优势**：专有名词和精确术语匹配。query 中的关键词在文档中原文出现时（如"路径操作装饰器"），BM25 精准命中。

**向量检索的优势**：自然语言语义查询。S04 是最典型的一条——query 里没有一个字提到"中间件"，BM25 完全失效（MRR 0.0000），Vector 满分命中。

**必须承认的一面**：融合不是万能的，**RRF 也可能反而丢东西**——S06 在 RRF 阶段 Hit@5 从 1 掉到 0（BM25 捞到了，融合后反而被挤掉），最后只有 CE 把它救回来。这也是"为什么不能省掉精排"最硬的证据。

**怎么调两路权重**：答案是没有调，刻意不调。BM25 原始分数范围 0~几十，向量余弦相似度 0~1，直接加权融合 BM25 会靠量纲优势主导排序。采用的方案是 RRF 而非加权融合——只用排名位置，不用原始分数，天然消除量纲差异。核心结论：BM25 和向量检索的权不是"调"出来的，而是通过架构选择（RRF + CE）让它们各自在自己的优势区发挥作用。

### 追问 5：GoldenTestSet 构建 + 改写评测

**问题**：你的 GoldenTestSet 是如何构建的？怎么判断改写后的查询是"变好了"还是"变差了"？

**第一问：GoldenTestSet 如何构建**

现在是 **18 条**，手动构建，按检索难度分四类（不再是早期的"三类各 5 条"）：

| 类别 | 条数 | 设计意图 | 示例 |
|------|------|----------|------|
| exact_match（E） | 4 | 专有名词精确匹配，测 BM25 优势 | "路径操作装饰器" |
| semantic（S） | 4 | 口语化语义查询，字面不匹配，测向量 | "应用启动只想执行一次初始化、关闭时收尾，该用什么机制？"（→lifespan） |
| mixed（M） | 4 | 综合多段信息，测全链路 | "FastAPI 应用怎么做测试？" |
| graph（G） | 6 | 需要把多个概念串起来 | "SQLModel 与 SQLAlchemy、Pydantic 是什么关系？" |

每条用例含四个字段：`query`、`golden_chunk_sources`（文档级来源）、`golden_answer`（参考答案）、`notes`（测试意图说明）。**每条 `golden_answer` 都能在 `golden_chunk_sources` 指定的文件正文里回查到原文**，由 `scripts/validate_golden.py` 自动校验——防止标注漂移。

**另外还有两套验收集**（这是容易被忽略但很加分的点）：
- **10 条拒答集**（`unanswerable_queries.json`）：near_miss / out_of_domain 等，测"该不该说不知道"
- **3 条多证据集**（`multi_evidence_queries.json`）：每题需跨 2 篇文档才能答全，测引用覆盖率

**为什么不拆 train/test？** 拆分原本是为"用 CE 分数卡阈值做自动拒答"那个方案服务的，而那方案被我自己的数据证伪了（能答与不能答的分数分布严重重叠），方案废弃后拆分就失去了意义，所以收敛为单一测试集。**这个回答能展示"我会根据证据推翻自己的设计"**，比堆概念有用。

**为什么手动而非自动生成？** 人知道每一组 query 在测哪个模块的哪个能力（E02 测 BM25 对术语的敏感度，S04 测向量对完全不重合字面的语义理解）。自动生成做不到这种分层覆盖的意图设计。

**第二问：怎么判断改写后变好还是变差**

核心思路是 A/B 对比——对每组 test case 分别用原始 query 和改写 query 走全链路检索，计算 Δ = 改写后 MRR - 改写前 MRR。Δ > 0 → 改写有效，Δ < 0 → 改写退化。

同时做语义保真度检查：改写可能提升 MRR 但跑偏意图。用 LLM-as-Judge 判断"改写后的查询是否保留了原始的信息需求"，输出 fidelity_score 0~1。

再加 CE 阈值校准：最初阈值是拍脑袋定的，所以用"改写是否实际提升了 MRR"作为 ground truth，扫阈值找 F1 最优点。

⚠️ **这里有个我自己踩过并修掉的坑，很适合当谈资**：校准代码原本硬编码扫描区间 `1.0~6.0`——那是给旧英文 `ms-marco` 模型（输出无界 logits）设计的。换成 `bge-reranker-base`（sigmoid 输出 [0,1]）后**忘了改**，后果是所有 [0,1] 的分数都恒小于 1.0，每个阈值都判定"全部需要改写"，F1 恒定不变——**校准等于空跑，而且不会报错**。现在的做法是**按本次实测分数的 min/max 自适应扫描**，换任何模型都不会再静默失效。

另外要讲清楚：这个阈值**只决定"要不要改写重试"，不决定"要不要拒答"**。拒答交给生成阶段的 LLM 判断。

### 追问 8：TOP_K 为什么是固定值

**问题**：你的 BM25 TOP_K=20、CE TOP_K=5 都是写死的。如果遇到一个查询质量很高（CE 第 1 名和第 2 名之间分数断崖），或者一个模糊查询（分数一路平缓、没有明显断点），固定 K 会分别造成返回冗余和返回不足——怎么应对？

**核心思路：把"固定 K"变成"自适应截断"——和 CE 延迟优化里的自适应截断用同一个模式。**

> "固定 TOP_K 的问题是不管查询质量如何，返回相同数量的结果。解决方案是在 Cross-Encoder 分数序列上检测相邻候选的降幅——分数断层处就是自然截止点。"

```
自适应 TOP_K:
  1. 跑 CE，得到分数序列 [0.82, 0.78, 0.61, 0.05, 0.02]   # bge-reranker 输出 [0,1]
  2. 遍历相邻分数的降幅比例: drop = (score[i] - score[i+1]) / score[i]
     rank 2→3 降 22%, rank 3→4 降 92% ← 断崖！
  3. 在第 3 个位置截断，返回 3 个结果而不是强制性 5 个
```

**三种情况的行为**：
| 查询类型 | CE 分数分布 | 自适应截断行为 |
|----------|------------|---------------|
| 高质量查询 | [0.91, 0.88, 0.02, ...] | 在断崖处截断，返回 2 个而不是 5 个 |
| 模糊查询 | [0.42, 0.39, 0.35, 0.31, 0.28] | 分数平缓下降，保留全部 5 个给 LLM 判断 |
| 普通查询 | [0.75, 0.68, 0.41, 0.39, 0.37] | 中间有自然断点，返回 3 个 |

> 本项目实际已实现了一个简化版：**相对阈值过滤**（`CE_RELATIVE_THRESHOLD=0.2`）——
> 低于 Top-1 分数 20% 的候选直接丢弃。动机是 bge-reranker 下正解与噪声能差三个数量级
> （实测 0.699 vs 0.0007），硬取 Top-5 会把明显无关的 chunk 塞进生成上下文。

**回答收尾**：「这和 CE 延迟优化里的自适应截断是同一个模式——不靠位置做决策，而是靠信号的形状做决策。区别只在于应用位置：延迟优化时从 RRF 分数上截断（省 CE 计算），这里从 CE 分数上截断（决定给下游多少信息）。最小保留数保证至少返回若干候选，比例阈值控制敏感度。分布漂移时回退到固定 K。」

**追问："为什么不把这个逻辑写进代码里？"**

> "我已经实现了一个简化版：**相对阈值过滤**——低于 Top-1 分数 20% 的候选直接丢弃。实测 bge-reranker 下正解和噪声能差三个数量级（0.699 vs 0.0007），所以这个简单规则在大多数情况下已经够用。
>
> 完整的自适应截断我**还没上**，原因是 18 条测试集的样本量还不足以可靠地校准断崖阈值——在小样本上调出来的参数，换个语料大概率要重调。现在语料规模已经上来了（1445 Chunk），等把生成侧评测跑完、有了更稳定的指标基线，再回来做这个参数才有意义。**先把能证伪的部分做完，再上需要调参的优化**——这是我给自己定的顺序。"
