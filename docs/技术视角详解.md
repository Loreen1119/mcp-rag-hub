# MCP-RAG-Hub —— 技术视角全览

> 文中所有模型名、超参数、指标基线以 `config.py` 与 `experiments/*.json` 为准。
> 指标基线为 2026-09-12 语料迁移至 `corpora/fastapi-zh` 后的当前值；语料一换，旧基线全部失效。

## 项目定位

一个**从底层原理出发、全手工实现的 RAG 知识检索系统**，覆盖文档解析、Token 级滑动窗口切块、BM25+向量双路检索、RRF 融合、Cross-Encoder 重排序、LangGraph 代理编排、FastMCP 工具封装、以及完整评测体系的端到端管线。知识图谱作为可选实验功能（`ENABLE_KG` 开关）默认关闭。所有环节不依赖框架高级封装，每个步骤的实现均可见、可调试、可复现。

系统围绕「教学可演示 + 实验可验证 + 组件可复用」三条设计主线构建，支持通过 Streamlit 网页、MCP 协议、和 LangGraph 代理三种方式交互。

**知识库语料**：索引对象是 `corpora/<语料名>/`，与项目自身文档分离（`PROJECT_ROOT/docs/` 是人读的，不参与索引）。

| 语料 | 内容 | 规模 | 许可 | 状态 |
|------|------|------|------|------|
| `fastapi-zh`（默认） | FastAPI 中文文档 | 122 篇 / 677KB / 1445 chunk | MIT | 索引 + 三套验收集齐备 |
| `vue-zh` | Vue 3 官方中文文档 | 110 篇 / 941KB / 1804 chunk | CC BY 4.0 | 语料已落地，**索引与验收集待建** |

用环境变量 `MCP_RAG_CORPUS` 切换；每份语料使用独立的 Chroma 集合（命名 `kb__{corpus}__{model}__v{schema}`），互不覆盖。

## 一、解决的工程问题

RAG 系统的核心挑战不在于「能跑」，而在于**每个环节的可靠性和可解释性**：

- **文档切块的粒度控制**：切太细则语义不完整，切太粗则检索精度下降。需要 token 级别的精确控制，而非简单的字符计数。
- **单一检索方式的盲区**：BM25 依赖词频匹配，对同义词、改写、跨语言场景无效。向量检索捕捉语义但可能丢失专有名词精确匹配。单用一种必然有盲区。
- **多路检索结果的融合**：BM25 和向量检索的评分分布（量纲和尺度）完全不同，不能直接线性加权。需要一种与评分尺度无关的融合策略。
- **检索质量的自我感知**：一个简单的 RAG 管线不管检出质量好坏都直接生成回答。需要一个能感知检索质量、在质量不足时主动调整策略的代理机制。
- **效果验证的闭环**：改了一个参数或换了一个模型后，如何量化地知道效果是变好还是变差？需要一套系统的评测和消融实验框架。
- **「不知道」也要能说清楚**：检索不到时不能含糊地回一句"没找到"——系统要能区分「知识库里确实没有」（正确拒答）、「生成服务挂了」（技术故障）、「输出不合法」（解析失败），三者的处置方式完全不同。

## 二、系统架构

整体分为**离线索引管线**和**在线检索服务**两大部分，中间通过 ChromaDB 持久化向量存储和内存级 BM25 索引连接。

### 离线管线（文档 → 可检索索引）

```
corpora/<语料名>/ 下的 PDF / Markdown / TXT / Python 文档
        │
        ▼
  文档加载器（pdfplumber + 编码自检测）
        │
        ▼
  Token 级滑动窗口切块（tiktoken cl100k_base，256 / overlap 38）
  + Markdown 标题面包屑提取（栈式层级解析）
  + Python AST 语义分块
        │
        ▼
  Chunk 数据类（text + metadata + heading_breadcrumb）
  chunk_id = sha256(相对语料根路径 : 序号)[:16]
        │
        ├──────────────────────────┐
        ▼                          ▼
  BM25 索引构建              向量嵌入计算
  (rank_bm25 + jieba)       (BAAI/bge-small-zh-v1.5, 512 维)
        │                          │
        │                          ▼
        │                   ChromaDB 持久化
        │                   (HNSW 索引, cosine 距离)
        │                   集合按 语料+模型+schema 命名
        └──────────┬───────────────┘
                   ▼
              检索准备就绪
```

### 在线检索（问题 → 排序结果）

```
用户输入问题
        │
        ├──────────────────────────┐
        ▼                          ▼
  BM25 关键词检索            向量语义检索
  (jieba 分词 + BM25)       (query embedding + ChromaDB query)
        │                          │
        │  各自取 Top-20            │
        │                          │
        └──────────┬───────────────┘
                   ▼
           RRF 倒数排名融合
           (rank-based, K=60)
                   │
                   ▼
    Cross-Encoder 精排（BAAI/bge-reranker-base）
    (query-document 联合编码 → sigmoid 打分 → Top-5)
    + 相对阈值过滤（低于 Top-1 分数 20% 的丢弃）
                   │
                   ▼
              最终排序结果
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   Streamlit    MCP        LangGraph
   可视化界面   工具接口    代理问答
```

### 代理状态机（LangGraph）

LangGraph 编译的声明式状态机，五个节点 + 条件边：

```
START → analyze_query  →  retrieve  →  check_results
                             ▲              │
                             │              ├── CE Top-1 ≥ 0.3 → generate_answer → END
                             │              │
                             │              └── CE Top-1 < 0.3 且 attempt < 2 → rewrite_query ──┘
                             │                                        (最多循环 2 次)
                             └────────────────────────────────────────┘
```

状态通过 TypedDict 在全图中传递，包含 query 的各阶段变体（原始、改写）、检索结果、重试计数、和最终回答。条件路由以 Cross-Encoder 最高得分与阈值 `CE_THRESHOLD=0.3` 的比较作为分支判断依据。

> **注意阈值的量纲**：`0.3` 是 `bge-reranker-base` 经 sigmoid 后 [0,1] 区间下的值。早期用英文 `ms-marco-MiniLM` 时输出是无界 logits，阈值是 `3.0`——换模型后阈值必须跟着换，否则永远判定为"质量不足"。

## 三、数据管线详解

### 文档加载与编码检测

加载器支持五类后缀（`.pdf` / `.md` / `.markdown` / `.txt` / `.py`），每种有独立的提取路径：

- **PDF**：使用 `pdfplumber` 逐页提取，不处理表格与图片
- **Markdown**：用正则剥离标记语法取纯文本，同时运行栈式标题层级解析器构建 heading breadcrumb
- **纯文本**：做编码自检测（UTF-8 / GBK / GB2312）
- **Python**：额外使用 `ast` 做语义分块，优先按 AST 节点组织

### Token 级滑动窗口切块

这是整条管线中最重要的基础环节。切块质量直接决定检索质量的上界。

**为什么用 token 而非字符数？**
sentence-transformers 模型的输入是按 token 计数的。中文字符和英文单词的 token 化比例差异巨大（一个汉字可能 1-2 token，一个英文单词可能 2-5 token）。用字符数做窗口控制，实际上每个块的「模型可见信息量」波动很大。用 tiktoken 的 cl100k_base 编码器精确计数 token，保证每个块在模型视角下大小一致。

**滑动窗口重叠**：`chunk_size=256 tokens, overlap=38 tokens`（约 15%，行业推荐 10%~20% 区间），与 embedding 模型的有效编码窗口对齐。

**句子边界感知**：普通文本按 token 滑窗切分；Markdown 先保留标题 breadcrumb；Python 文件优先按 AST 节点组织语义块。

### Markdown 标题面包屑

栈式算法维护当前章节路径：遇到一级标题清空栈并压入新标题；遇到二级标题弹出栈中同级及更低级标题后压入；依此类推。每个切好的 chunk 继承切分点当时的完整栈状态，格式化为「一级标题 > 二级标题 > 三级标题」的面包屑字符串。纯文本和 PDF 文档此字段为空。

### 双重索引构建

**BM25 索引**：以 jieba 分词器的 `lcut` 模式对所有 chunk 做中文分词。使用 `rank_bm25` 库的 BM25Okapi 实现，默认参数（k1=1.5, b=0.75）。索引在内存中维护，服务启动时构建。

**向量索引**：使用 `BAAI/bge-small-zh-v1.5`（512 维，~95MB）逐个对 chunk 编码。中文知识库必须用中文/多语言 embedding——早期用纯英文的 `all-MiniLM-L6-v2` 时，中文相似度全部挤在 0.24~0.37 的窄区间、毫无区分度，实测会把无关文档排到正确 chunk 前面（正确 chunk 只排第 10）。编码过程是显式调用 `model.encode()` 逐条完成的，而非使用 ChromaDB 的自动 embedding 函数——这样做是为了完全掌控向量计算过程，便于调试和替换模型。编码后的向量连同元数据存入 ChromaDB 持久化集合，底层使用 HNSW 图索引 + cosine 距离度量。

## 四、检索与融合管线

### BM25 检索

```python
tokenized_query = jieba.lcut(query)
bm25_scores = bm25_index.get_scores(tokenized_query)
top_k_indices = np.argsort(bm25_scores)[::-1][:20]
```

关键细节：BM25 的评分是**无界的**（取决于文档长度、词频等因素，通常在 0-50 区间）。这意味着 BM25 的分数不能直接和余弦相似度做线性组合。

### 向量检索

查询文本以相同方式编码为 512 维向量，然后调用 ChromaDB 的 `collection.query(query_embeddings=[...], n_results=20)`。返回的 distance 值通过 `1 - distance` 转换为相似度（因为 ChromaDB 使用 cosine distance，范围 [0, 2]，其中 0 表示完全相同）。

### RRF 倒数排名融合

这是解决「两种检索方式评分不可比」问题的关键设计。

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 个排名列表中的位置（从 1 开始），k 是平滑常数（默认 60）。

**为什么 k=60？**
k 值越大，排名靠后的文档的权重衰减越平缓。k=60 是一个经验上的平衡点：
- k 过小（如 k=1）：第一名和第二名的差距过大（1 和 0.5），过于强调各自的第一名，融合效果接近「各自取 Top-1」
- k 过大（如 k=200）：所有排名位置的分数趋同，融合退化为「投票制」——只要在两个列表中都出现就差不多，失去了排名的精细区分
- k=60 在保留排名区分度的同时，避免极端权重集中

RRF 的核心优势是与评分尺度无关——无论原始分数是什么量纲，只使用相对排名信息。

### Cross-Encoder 重排序

这是检索质量的最后一道提升。与 Bi-Encoder（分别编码 query 和 document 再计算相似度）不同，Cross-Encoder 将 query 和 document 拼接后**联合编码**，使注意力机制能在 query 和 document token 之间自由流动，从而捕捉到细粒度的语义匹配关系。

模型选择 `BAAI/bge-reranker-base`（~1.1GB，中文优化），输出经 sigmoid 归一到 [0, 1]。早期用的是英文 `cross-encoder/ms-marco-MiniLM-L-6-v2`，输出是无界 logits——换模型的直接后果是**所有分数相关的阈值都要重标**：质量门控阈值从 3.0 降到 0.3。

重排后还有一道**相对阈值过滤**：低于 Top-1 分数 20%（`CE_RELATIVE_THRESHOLD=0.2`）的候选直接丢弃。动机是 bge-reranker 下正解与噪声的分数差可达三个数量级（实测 0.699 vs 0.0007），硬取 Top-5 会把明显无关的 chunk 塞进生成上下文。

**为什么只在 Top-20 上做 CE？**
Cross-Encoder 要为每个候选做一次完整的联合编码推理，代价比向量检索高一到两个数量级（实测：一次精排约 373 ms，一次向量检索约 21 ms）。在 1445 条 chunk 上全部跑 CE 会导致数秒的延迟。策略是：Bi-Encoder 做粗筛（召回率优先，Top-20），Cross-Encoder 做精排（精确率优先，Top-5）。这是检索系统中经典的两阶段排序范式。

## 五、LangGraph 代理设计

### 节点职责

**analyze_query**：清理并记录原始查询，初始化 attempt、历史记录和日志，不调用 LLM 做额外意图分析。

**retrieve**：将 `query`（或 rewrite_query 产出的变体）送入完整的检索+融合+精排管线，产出带有 CE 分数的 Top-5 结果列表。

**check_results**：检查 Top-1 CE 分数是否达到配置阈值 `CE_THRESHOLD=0.3`。达到或已到最大 2 次尝试就生成答案，否则路由到 `rewrite_query`。

> 这个阈值**只用于决定是否改写重试**，不用于拒答。历史教训：曾尝试用 CE 分数做"能不能回答"的门控，实测被证伪——能答与不能答的问题分数分布严重重叠，卡任何一条线都是赌。现在拒答完全交给生成阶段的 LLM 判断。

**rewrite_query**：调用本地 Ollama 改写查询；不可用时使用规则式追加关键词。改写文本写入 `query`，并追加到 `rewritten_queries`，随后回到 `retrieve`。

**generate_answer**：取 Top-3（`ANSWER_TOP_K`）检索结果的文本拼接为上下文，连同原始 query 送入 LLM，生成带引用的自然语言回答，每个事实主张后标注来源编号。

生成阶段有三态输出，前端分开展示：

| 状态 | 含义 | 用户看到什么 |
|------|------|-------------|
| `ok` | 正常生成 | 带 `[1][2][3]` 引用的答案 + 证据卡片（被引用的卡标记「已引用」） |
| `insufficient_evidence` | 知识库确实没有 | 「知识库信息不足，未生成答案」——**这是正确的拒答** |
| `generation_unavailable` | 本地 LLM 服务不可用 | 「回答生成服务暂不可用」+ 检索到的原文拼接，不让人空手而归 |
| 解析失败 | 输出格式不合法 | 「回答处理出错」——技术故障，与业务判断区分开 |

### 节点间状态传递

状态为 TypedDict，字段包括：

| 字段 | 类型 | 说明 |
|------|------|------|
| `original_query` | str | 用户原始输入，全程不变 |
| `query` | str | 当前生效的原始或改写查询 |
| `last_retrieved_chunks` | list[dict] | 最近一次检索结果 |
| `retrieval_history` | list[dict] | 各轮检索观测记录 |
| `rewritten_queries` | list[str] | 已尝试的改写查询 |
| `search_log` | list[str] | 逐节点的执行日志（前端直接展示） |
| `attempt` | int | 当前检索尝试次数 |
| `answer` | str | 最终答案 |

### 降级策略

LLM 调用全部有 fallback：
- `rewrite_query` 失败 → 使用规则改写（追加同义表达、拆分短句）
- `generate_answer` 失败（服务未起 / 超时）→ 降级为 BM25 原文拼接，状态标 `generation_unavailable`
- 整个 LangGraph 图执行异常 → 返回静态错误消息

所有 LLM 调用带超时（`LLM_TIMEOUT_SECONDS=120`，纯 CPU 推理 3b 出 300 字约 15~25 秒，20 秒必然超时）与一次重试（仅针对连接失败/超时，JSON 解析失败不重试），并按错误类型分类上报。

## 六、MCP 工具封装

基于 FastMCP 2.0，通过 stdio 传输协议暴露四个工具。MCP 客户端（如 Claude Desktop 或其他 MCP Host）可以通过标准输入输出流调用这些工具。

| 工具名 | 参数 | 返回 | 实现要点 |
|--------|------|------|---------|
| `search_knowledge` | query: str, top_k: int = 5 | 包含文本、来源、CE 分数的检索结果列表 | 走完整检索+融合+精排管线 |
| `list_documents` | 无 | 知识库中所有文档的文件名和块数 | 从已加载的文档名集合中汇总 |
| `get_chunk` | chunk_id: str | 指定块的完整文本和元数据 | 按 16 位确定性 chunk_id 查内存 chunks |
| `get_chunk_count` | 无 | 知识库总块数 | 返回内存权威 chunks 的长度 |

工具返回类型按职责分别是 `list[dict]`、`dict | None` 或 `int`；当前代码没有统一的 `success/data/error` 包装，也没有在工具层统一吞掉异常。

### 共享管线生命周期

MCP 不再独立创建 `process_directory`、BM25、Vector 和 Fusion 对象，而是通过 `src.pipeline.get_pipeline()` 获取 `PipelineContext`。该模块使用参数签名绑定的进程内单例和 `threading.Lock` 双重检查，统一服务 MCP、Agent、Streamlit 和评测入口。向量索引按 corpus hash 与 schema version 命名；摘要匹配时复用 Chroma collection，语料或切片参数变化时创建新 collection。

### KG 三元组缓存与 sidecar 校验

知识图谱三元组保存在 `knowledge_triples.jsonl`，其配套的 sidecar（旁车）文件 `knowledge_triples.jsonl.meta` 保存构建信息：`docs_dir`、`chunk_size`、`chunk_overlap`、`chunk_id_rule_version`、`corpus_hash` 与 `meta_version`。sidecar 不保存三元组本身，而是用于判断主缓存能否安全复用。

复用前，代码依次确认：JSONL 主文件存在；sidecar 存在且可解析；sidecar 中的 `meta_version`、`chunk_id_rule_version` 和 `corpus_hash` 与当前运行配置一致。`chunk_size` 与 `chunk_overlap` 也记录在 sidecar 中用于诊断，但它们已参与 `corpus_hash` 计算，所以参数变化会通过 hash 不匹配触发全量重建。

不能只检查 `chunk_id`：当前 ID 由相对路径和切片序号确定，同一位置的文本内容被修改后 ID 仍可能相同。只有 corpus hash 才能检测整套文档内容或切片配置是否变化。重建时先把结果写到临时 JSONL，成功后用原子替换更新正式文件，最后才更新 sidecar，避免中途失败留下被误认为有效的半成品缓存。

### 三套验收集

| 集合 | 文件 | 条数 | 用途 |
|------|------|------|------|
| 可答 golden | `data/test_queries.json` | 18（E4 / S4 / M4 / G6） | 检索指标分层归因 |
| 拒答 | `data/unanswerable_queries.json` | 10 | 端到端拒答率 / 幻觉率 |
| 多证据 | `data/multi_evidence_queries.json` | 3 | 跨文档引用覆盖率 |

每条 golden 的 `golden_answer` 都能在 `golden_chunk_sources` 指定的文件正文里回查到原文依据，由 `python scripts/validate_golden.py` 统一校验（当前 0 问题）。

> **不做 train/test 拆分**。拆分原本是为「用 CE 分数卡阈值自动拒答」那个方案服务的，而那套方案经实测被证伪、已废弃（见 `docs/开发过程中遇到的问题.md`），拆分随之失去意义，2026-09-12 起收敛为单一 golden set。

### 检索层指标

全部自实现，不依赖外部评测库：

- **MRR**（Mean Reciprocal Rank）：第一个正确答案的平均倒数排名。MRR=1.0 表示所有查询的第一个正确答案都排在第一位
- **Hit@K**：正确答案出现在前 K 个结果中的查询占比
- **Precision@K**：前 K 个结果中正确答案的占比
- **Recall@K**：所有正确答案中有多少出现在前 K 个结果中

### 当前基线（18 条，2026-09-12，语料 `corpora/fastapi-zh`）

| 阶段 | MRR@5 | Hit@5 | Prec@5 | Recall@5 |
|------|-------|-------|--------|----------|
| BM25 | 0.5469 | 0.8889 | 0.4333 | 0.8889 |
| Vector | 0.7246 | 0.8333 | 0.3889 | 0.8333 |
| RRF 融合 | 0.7833 | 0.9444 | 0.5000 | 0.9444 |
| **CE 精排（全管线）** | **0.7889** | **1.0000** | **0.5444** | **1.0000** |

**怎么读这张表：**

- **两路的失败集合几乎不重叠**：向量把 S04 从 MRR 0.000 拉到 1.000，BM25 则在 Vector 掉到 0.000 的 S02/S06 上仍有召回——这是"混合召回"最硬的证据
- **RRF 补短板，不加上限**：单路 Hit@5 88.9% / 83.3% → 融合 94.4%，它是唯一把两路各自漏掉的单条同时补回的环节
- **CE 的价值在 Hit@5，不在 MRR**：Hit@5 补到 **100%**，但净 MRR 只 +0.006（救回 E02，也把 G08/M04 从 1.0 挪到 0.25）——精排的定位是"兜底 + 排序"，不是"提分"

### 消融实验框架

`experiments.py` 的 `run_module_ablation` 跑 7 种固定配置（不是 2^n 全组合）：`bm25_only` / `vector_only` / `graph_only` / `concat_naive` / `rrf_fusion` / `full_pipeline` / `triple_fusion`，每种在全部 18 条查询上出 MRR / Hit@5 / Prec@5 / Recall@5 与相邻配置的 delta。

这样切的关键对照是：`concat_naive`（直接把两路结果拼起来去重）vs `rrf_fusion`（按排名融合）——用来证明"融合策略本身有讲究，不是把两路结果堆一起就行"。另有 `run_category_breakdown`（按 E/S/M/G 四类分解）、`run_parameter_sweep`（RRF_K / CE_TOP_K 网格扫描）、`run_latency_profile`、`run_query_deep_dive`（单条查询的逐阶段追踪）。

### LLM-as-Judge 评测

**自实现**，指标定义对齐 Ragas 的三项（Ragas 框架本身在 Windows SSL 层不兼容，故不用）：

- **Faithfulness（忠实度）**：将回答拆分为原子陈述，逐条验证是否能从检索上下文中推断出来。得分为「可验证陈述数 / 总陈述数」
- **Answer Relevancy（回答相关性）**：反向生成问题——从回答中生成若干问题，看这些问题与原始 query 的语义相似度
- **Context Recall（上下文召回率）**：标准答案中的每个句子是否都能在检索上下文中找到对应

**生成与裁判解耦**：生成用 `qwen2.5:3b`（与生产链路一致，CPU 可跑），裁判用 `qwen2.5:7b`。原因是裁判比生成更需要模型能力——3b 当裁判会给出自相矛盾的判词（同一句话里说「大部分信息来自上下文」却按「大量编造」档打 0.10 分），无区分度。

**当前状态**：⚠️ `experiments/llm_evaluation_results.json` 里只有一次**旧语料、3 条、3b 自评**的快跑（F=0.60 / AR=0.50 / CR=0.50，单条生成 14.6~43.8 秒）。**新语料 + 7b 裁判的完整跑还没做**——也就是说，项目目前只有"检索准"的证据，还没有一条可信的"回答质量好"的证据。

### 代理评测

`agent_eval.py` 三个任务：
- 改写增益：改写后 query 相对原始 query 的检索指标 delta
- 语义保真度：LLM 判断改写是否保留了原始信息需求（防改写漂移）
- CE 阈值校准：扫阈值找最能预测"改写是否有效"的取值

> ⚠️ 校准的扫描区间目前仍是 `1.0~6.0`（为旧 `ms-marco` 的无界 logits 设计的），而 `bge-reranker-base` 输出在 [0,1]——**这段代码沿用旧量纲，换模型后没跟着改**，校准结果不可用。

## 八、关键设计决策

### 为什么不使用 LangChain/LlamaIndex 的高级抽象？

LangChain 的 `RecursiveCharacterTextSplitter`、`VectorStoreRetriever`、`EnsembleRetriever` 等封装确实可以减少代码量。但封装层隐藏了内部细节——token 计数方式、embedding 调用时机、融合的具体算法——这些正是这个项目想要展示和理解的东西。

所有组件从底层实现：切块逻辑手写、embedding 计算手动批处理、融合算法直接实现、评测指标从 numpy 基础运算构建。每条线都是透明的。

### 为什么不使用 Cohere/OpenAI 的 Embedding API？

使用本地模型（`BAAI/bge-small-zh-v1.5`）而不是 API 的三点考虑：
1. **零成本**：无 API 调用费用，实验可以无限次运行
2. **离线可用**：不依赖外部网络，任何机器都能跑
3. **结果可复现**：本地模型的输出是确定性的，而商业 API 可能在后台更新模型版本导致同输入不同输出

512 维向量在几千个 chunk 的规模下完全够用，不需要 1024 或 1536 维的高维嵌入。

### 为什么用 ChromaDB 而不是 FAISS 或 Qdrant？

- **ChromaDB**：开箱即用的持久化，Python 原生集成，无需单独部署服务，对开发体验最友好
- FAISS 的检索性能更强但持久化需要额外工作，Qdrant 需要独立服务进程
- 在当前文档规模（千级 chunk）下，ChromaDB 的 HNSW 索引性能完全够用

### 为什么用 jieba 分词而不是直接用字级别的 BM25？

中文不像英文有天然的空格分隔。如果对中文做字级别的 token 化，「机器学习」会变成「机」「器」「学」「习」四个独立 token，BM25 的倒排索引无法识别它们作为一个整体词组的匹配价值。jieba 将中文文本正确切分为有意义的词组，使 BM25 在中文上的检索质量从字符匹配提升到了词汇匹配。

### 为什么生成用 3b、裁判用 7b？

本机 GPU 是 Intel UHD 集显、无 CUDA，只能纯 CPU 推理：`qwen2.5:7b` 权重 4.36 GB，加载需 5.0~5.5 GB，开发环境全开时必然 OOM，且 2~4 tok/s 下 300 字答案要 50~100 秒，演示不可用；`qwen2.5:3b` 权重 1.80 GB，总占 2.4~2.8 GB，8~15 tok/s，15~25 秒出答案。生成任务是"给 3 条证据做抽取归纳 + 标引用 + 输 JSON"的窄任务，3b 够用；裁判需要逐句比对并分档打分，是 3b 做不到的活，只能在跑评测时才加载 7b。

## 十、工程要点总结

**每个环节的「为什么」都有一个答案：**

| 设计决策 | 原因 |
|---------|------|
| Token 级而非字符级切块 | 中英文 token 化比例差异大，token 计数保证模型视角下块大小一致 |
| 滑动窗口重叠 38 token（约 15%） | 防止关键句被切在两块中间；15% 落在行业推荐 10%~20% 区间 |
| 双路检索各自独立 | BM25 和向量的失效模式正交——前者怕同义词改写，后者怕专有名词模糊 |
| RRF 而非分数线性加权 | 两种检索方式的评分量纲不同（BM25 无上界，向量在 [0,1]），直接加权无意义 |
| CE 仅在 Top-20 上运行 | 性能取舍：一次精排约 373ms vs 一次向量检索约 21ms，两阶段排序是行业标准策略 |
| CE 后再加相对阈值过滤 | bge-reranker 下正解与噪声差三个数量级（0.699 vs 0.0007），硬取 Top-5 会引入噪声 |
| 代理自省节点 | 避免在检索质量差时强行生成幻觉答案，改写重试的性价比远高于硬编 |
| 拒答交给 LLM 判断，不用分数门控 | 实测能答与不能答的 CE 分数分布严重重叠，卡阈值是赌，方案已废弃 |
| 三态降级（拒答 / 服务不可用 / 解析失败） | 让用户分清「知识库里没有」和「服务坏了」，两者的处置方式完全不同 |
| 所有 LLM 调用有 fallback + 超时 | 本地模型可能不可用（OOM、未启动等），规则降级保证系统永不崩溃 |
| 评测指标全部自实现 | 透明度和可控性优先于便利性——知道每个数字是怎么算出来的 |
| 评测覆盖四类查询 | 确保系统在术语精确匹配、语义泛化、混合、多跳关联场景下都经过验证 |
| LLM-as-Judge 三道把关 | 忠实度防幻觉、相关性防偏题、召回率防遗漏——三道互补覆盖回答质量全貌 |

这个项目的架构理念是：**每一层都暴露，每一步都可测，每一个组件都可替换**。它不是最快的 RAG、不是最强的 RAG、但它是每个环节都能被完整理解和独立验证的 RAG。
