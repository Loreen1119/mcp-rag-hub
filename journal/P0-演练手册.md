## 1. 内存预算（2026-09-13 23:00 实测）

| 指标 | 实测值 |
|---|---|
| 物理内存 | 总 15.71 GB / **可用 2.14 GB** |
| 提交量（Commit） | 上限 31.43 GB / 已用 25.80 GB / **剩余 5.63 GB** |

> Ollama 的判断依据是**物理可用内存**（报错原文：`model requires more system memory (5.6 GiB) than is available (3.0 GiB)`）。

| 要跑的东西 | 需要物理可用 | 现在够吗 | 怎么办 |
|---|---|---|---|
| **3b（生成 / 演示）** | ≳ 2.5 GB | ⚠️ 卡线 | 关掉 QQ（-1.1 GB）→ 约 3.2 GB ✅ |
| **7b（裁判 / 评测）** | ≳ 6 GB | ❌ 不够 | 见下面清单，凑到 7 GB 以上 |

### 要关掉的（按性价比排序，合计约 5.2 GB）

| 进程 | 占用 | 说明 |
|---|---|---|
| chrome（28 个进程） | 2,551 MB | 最划算，先关这个 |
| QQ（8 个） | 1,118 MB | 关 |
| WeChatAppEx + Weixin | 807 MB | 关 |
| claude（4 个） | 766 MB | VS Code 里的 Claude Code 会话进程，演示时不需要 |
| Code（20 个） | 2,398 MB | 15 GB 内存的机器上，**开着 VS Code 跑 7b 会很难** |

⚠️ **WorkBuddy 自己占 3,497 MB，关不掉**（我就在里面跑）。所以算预算时这 3.5 GB 是固定支出。

### 建议的重启顺序（你原计划的重启 + 清界面）

```
1. 重启（彻底清空）
2. 只开 WorkBuddy（打开这份手册）
3. 先查内存 —— 一条命令：
   $os=Get-CimInstance Win32_OperatingSystem; "物理可用 {0:N2} GB | 提交剩余 {1:N2} GB" -f ([int64]$os.FreePhysicalMemory*1KB/1GB), ($os.FreeVirtualMemory/1MB)
4. 物理可用 ≥ 3 GB → 起 Ollama，跑 3b（演示路径）
   物理可用 ≥ 6.5 GB → 也可以跑 7b 裁判
5. 全程别开 Chrome / VS Code / QQ
```

## 3. 演练五步（每步都有"看到什么算成功"）

### Step 1 · 环境自检（约 1 分钟，不依赖 Ollama）


### Step 2 · 连通性冒烟（约 3~5 分钟，只跑 3 条）

- 脚本会先发一句"回复 OK"，**通了才继续**；不通会直接打印三条排查提示。
- 期望：3 条都产出 `answer` 字段 + 三个分数。

### Step 3 · 主验收：18 条可答（**这是 A2 的核心**）


- 耗时估算：3b 生成实测 **14.5~43.8 秒/条**，而每条还要 3 次裁判调用 →
  **3b 生成 + 3b 裁判 ≈ 20~40 分钟；3b 生成 + 7b 裁判 ≈ 60~90 分钟**（7b 慢 2~3 倍）。
- **建议**：先跑 `--sample 3` 拿到"3 条样例 + 一条真数字"，全量放最后。

### Step 4 · 延迟重测（`experiments/latency_profile.json` 还是 7/27 的）

## 4. ⚠️ 三个会毁掉数据的坑（这个项目已经栽过两次）

### 坑 1：`experiments/` 的产物曾经**不在版本控制里** —— 已于 2026-09-14 修掉

旧 `.gitignore` 是 `experiments/*` 全忽略，`llm_evaluation_results.json` 这类**关键证据**没有 git
恢复通道，而 `--sample 3` / `--quick` **会直接覆盖它**。
**现在该规则已取消**（整个 `experiments/` 仅 170KB，已全部纳管），跑出来的数字会被 git 保护。
→ 仍然建议：跑完就 `commit`，别让证据停在 untracked 状态。

### 坑 2：**不要** `nohup ./ollama serve &`

工具调用结束时会把该会话的子进程一起回收 —— 当次能看到 `LISTENING`，**下一次调用就没了**。
（这就是"我明明起过，怎么又没了"的真相。）用第 2 节的方式 A 或 B。

### 坑 3：**不要覆盖 `OLLAMA_MODELS`**

覆盖成 `D:\ollama_models` 或 `C:\Users\REDMI\.ollama\models` 会命中**空壳目录**（0 个 blob），
症状是「**服务在跑、端口通，但 `/api/tags` 返回 `{"models":[]}`、生成全报 `connection_error`**」。
现在用户级变量是对的，**什么都别设**就行。

## 6. 故障对照表

| 症状 | 真因 | 处置 |
|---|---|---|
| `/api/tags` 返回 `{"models":[]}` | `OLLAMA_MODELS` 被覆盖成空壳目录 | 什么都别设，重启 serve |
| 生成全报 `connection_error` | 服务没起 / 被回收了 | 用方式 A 重起，跨调用再验一次 |
| 报 `model requires more system memory` | 物理可用不够 | 按第 1 节关进程 |
| 单条生成 > 60 秒 | 内存紧张导致换页，或用了 7b | 关掉 Chrome/VS Code；确认 `LLM_MODEL=qwen2.5:3b` |
| 结果里出现 `malformed_json` | 小模型没吐合法 JSON | 已接 `format="json"`；偶发属正常，看比例 |
| `Failed to send telemetry event ... capture()` | chromadb 版本兼容噪音 | **无视**，不影响数据 |
| 评测跑到一半想停 | 有 checkpoint 机制 | 直接 Ctrl+C，产物里已有部分结果 |
| 卡住十分钟没输出 | 忘了设 `HF_HUB_OFFLINE=1` | 停掉重跑，命令前先设环境变量 |
