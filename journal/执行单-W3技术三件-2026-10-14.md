## 一、为什么入口要新写（背景，供复核）

三个"老入口"全都绑在旧的 **fastapi-zh 18 条**小集上，不能直接跑 TiDB 评测集：

| 老入口 | 绑定 | 问题 |
|---|---|---|
| `src/evaluation/llm_eval.py` | `data/test_queries.json`（18 条） | 少了 `test_cases` 就回落旧集；且它需要 `golden_answer` 文本 |
| `src/evaluation/acceptance_eval.py` | `data/unanswerable_queries.json`(10) + `multi_evidence_queries.json`(3) | 样本集不对 |
| `scripts/reproduce_latency.py` | `load_test_cases()`（18 条） | 且把**图检索**算进链路（生产默认关） |

🔴 **一个硬约束**：生成层三维里的 **Context Recall 需要「参考答案」文本**。主集
`data/eval_set.jsonl` 只给 `golden_slugs`（指向文档页），**没有参考答** → 算不出来。
所以生成层三维跑在 `data/judge_gold_100.jsonl`（100 条带 `reference_answer`），
**不跑 375 条全量生成**（那 275 条没有参考标准，评不了）。

## 二、执行单一：生成层三维指标 + 端到端拒答链路

**脚本**：`scripts/eval_generation_tidb.py`（主会话新写，已干跑自检）
复用而不重写：三维裁判的 prompt/解析取自 `llm_eval`；拒答三态判定直接用
`acceptance_eval.evaluate_refusal`（跑真实 agent 链路，含 validator 三态）。

**样本**：生成层三维 **100 条**（`judge_gold_100`）+ 拒答链路 **60 条**（主集 `unanswerable` 40
+ `miss_kill` 20）。两者无交集，合计 160 条。

**前置**：**Ollama 必须在跑**，且 3b（生成）与 7b（裁判）都已就位。
拒答阶段自带连通性自检，不通会直接退出（不会产出"系统很爱拒答"的假数字）。

```bash
cd D:/1base/computer/Agent/DevRoot/mcp-rag-hub
unset HTTP_PROXY HTTPS_PROXY ALL_PROXY http_proxy https_proxy all_proxy FTP_PROXY ftp_proxy
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 MCP_RAG_CORPUS=tidb NO_PROXY=127.0.0.1,localhost
./.venv/Scripts/python.exe -u -m scripts.eval_generation_tidb --stage all \
  > .workbuddy/tmp/eval_generation.log 2>&1
```

**阶段可单独重跑**（各自按 id 续跑）：`--stage gen` / `--stage judge` / `--stage refusal` / `--stage report`
**冒烟**：先 `--stage gen --limit 3` 确认 3b 出字正常，再上全量。
**自检（不加载模型、不调 LLM、不写文件）**：`--dry-run`

**规模与时间**（按旧语料实测外推，纯 CPU）
- 生成 100 条：约 15~45 s/条 → **25~75 min**
- 裁判 100 条 × 3 个指标 = 300 次 7b 调用：约 20~40 s/次 → **1.7~3.3 h** ← 大头
- 拒答 60 条（走 agent，含可能的改写重试）：**约 1~2 h**
- 合计 **约 4~7 h**。断点续跑，可分段跑。

**硬约束**
1. 不重建索引：日志须出现 `collection=kb__tidb__bge-small-zh-v1.5__v2`
2. **避开与其它 CE / 大 Docker 任务并行**（7b 常驻约 5GB，叠加 CE 1.1GB 有内存压力）
3. `data/eval_set*.jsonl`、`data/judge_gold_100.jsonl` 只读；不 commit、不 push
4. 拒答脚本会把 `acceptance_eval.OUT_FILE` 改指到本目录，**不得**回写覆盖 9 月那批结果

**产物** `experiments/generation_eval/`
- `gen_100.jsonl`、`judge_100.jsonl`、`refusal_60.jsonl`、`summary.json`

**回报要求**
1. `--dry-run` 两行样本数（应为 100 / 60）与 `--stage gen --limit 3` 的 3 条样例（含 answer 是否为空）
2. 汇总四行：生成条数/失败数/空答数；三维（Faithfulness / Relevancy / ContextRecall）；
   拒答（不可答正确拒答率、误杀率）
3. 是否有 `generation_unavailable` 集中出现（若有 ⇒ Ollama 中途挂了，该批不可用）
4. 各阶段实际耗时；任何报错原文

## 三、执行单二：TiDB 10 万级索引下的延迟画像

**脚本**：`scripts/reproduce_latency.py`（主会话改造，已验 `--help` 与 query 来源）
改动三点：① query 改为取 `data/eval_set.jsonl` 可答样本（默认 20 条），不再绑旧 18 条；
② **图检索默认不计入**（生产默认关闭），需要时用 `--with-graph`；
③ 输出改名 `experiments/latency_profile_tidb.json`，**不覆盖**旧的 fastapi-zh 画像；
另加 `--warmup`（CE 首次前向含惰性初始化，不预热会虚高）与 P95。

🔴 **必须在机器空闲时跑**：同一链路有负载时会全线慢 1.35~2.66 倍（实测空载 12.8s vs 有负载 34s）。
**不要与任何 CE / Ollama / 大 Docker 任务并行。**

```bash
cd D:/1base/computer/Agent/DevRoot/mcp-rag-hub
unset HTTP_PROXY HTTPS_PROXY ALL_PROXY http_proxy https_proxy all_proxy FTP_PROXY ftp_proxy
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 MCP_RAG_CORPUS=tidb NO_PROXY=127.0.0.1,localhost
./.venv/Scripts/python.exe -u -m scripts.reproduce_latency --n 20 --warmup 2 \
  > .workbuddy/tmp/latency_tidb.log 2>&1
```

**规模与时间**：加载 10 万 chunk + 建 BM25 + 加载 CE 约 3~5 min；20 条 query ×（约 0.6s 检索 + CE 约 13s）≈ **5 min**。合计 **约 10 min**。

**产物**：`experiments/latency_profile_tidb.json`（各阶段 mean/min/max/P95 + total + CE 占比）
**日志须含**：`chunks=`、`collection=`、`queries = 20`、`warmup = 2`、以及"必须在机器空闲时跑"那行

**回报要求**
1. 启动三行：chunks 数、collection 名、queries/warmup
2. 四阶段（bm25 / vector / rrf / ce_rerank）的 mean 与 P95，以及 Pipeline Total 与 CE 占比
3. 跑之前**确认机器空闲**（没有其它 python/ollama/docker 重活），并在回报里写明
4. 任何报错原文

**⚠️ 与前值的对比纪律**：旧的 `12.76s → 7.30s（降 43%）` 是 **fastapi-zh / 1445 chunk** 上的数，
与 10 万 chunk 的绝对值**不可直接比**；只有"CE 占比极高、其余四项合计数十毫秒"这个**结构性结论**可比。
