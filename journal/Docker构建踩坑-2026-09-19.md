# 本地容器化：给 mcp-rag-hub 写 Dockerfile 并跑通构建

> 日期：2026-09-19
> 关键词：Docker、Dockerfile、镜像构建、ModelScope、层缓存、容器验证

## 可复用结论（TL;DR）

1. **容器化没跑过就等于没做。** 这份 Dockerfile 写了有一段时间，却**从未被真正构建过**——今天第一次 `docker build` 就暴露一个必然中断构建的缺陷。
2. **ModelScope 的 `snapshot_download` 不创建 `refs/` 目录**。想手写 `refs/main` 必须先 `mkdir -p`，否则报 `Directory nonexistent`。
3. **层缓存让"改一行重跑"极其便宜**：8 分钟的模型下载层走缓存后，重跑只花 6 分 16 秒，而且其中约 6 分钟都花在**导出镜像**上，不在构建逻辑。
4. **同一份代码 + 一个环境变量 = 两种部署形态**。`MCP_RAG_ENABLE_RERANKER` 让 4G/本地启用 CE 精排、2G 只跑 RRF 融合，既不用改代码、也不用分叉镜像。
5. **容器验证要看三件事**：健康检查端点、容器内端到端查询、失败路径是否按设计降级。

## 背景

项目已经在阿里云 2 核 2G 的轻量服务器上用**裸机 venv** 部署并跑通（部署过程记在本地部署手册，`career/` 下、不入库）——放弃 Docker 的原因不是不想用，而是目标机房出网做了白名单，Docker Hub 及所有国内镜像源全部超时，连基础镜像都拉不下来。

但"因为拉不到镜像所以没用 Docker"这个理由，只在**服务器**成立。本地有代理、能拉镜像，所以容器化这条链路其实是**可以在本机闭环**的。欠着它有个实际代价：Dockerfile 一直处于"写了但没验证"的状态——万一它本身有错，就会在某个真正需要它的场合（比如换一台 4G 机器部署）才突然炸出来。

于是今天在本地把它跑通，目标有三个：

1. `docker build` 能成功产出镜像
2. `docker compose up` 能起容器，界面可访问
3. 容器内检索链路端到端可用

## 第一次构建：直接失败

`docker compose build` 跑起来后，前六步都很顺：

```
#5  FROM python:3.11-slim               ✅ 基础镜像
#8  apt-get install libgomp1 curl       ✅（原本担心的 Debian 源超时没有发生）
#9  pip install torch                   ✅ 走清华镜像
#10 pip install -r requirements.txt     ✅
#11 ModelScope 下载两个模型              ✅ DONE 488.4s
#12 RUN printf 'local' > .../refs/main  ❌ 构建中断
```

失败信息：

```
/bin/sh: 1: cannot create /root/.cache/huggingface/hub/models--BAAI--bge-small-zh-v1.5/refs/main:
Directory nonexistent
```

### 根因

`snapshot_download()` 只把模型文件放进 `snapshots/local`，**不会创建 `refs/` 这个目录层级**。而下一行直接往 `refs/main` 里写（这是 HuggingFace 缓存的目录约定，用来标记当前快照版本），目录不存在 → 重定向失败。

### 为什么这个错误值得记一笔

在服务器部署脚本 `dl_models.py` 里，同一个动作是这么写的：

```python
ref = os.path.join(base, 'models--' + m.replace('/', '--'), 'refs')
os.makedirs(ref, exist_ok=True)      # ← 服务器那份有这一步
open(os.path.join(ref, 'main'), 'w').write('local')
```

**服务器那份带着 `os.makedirs`，Dockerfile 里漏了。** 这是一个典型的"同一逻辑两处实现、改的时候只改了一处"——只不过这次两边都没改，而是从一开始就有一处是缺的。

更重要的是它**反证了一件事**：如果这份 Dockerfile 曾经被构建成功过，这个错误不可能存在。所以它确实**一次都没跑过**。

## 修复与重跑

修复只有两行：

```dockerfile
RUN mkdir -p /root/.cache/huggingface/hub/models--BAAI--bge-small-zh-v1.5/refs \
 && mkdir -p /root/.cache/huggingface/hub/models--BAAI--bge-reranker-base/refs \
 && printf 'local' > .../bge-small-zh-v1.5/refs/main \
 && printf 'local' > .../bge-reranker-base/refs/main
```

重跑的耗时很说明问题：**15:59:04 → 16:05:20，共 6 分 16 秒**。而首次构建光下载模型就花了 8 分钟。差值来自 Docker 的层缓存——前六步全部命中缓存，这次只重新执行了第 12 步（秒级）和最后两步：

```
#13 [8/8] COPY . .            DONE 0.6s
#14 exporting to image        导出层 271.8s + 解包 87.8s
    Image mcp-rag-hub:local Built
```

**也就是说，"改一行再跑一次"的边际成本几乎为零，时间全花在把大镜像写进本地存储上。**

最终镜像 **17.7GB**。偏大，原因是 torch 走的是清华 PyPI 镜像上那版（含 CUDA 依赖，2GB+）——这是为服务器出网环境做的妥协。本地或 4G 环境若要瘦身，把 `PIP_INDEX_URL` 换回 `download.pytorch.org/whl/cpu` 即可，CPU 推理功能完全一致。

## 启动与三项验证

```
docker compose up -d
→ mcp-rag-hub   Up (healthy)   0.0.0.0:8501->8501/tcp
→ Uvicorn server started on 0.0.0.0:8501
```

| 验证项 | 做法 | 结果 |
|---|---|---|
| ① 服务健康 | `curl /_stcore/health` | **`ok`**（Dockerfile 里的 HEALTHCHECK 也转成 `healthy`） |
| ② 界面可访问 | `curl /` | **HTTP 200** |
| ③ 检索链路 | 容器内 `python scripts/run_once.py "RAG 混合检索策略"` | **返回 5 条证据** |

第 ③ 项还顺带验了一个**失败路径**。容器的 environment 里没有 `DEEPSEEK_API_KEY`，于是：

```
[llm] 未配置 DEEPSEEK_API_KEY，跳过生成
status: generation_unavailable
answer: （回答生成服务暂不可用，以下为检索到的原始证据，供参考）
        [1] tutorial/query-params.md · 查询参数 ...
```

**这正是系统设计的三态之一**——"LLM 服务不可用"没有被伪装成"知识库信息不足"，而是如实报出技术故障、同时把检索到的原文交出来。这条降级逻辑在本机容器里同样成立。

另外值得一提：向量索引是**通过卷挂载复用**的（`./chroma_db:/app/chroma_db`），容器启动**没有触发重建索引**——挂载设计的价值在这里体现得很直接。

## 环境层的三个坑

这次踩的坑不全在 Dockerfile 里，还有几个是本地环境造成的：

1. **`cmd //c start "" "Docker Desktop.exe"` 启动无效**。命令看起来执行了（还开出一个 cmd 窗口），但等了 100 秒一个 docker 进程都没有。改用 `explorer.exe "D:\Docker\DockerDesktop\Docker Desktop.exe"` 后，10 秒内 6 个进程到位。
2. **PATH 漂移导致 docker CLI 直接失效**。`resources/bin/docker` 是一个 `#!/usr/bin/env sh` 脚本，而当前 shell 的 PATH 里没有 `/usr/bin`（被工具的 shim 目录占满）→ 找不到 `sh`，退出码 127。改用同目录下的 **`docker.exe`**（原生可执行）即可。固定写法：命令开头 `export PATH="/usr/bin:/bin:$PATH"`。
3. **本地请求必须绕开代理**。访问 `localhost:8501` 要设 `NO_PROXY=127.0.0.1,localhost` 并清空所有 `*_PROXY`，否则请求会被代理拦下（表现为连不上，但服务其实是好的）。

## 与 2026-07-31 那次的关系

两次 Docker 经历看起来相似，实际上是两个层次：

| | 2026-07-31（Dify） | 2026-09-19（本项目） |
|---|---|---|
| 部署对象 | **别人的平台**（Dify 开源项目） | **自己的项目** |
| 视角 | 使用者 —— 拉官方镜像、点界面配参数 | 作者 —— 自己写 Dockerfile、定义构建流程 |
| 镜像来源 | Registry 上现成的 | **自己构建** |
| 遇到的坑 | **环境层**：C 盘爆满把 WSL2 引擎挤崩 | **构建层**：Dockerfile 自身的逻辑缺陷 |
| 学到的东西 | 镜像数据目录要配到非系统盘 | 构建期依赖、层缓存、镜像体积权衡 |

那次练的是"**会用** Docker"，这次练的是"**会写** Docker"。

有个细节可以对上：07-31 记下的教训是"镜像数据目录一定要配到非系统盘"，今天查环境时确认 Docker Desktop 装在 `D:\Docker\DockerDesktop`、D 盘剩余 93GB，整个构建过程没有爆盘——**当时那条教训是落地了的**。

## 经验总结

1. **"写了" 和 "跑通了" 之间隔着一个必现的 bug。** 这份 Dockerfile 静态看没有任何问题——语法正确、注释详尽、分层合理，但它一次都没构建过。凡是没被执行过的配置，都只能算草稿。
2. **层缓存是构建脚本的"快速迭代"开关。** 把不常变的部分（依赖安装、模型下载）放在 `COPY . .` 之前，改代码时就不用重跑它们。这次把 8 分钟的下载变成了 0 秒命中。
3. **降级路径也要验。** 容器里没配 API key 反而是个机会——它顺手证明了"LLM 不可用"时系统会如实报故障、并交出检索原文，而不是伪装成业务拒答。
4. **部署约束应该配在部署侧，不该写进代码默认值。** 2G 内存跑不了 1.1GB 的 reranker，这个约束通过环境变量 `MCP_RAG_ENABLE_RERANKER` 表达在启动脚本/编排文件里，代码的默认值保持"按理应有的行为"（启用 CE 精排）。这样同一份代码能同时服务 2G 和 4G 两种环境。

## 遗留

- **容器未注入 `DEEPSEEK_API_KEY`**：compose 的 `environment` 里没有这一项，所以容器内问答只能走原文拼接降级。要完整体验需加 `DEEPSEEK_API_KEY: ${DEEPSEEK_API_KEY:-}`。
- **镜像 17.7GB 偏大**：见上文，是 torch 源的妥协，可按需切换。
- **服务器仍是裸机部署**：2G 机器跑不了 CE 精排这条约束没变，Dockerfile 里的镜像反而带着 1.1GB 的 reranker 而默认不启用——如果确定 2G 场景永远不用 CE，可以考虑出一个不带 reranker 的精简镜像。
- **本地镜像占用**：`mcp-rag-hub:local` 单镜像 17.7GB，用完可用 `docker compose down --rmi local` 清理（注意会删掉镜像，下次需重新构建）。
