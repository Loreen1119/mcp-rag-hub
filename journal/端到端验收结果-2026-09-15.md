# A 组端到端验收结果（2026-09-15）

> 项目**第一次**在新语料 `corpora/fastapi-zh` 上跑完整端到端验收。
> 核心结论：**"能回答问题"这件事第一次有了数据支撑**，且**瓶颈被定位在生成层**。
> 三维分数有 3b 与 7b 两版 —— **以 7b 版为准**，理由见 §2。

## 0. 一句话结论

| 问题 | 答案 |
|---|---|
| 系统能回答问题吗？ | **能**。18 条可答全部产出答案（生成率 **100%**） |
| 该拒答的会拒吗？ | **基本会**。拒答率 **90%**，最难的 near_miss 类 5/5 全对 |
| 多证据问答行不行？ | **不行**。跨文档引用率 **0%** |
| 瓶颈在哪？ | **生成层**，不是检索层（检索证据覆盖 83.3% vs 答案 50%） |
| 答案有没有依据？ | **有**。18 条里 Faithfulness 最低 0.70、无一条"完全无依据" |

## 2. 可答集（`data/test_queries.json`，18 条）

**生成率 18/18 = 100%** —— 没有一条落到 `generation_unavailable`。单条生成 14.5~43.8 秒（3b / CPU）。

### 三维分数：两版裁判对比

| 指标 | 3b 裁判（v1） | **7b 裁判（v2）** | 差值 |
|---|---|---|---|
| Faithfulness | 0.7000 | **0.8556** | +0.1556 |
| Answer Relevancy | 0.6722 | **0.7944** | +0.1222 |
| Context Recall | 0.4778 | **0.6000** | +0.1222 |

### ⚠️ 这张表最容易被误读，必须说清

**两版评的是同一批答案**（生成都用 3b，一字未改）。差 0.12~0.16 **不是答案变好了，是裁判变准了**：

- 3b 当裁判会**打安全分**：18 条里 **13 条 Faithfulness 都是整 0.70**，无区分度；
- 7b 当裁判给出**梯度**（0.70 / 0.90 / 1.00），理由也具体到句子
  （如"缺失了 '装饰器接收位于其下方的函数并且用它完成一些工作' 这个关键信息"）。

**所以"答案质量"只能用 v2（7b）的数字讲；v1 那版没有参考价值。**

| 类别 | Faithfulness | Answer Relevancy | Context Recall | 条数 |
|---|---|---|---|---|
| exact_match | 0.9500 | 0.7750 | 0.7750 | 4 |

### 唯一失手 U08「FastAPI 内置的图形化管理后台（Admin UI）要怎么开启？」

**关键：它不是幻觉，是状态误判。** 答案原文：

> 按照你所选云服务商的指南部署 FastAPI 应用即可……**用户询问关于如何开启内置的图形化管理后台
> （Admin UI），但未在文档中找到相关答案**。文档提及了使用 `fastapi dev` 命令……

也就是说：**LLM 在正文里明确写了"没找到答案"，但 JSON 的 `status` 字段仍填了 `answered`**。
validator 只认 `status` 字段，没识别"正文自述找不到"这种模式 → 判成 `false_acceptance`。

**这是自研拒答链路的一个真实边界情况**，不是随机错误。改进方向两条：
1. prompt 里强化"不确定时必须置 `insufficient_evidence`"的约束；
2. validator 增加交叉校验 —— 正文含"未找到 / 没有提到"类措辞但 `status=answered` 时应改判。

## 5. 两个评测坑（都是实测撞出来的，值得记）

### 坑 1：3b 当裁判 = 打安全分，无区分度

18 条里 13 条 Faithfulness 都是整 `0.70`；项目此前也测过 3b 当裁判会自相矛盾
（同一句里说"大部分信息来自上下文"却按"大量编造"档打 0.10）。
**结论：生成可以用 3b，裁判必须 7b。** 这不是偏好，是数据。

### 坑 2：`num_predict=512` 截断 JSON → **静默记 0 分**

`src/evaluation/llm_eval.py:103` 写死 `"options": {"temperature": 0.0, "num_predict": 512}`。
**3b 的 reason 短、够用；7b 的 reason 更长 → 输出被截断 → `json.loads` 失败 →
`_parse_score` 静默 `return 0.0`，不报错。**

实测 18 条里中招 1 条：S02 的原始输出是
`{"score": 0.9, "reason": "仅有一处轻微的推论性表述：'FastAPI 支持定义多个事件处理器函数…`（句子中间被切断）
→ **真实分 0.9 被记成 0.0**，Faithfulness 均值被拉低 0.05（0.8556 → 0.8056）。

**处置**：不改评测代码（保持产物可复现），改为**后处理恢复** ——
筛出 `score==0.0 且 reason 以"解析失败"开头` 的条目，用正则从截断文本里提取真实 `"score"`
（score 字段在 reason 之前，必然已写出）。恢复结果另存
`experiments/llm_evaluation_results.recovered.json`。

> 这条与项目既往教训同源：**数字变坏而不报错**。已记为待修项 **C8**
> （修法：`num_predict` 提到 1024~2048，或解析失败时正则抢救 score）。

## 6. A4 重测：模块消融 + 延迟

> **C9 已修（2026-09-15 12:30）**，`experiments.py --quick` 首次跑通（12:33~13:17，44 分钟），
> 五个实验全部产出新语料数据 —— `experiments/` 里的旧语料产物已全部替换。
> 下面的消融与延迟都来自**标准入口**（不再是临时脚本）。

### 6.1 模块消融（18 条，新语料）

| 配置 | MRR | Hit@5 | Prec@5 |
|---|---|---|---|
| bm25_only | 0.5469 | 0.8889 | 0.4333 |
| vector_only | 0.7246 | 0.8333 | 0.3889 |
| graph_only | **0.0958** | 0.1111 | 0.0222 |
| concat_naive | 0.5770 | 0.8333 | 0.4333 |
| rrf_fusion | 0.7833 | 0.9444 | 0.5000 |
| **full_pipeline**（双路 + CE） | **0.7889** | **1.0000** | **0.5444** |
| triple_fusion（三路 + CE） | 0.7889 | 1.0000 | 0.5333 |

**三个发现**：

1. **GraphRAG 在真实语料上没有任何增量** —— full（双路）→ triple（三路）**Δ MRR = 0.0000**，
   Prec@5 反而从 0.5444 降到 0.5333。
2. **图检索在最该它擅长的类别上最差**：`graph` 类别下 Graph MRR 仅 **0.0833**
   （同类别 BM25 0.7083 / Vector 0.8571）。
3. **交叉验证成功**：`full_pipeline` 的 **MRR 0.7889 / Hit@5 1.0000** 与 09-12 独立跑的检索评测
   **完全一致** —— 两条独立路径得出同一组数字，说明评测链路可靠。

> ⚠️ 脚本输出里有一句**硬编码结论与数据矛盾**：
> `[OK] 三路混合检索（+GraphRAG）MRR=0.7889，图检索为双路召回提供了增量价值`
> —— 实测 Δ=0.0000。这句是 `generate_report` 里写死的文案，不随数据变化。已记为 **C10**。

### 6.2 延迟：标准入口 vs 上午的临时脚本

| 阶段 | **标准入口（13:17）** | 临时脚本（09:43） | 倍数 |
|---|---|---|---|
| BM25 | 5.23 ms | 7.08 ms | 1.35× |
| 向量 | 18.25 ms | 37.51 ms | 2.06× |
| 图 | 7.08 ms | 11.13 ms | 1.57× |
| RRF | 0.18 ms | 0.26 ms | 1.44× |
| **CE 精排** | **12,763.11 ms** | 33,973.76 ms | **2.66×** |
| **合计** | **12,793.85 ms（12.8 秒）** | 34,029.74 ms | 2.66× |


### 三个必须说清的点

**① 旧数字（395ms、CE 占 94%）完全不可比。**
那是**旧语料（3 个 chunk）+ 英文 `ms-marco-MiniLM-L-6-v2`（~80MB）** 的产物 ——
候选只有 3 条、CE 只需前向 3 次。现在候选几十条、模型换成 `bge-reranker-base`（~1.1GB），
两个变量同时变了。**README 里"待重测"的标注是对的，旧数字确实不能用。**

**② 文档说"CE 限制在 Top-20 候选内"，与代码不符。**
`FusionPipeline.run` → `CrossEncoderReranker.rerank(query, fused, top_k=ce_top_k)`，
其中 **`top_k` 只控制「输出几条」，不控制「对几条打分」** ——
`pairs = [(query, r.chunk.content) for r in candidates]` 是对**全部候选**做前向（`src/fusion.py:122-123`）。
按二路（BM25 20 + Vector 20）约 40 条、三路约 60 条候选算，即可解释十几秒级的 CE 耗时。

**③ 纯 CPU 推理的绝对值对机器负载极敏感。**
同一套管线、同样的 18 条 query，**机器有负载时比空闲时全线慢 1.35~2.66 倍**（见 6.2 对比表）。
引用延迟数字时**必须带上"机器空闲"这个前提**，否则换个环境一跑就对不上。
**以标准入口的 12.8 秒为准。**

### 优化方向（按性价比排序）

1. **RRF 之后先截断再送 CE**：只对 top 20 打分 → 时间约降 60%。
   这是最直接的一刀，而且**正是文档里以为已经做了的事**。
2. **限制 CE 输入长度**（`max_length`）：chunk 长时收益明显。
3. **int8 量化 / ONNX Runtime**：CPU 上通常有 2~4 倍。
4. **换更小的中文 CE**：代价是排序质量。

> 这条对面试反而是好素材：**"我实测定位到 CE 占 99.8% 的延迟；
> 而文档里以为已经限制了候选数、实际代码没有 —— 这是把性能问题从『感觉慢』变成『知道慢在哪』的过程。"**

## 7. 面试口径（怎么说这一轮）

**可以说：**
- "检索侧有 18 条四阶段消融数据（CE Hit@5 = 100%）；生成侧我在新语料上跑完了端到端 ——
  18 条可答**全部产出答案**，7b 裁判的 Faithfulness 0.86、最低一条也有 0.70；
  10 条拒答里 9 条正确拒答，其中 near_miss 那 5 条全部拒对。"
- "我实测定位到瓶颈不在检索：多证据题的关键词覆盖，检索证据 83.3%、答案只有 50%；
  semantic 类的 Context Recall 只有 0.28 —— 该找的都找到了，是生成没整合起来。
  下一步优化该投在生成层。"
- （加分项）"评测本身我也踩了两个坑并查清了：3b 当裁判会打安全分、无区分度；
  7b 的评分 JSON 因为 `num_predict=512` 被截断、静默记 0 分。两个都定位到了根因。"
- （加分项）"延迟我也量了：**CE 精排占 99.8%（12.8 秒/条）**，其他四个环节加起来只有 31ms。
  而且我发现文档里写的『CE 限制在 Top-20 候选内』实际代码没实现 ——
  `top_k` 只控制输出条数、不控制打分条数。"
- （加分项）"消融还发现了件事：**GraphRAG 这条路在真实语料上完全没有增量** ——
  双路 0.7889、加图变三路还是 0.7889，Prec@5 反而略降；而图检索在『图关联型』
  问题上得分最低（MRR 0.083）。所以我把 KG 降级成了默认关闭的可选开关。"

**不要说：**
- ❌ 不要说"换 7b 之后答案质量提升了 15%" —— **答案是同一批**，变的是裁判
- ❌ 不要把"跨文档引用率 0%"当系统缺陷抱怨 —— 说"3b 目前做不到跨文档整合，ME01 就是证据"
- ❌ 不要把 U08 说成"幻觉" —— 它是**状态误判**，答案正文自己都写了"没找到"
- ❌ 不要报 3b 版的 Faithfulness 0.70 —— 那是无区分度的安全分
