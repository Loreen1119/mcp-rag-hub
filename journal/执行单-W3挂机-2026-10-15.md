
**第 0 步 · 自检（不加载模型、不调 LLM、不写文件）**

```bash

```
→ 应输出两行样本数 **100 / 60**。不是这两个数就停下，别开全量。

**第 1 步 · 冒烟（3 条，确认 3b 出字正常）**

```bash

```
→ 看 `eval_gen_smoke.log`，3 条 answer **非空**才继续。若空答/Ollama 没起，先修，别开全量。

**第 2 步 · 全量（分段跑，各自按 id 续跑）**

```bash
./.venv/Scripts/python.exe -u -m scripts.eval_generation_tidb --stage gen \
  > .workbuddy/tmp/eval_generation_gen.log 2>&1

./.venv/Scripts/python.exe -u -m scripts.eval_generation_tidb --stage judge \
  > .workbuddy/tmp/eval_generation_judge.log 2>&1

./.venv/Scripts/python.exe -u -m scripts.eval_generation_tidb --stage refusal \
  > .workbuddy/tmp/eval_generation_refusal.log 2>&1

./.venv/Scripts/python.exe -u -m scripts.eval_generation_tidb --stage report \
  > .workbuddy/tmp/eval_generation_report.log 2>&1
```

> 也可以直接 `--stage all` 一把梭，但分段跑的好处是：某一阶段挂了能定位到段、能单独续跑。
> **建议分段**，每段跑完 `tail` 确认没崩再下一段。

**产物**：`experiments/generation_eval/{gen_100.jsonl, judge_100.jsonl, refusal_60.jsonl, summary.json}`

**回报要求（分支会话跑完给主会话/用户）**

## 三、进度盯法（用户手机抽空看）

用户手机 WorkBuddy 随时让分支会话 `tail` 这几个日志即可，不用一直盯：

| 阶段 | 看哪个日志 | 看什么 |
|---|---|---|
| 冒烟 | `.workbuddy/tmp/eval_gen_smoke.log` | 3 条 answer 是否非空 |
| 生成 | `.workbuddy/tmp/eval_generation_gen.log` | 进度条（x/100） |
| 裁判 | `.workbuddy/tmp/eval_generation_judge.log` | 进度（x/100 × 3 指标，最慢） |
| 拒答 | `.workbuddy/tmp/eval_generation_refusal.log` | 进度（x/60） |
| 延迟 | `.workbuddy/tmp/latency_tidb.log` | 四阶段耗时 |

**给分支会话的盯进度指令**：每阶段跑完 `tail -3` 对应日志，确认「没崩、进度正常」再进下一段；任何 EXIT 非 0 / 报错原文，先停下记日志，别盲目重跑（避免覆盖已续跑的 id）。
